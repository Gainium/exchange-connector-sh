# 002 — plan

Spec: [`../specs/002.kraken-spot-ambiguous-userref-lookup.md`](../specs/002.kraken-spot-ambiguous-userref-lookup.md)

## Solution

Fixes the root cause named in spec §3 — the `return`-on-first-match — not the
callers that reach it.

In `src/exchange/exchanges/kraken/index.ts`, in both userref scans inside
`getOrder`, collect the matching `[txid, orderData]` entries instead of
returning from inside the loop, then branch on the count:

- `0` → `throw` the existing not-found string (unchanged control flow)
- `1` → convert and `returnGood`, exactly as today
- `>1` → `returnBad` with an ambiguity reason

`returnBad` rather than `throw`, deliberately: a throw in the open-orders scan
is caught below and re-asked as a closed-orders lookup (which is ambiguous for
the same reason), and `handleKrakenErrors` would spend the retry ladder on a
verdict that is deterministic.

### Reason wording (spec §4.6)

```
Ambiguous order lookup: client order id <id> maps to Kraken userref <n>, which
matches <k> open orders. Kraken spot cannot resolve a client order id; refusing
to guess. Address this order by its txid.
```

Checked against main-app `core/src/bot/main.ts`: contains none of the 32
`unknownOrderMessages` substrings (`:200`) and fails
`isDefinitiveOrderNotFound`'s `/\border not found\b/`, `/\border does not
exist\b/`, `unknownoid` tests (`:403`) — so main-app reads it as "the call did
not succeed", retries, and takes no quarantine strike.

### JIT legacy tier

**Tier 0.** `getOrder`'s spot branch is I/O-coupled legacy, but the decision
being fixed — "how many matches did I get" — is three lines inside the existing
loop. Extracting a pure `resolveUserrefMatches()` module would move a `for`
loop behind an interface without removing a single mock from the test (the test
still needs a stubbed `spotClient` to reach `getOrder`'s branch at all), so it
buys nothing. Tier 1 would be scope creep on a hot money path.

## Blast Radius

1. **Other call sites of the changed code.** `getOrder` is called internally by
   `cancelOrder` (`:2623`) and externally over `/order`. The userref scans are
   private to `getOrder` — no other reader. `getOrdersBatch` (`:2035`)
   deliberately batches txids only and is untouched.
2. **`core/` submodule** — yes: `exchange-connector-sh`, deployed platform-wide
   (cloud egress fleet + self-hosted). Behaviour change is confined to the
   Kraken spot client-id path.
3. **Owned contracts** (`exchange-connector/CLAUDE.md`): `BaseReturn<T>` shape
   unchanged — a `returnBad` on an existing method, which every caller already
   handles. No endpoint, no `exchangeLimits`, no `admin-config` change. The
   cross-service coupling that DOES matter is the reason-string one, handled
   above as spec §4.6.
4. **Tests that must stay green.** `kraken/spot-txid-lookup.spec.ts` asserts the
   client-id path still reaches `getOpenOrders` exactly once with an empty open
   list (its last block) — that is the 0-match case, unchanged. Plus the other
   five kraken specs and the full `npm test` suite.
