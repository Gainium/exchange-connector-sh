# 002 — WhiteBit exchange integration (spot + USDⓈ-M perps)

## Build order

1. **Resolve the two remaining narrow open items** (spec §3.1-new: is
   leverage account-wide or per-market; §3.2-new: where margin-type is
   set) by reading `update-collateral-account-hedge-mode`,
   `collateral-account-summary`, and the `collateral-*-order` endpoint
   pages in full — small, targeted reads, not the open-ended futures-
   existence question the spec started with (that's resolved: WhiteBit's
   futures ride the same "collateral account" as leveraged-margin spot,
   distinguished only by the `_PERP` symbol suffix — §2.2).
2. `src/whitebit-custom/` — hand-rolled signing client (spec §2.5): a
   `WhitebitClient` wrapping `fetch`/`axios` with `signRequest(path, body)`
   implementing the nonce/base64-payload/HMAC-SHA512 scheme, plus thin
   per-endpoint methods as each is implemented in step 4. Unit-testable in
   isolation (signature bytes are deterministic given fixed inputs) —
   `src/whitebit-custom/signRequest.spec.ts`, mocha, matching
   `kraken-custom/serializeParams.spec.ts`'s template: fixed key/secret/nonce
   fixture in, assert the exact `X-TXC-SIGNATURE` hex string out.
3. `src/exchange/exchanges/whitebit/limit.ts` — rate-limit tracker, shaped
   like `kraken/limit.ts` (exported bound-methods object), values from
   spec §3.5 once resolved in step 1.
4. `src/exchange/exchanges/whitebit/index.ts` — `WhitebitExchange extends
   AbstractExchange implements Exchange`. Build in the order the spec's
   §2.2 table is *most* confirmed to least: `getBalance` → `getExchangeInfo`
   / `getAllExchangeInfo` (needed by the symbol mapper, step 5) →
   `getCandles` (§2.3's column-order gotcha — write
   `whitebit/candle-parsing.spec.ts` first, red, per gate 2) → `getTrades`
   → `openOrder`/`cancelOrder`/`getOrder`/`getAllOpenOrders` →
   `getUserFees`/`getAllUserFees`/`getAccountFills` → `getAllPrices`/
   `latestPrice` (`GET /api/v4/public/ticker`) → usdm-only methods last,
   through the `collateral-account/*` endpoint family, not the spot
   endpoints (`futures_changeLeverage`, `futures_getHedge`/`setHedge`,
   `futures_leverageBracket` derived from Market Info's `max_leverage`,
   `futures_getPositions`; `futures_changeMarginType` once step 1 finds
   where it's actually set) → stub the broker/affiliate family (§2.8)
   exactly like Kraken's stubs.
5. Symbol mapper (spec §2.4) — `WhitebitSymbolMapper`, singleton per
   variant, built from step 4's `getAllExchangeInfo`. Test:
   `whitebit/symbol-mapping.spec.ts` — feed a fixed Market Info fixture
   (once §3.4's real suffix pattern is known), assert `toOurSymbol` /
   `toWhitebitSymbol` round-trip and correctly separate spot vs. usdm
   markets from one combined list.
6. Registration (spec §2.7): `types.ts` enum members → `exchangeChooser.ts`
   → `verify.ts` (`verifyWhitebit`, §3.7's permission-check question
   resolved here) → `additionalApis.ts`.
7. `.env.sample` / `package.json` (spec §2.9) — only if step 2 ends up
   needing a new dependency; otherwise no change.
8. `npm test` — full green, including the new WhiteBit spec files
   alongside the existing 17.
9. CHANGELOG + version bump, per this repo's release convention.

## Contract decisions (resolving what the spec left open)

- Hand-rolled client (§2.5), not a wrapped SDK — no suitable npm package
  exists, unlike Kraken.
- Two enum variants only, no `whitebitCoinm` (§2.1) — and unlike Kraken's
  `krakenCoinm`, this repo will **not** declare an enum member for a variant
  it doesn't register, to avoid repeating that inconsistency.
- Broker code stays an accepted-but-unused parameter (§2.8) — explicit
  product/ops decision, not a gap to silently fill later without a spec
  update.
- No `wsCode` field added unless step 1's research contradicts spec §3.6's
  current "no evidence of divergence" finding.

## Blast radius

1. **Other call sites.** `ExchangeEnum` is read by every consumer of this
   repo's public surface (`exchangeChooser`, `additionalApis`, `verify`,
   and this repo's own `getAllExchangeInfo`-style callers) — grepped, all
   four are the registration files already listed in Build order step 6.
   No other file in this repo pattern-matches on a hardcoded exchange list
   outside those four plus `src/utils/index.ts`-style classification lists
   (none exist in this repo — that's an `app-sh` concern, out of scope
   here per spec §4).
2. **`core/` submodule.** This repo *is* the `core/` submodule consumed by
   `exchange-connector` (no `.gitmodules` here, confirmed in spec 001's own
   blast-radius note) — this PR's adapter is inert until `exchange-connector`
   bumps its pointer to this commit, which is explicitly out of scope
   (spec §4). Nothing in this repo breaks existing exchanges by adding a
   new one behind new enum branches.
3. **Cross-repo contract.** `ExchangeEnum` string values (`whitebit`,
   `whitebitUsdm`) become a contract the moment `websocket-connector-sh`
   (spec 003, same integration) and any later consumer read them — pick
   the final strings in this PR and do not rename them afterward without
   updating every consumer.
4. **Other tests exercising this path.** None yet — new files only, no
   existing test touches WhiteBit-shaped code. The existing 17 specs (spec
   001) must stay green; nothing in this plan touches their modules.
