# Plan 003 — Kraken spot native `cl_ord_id`

Spec: `specs/003.kraken-spot-native-cl-ord-id.md`.

> **Amended for §4.9 — the three-way discriminator.** See
> "## Amendment: the free-text arm (§4.9)" at the bottom. The Solution below is
> the LEGACY arm and is unchanged; the amendment adds the shape test in front of
> it and the verbatim path behind it.

## Solution

One private encoder plus four call-site edits in
`src/exchange/exchanges/kraken/index.ts`. No new dependency
(`@siebly/kraken-api@1.0.6` already types `cl_ord_id` on every leg), no change
to `BaseReturn`, no change to any `CommonOrder` field.

1. **`krakenClOrdId(clientOrderId)`** — `sha256(id).hex.slice(0, 32)`, Kraken's
   short-UUID form (spec §4.1). Reuses `createHash` from `crypto`, already
   imported at `:40` and already used in this file at `:1326`; the repo has no
   other hashing helper (`grep -rn 'createHash|md5|sha256' core/src` finds only
   `okx/index.ts:191` and this file's own key fingerprint), so nothing existing
   is being duplicated.
2. **`submitOrder` (`:1892`)** — `userref:` → `cl_ord_id:` (spec §4.2, §4.3).
   Replacement, not addition: Kraken rejects a request carrying both.
3. **Open-orders scan (`:2534`)** — match `orderData.cl_ord_id` against the
   encoded id first (§4.4); on zero matches fall back to the existing userref
   scan, excluding rows that carry any `cl_ord_id` (§4.6). The venue call stays
   unfiltered, so both passes read one payload.
4. **Closed-orders fallback (`:2603`)** — `getClosedOrders({ cl_ord_id })`
   first, confirming the returned rows carry it (§4.5); on zero matches, the
   existing `getClosedOrders({ userref })` call and scan, unchanged (§4.6).
5. **`cancelOrder` (`:2685`)** — unchanged behaviour, comment added recording
   why (spec §4.7 / §5.3). It resolves through `getOrder`, which this change
   makes exact, and cancels by the real txid.

The client-side re-check in 3 and 4 is not redundant with the request filter:
if a Kraken deployment ignored an unrecognised `cl_ord_id` parameter it would
return *every* order, and matching only on the request having been sent would
resolve an arbitrary one — the failure this whole issue is about.

## Legacy-order fallback: why it stays

Deleting the userref scan would be a smaller diff and is wrong. 334 orders are
resting on live Kraken accounts right now with a `userref` and no `cl_ord_id`;
a lookup for one of them would return "Order not found in history", which is in
main-app's `unknownOrderMessages` — so `_handleUnknownOrder` would retire a live
order as a phantom. That is the sibling failure #535 already caused. The
fallback drains on its own as those orders fill or cancel.

1. **Other call sites of the derived userref.** `grep -n 'userref' index.ts`:
   `:1892` submit, `:2534`/`:2551` open scan, `:2603`/`:2627` closed scan,
   `:2973` `getAllOpenOrders` display field (spec §5.4, deliberately untouched),
   and comment text. No other file in `core/src` derives a Kraken userref.
2. **`core/` submodule** — yes, this is `exchange-connector-sh`, shared with the
   self-hosted connector. The change is confined to the Kraken spot branch of one
   exchange class; no shared type, helper or base-class signature moves.
3. **Cross-service contracts** (root `CLAUDE.md` Danger List): `BaseReturn<T>`
   unchanged, `CommonOrder` unchanged, `exchangeLimits` unchanged, no REST route
   or socket event touched. What changes is the wire payload *to Kraken* and the
   parsing of Kraken's reply — both inside this class.
4. **Consumer semantics.** main-app reads `data.orderId` (venue txid) and copies
   it onto the order row (`bot/main.ts:7974`). This change makes that value
   correct more often and never makes it less correct — spec §5.3 is the
   constraint that kept `cancelOrder` structural.
5. **Other tests on this path that must stay green.**
   `ambiguous-userref.spec.ts` (002 — the legacy path, and the refusal wording
   main-app's phantom-retire logic depends on), `spot-txid-lookup.spec.ts`,
   `phantom-order-status.spec.ts`, `cancel-verdict.spec.ts`,
   `partial-fill.spec.ts`, `fill-price.spec.ts`, `rate-limit.spec.ts`,
   `outage-backoff.spec.ts`, `nonce-logging.spec.ts`.

   One assertion in `ambiguous-userref.spec.ts` changes: the not-found case
   counted venue calls (`getOpenOrders + getClosedOrders === 2`). Spec §5.2
   legitimately makes that three — one open, one closed by `cl_ord_id`, one
   closed by legacy `userref`. The behaviour under test (falls through open →
   closed, reports not found, never QueryOrders) is unchanged and still
   asserted; only the count moves, and it is relabelled to say what it counts.

## JIT extraction tier

**Tier 0/1.** The causal path is one method on a 3,000-line exchange class that
mixes decisions with venue I/O throughout. The only decision worth isolating is
the encoding, and it is extracted into its own pure, separately-testable method
(Tier 2 for that fragment). Restructuring `getOrder`'s open/closed fallback into
ports is a modernization task, not something to spring on a fix whose whole
point is that a live venue identifier is wrong.

## Amendment: the free-text arm (§4.9)

Spec §4.9. This is the **connector half of a two-repo change**; the other half is
main-app `core/specs/010.kraken-spot-client-order-id-length.md`, which makes
`getOrderId()` emit a ≤18-character id for Kraken spot. Encoding the id worked;
what it cost was that the id on our order row was not the id Kraken held, so
every call site had to re-derive the encoding and nothing that starts *at Kraken*
could get back to a Gainium order (spec 010 §1.3).

### Solution

Two private methods and three call-site edits, all in
`src/exchange/exchanges/kraken/index.ts`. Still no new dependency, no change to
`BaseReturn`, `CommonOrder` or any route.

1. **`isKrakenFreeTextClOrdId(id)`** — the discriminator: 1–18 characters, all
   printable ASCII. A property of the id, so nothing is stored and the two
   populations coexist for as long as legacy orders keep resting. Callers test
   `isKrakenSpotTxid` first, so a txid never reaches it.
2. **`krakenClOrdId(id)`** — now returns the id **verbatim** when it is already
   legal free text, and falls through to the existing sha32 short-UUID encoding
   otherwise. One method, so `submitOrder`, `getOrder` and `cancelOrder` cannot
   disagree about what the venue was told — the same property the original
   encoder was built for.
3. **`krakenClOrdIdCandidates(id)`** — the `cl_ord_id` values an order under this
   client id could be carrying: `[sha32]` for a legacy id, `[verbatim, sha32]`
   for a free-text one (§4.9.3's split-deploy bridge).
4. **Open-orders scan** — matches a row whose `cl_ord_id` is any candidate. The
   call is already unfiltered, so the second candidate costs nothing here.
5. **Closed-orders fallback** — asks `getClosedOrders({ cl_ord_id })` per
   candidate, in order, stopping at the first hit; the second is paid for only
   when the first missed. Same ceiling of two ClosedOrders calls on a miss that
   §5.2 already accepted (there it was `cl_ord_id` then `userref`).
6. **The legacy `userref` scan is gated on the id being legacy-shaped** — in
   both the open and the closed pass. §4.9.2: shortening does not remove the
   collision (`parseInt('D-RO-Ab3', 16)` is still 13), and a free-text id can
   only belong to an order that carries a `cl_ord_id`, so the scan could only
   ever return somebody else's order. `ambiguousUserrefMatch` and its wording are
   untouched and still reachable for legacy ids.

`submitOrder` and `cancelOrder` need no edit of their own: submit already routes
through `krakenClOrdId`, and cancel already resolves through `getOrder` and
cancels by the real txid (§4.7 — still true and still asserted).

### Deploy order

**None required**, deliberately. Connector-first is a no-op until main-app emits
short ids; main-app-first is hashed consistently by the running connector; and
the §4.9.3 bridge covers the orders placed inside the window. Getting this wrong
is not a cosmetic risk — an unresolvable resting order produces "Order not found
in history", which main-app's `isDefinitiveOrderNotFound` reads as a venue denial
and retires as a phantom.

### Blast radius (delta over the list above)

1. **`krakenClOrdId` gained a branch.** Its two other callers are the open and
   closed scans, both edited here; `submitOrder` is the third. `grep -n
   'krakenClOrdId\|userref' index.ts` shows no other use, and `getAllOpenOrders`'
   `userref` display field is still untouched (spec §5.4).
2. **Legacy behaviour must be bit-identical.** A 35-character id takes exactly
   the path it took before: sha32 `cl_ord_id`, then the userref scan, then the
   ambiguity refusal. This is what protects the **369 live Kraken spot orders**
   (56 bots, 21 users; **361** on bots holding two or more at once) measured in
   prod on 2026-09-05, none of which carries a native `cl_ord_id` yet.
3. **`getOrdersBatch` is untouched** — txids only, as before.
4. **`core/` submodule** — still `exchange-connector-sh`, shared with the
   self-hosted connector. A self-hosted install pairing this connector with an
   OLDER main-app only ever sees 35-character ids, i.e. the legacy arm.
