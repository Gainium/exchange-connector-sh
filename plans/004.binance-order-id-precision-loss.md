# 004 — Binance order ids lose precision before they are stored

Spec: `specs/004.binance-order-id-precision-loss.md`.

## 1. Solution

The digits only exist in the raw HTTP body, so the repair has to happen before
`JSON.parse` sees them.

1. **`src/binance-custom/losslessOrderId.ts` (new).** `quoteUnsafeIntegerIds(raw)`
   rewrites `"orderId": <digits>` as `"orderId": "<digits>"` when the digits exceed
   `Number.MAX_SAFE_INTEGER`, then `parseBinanceResponse` runs `JSON.parse` on the
   result. The scan is string-literal aware — it always steps over a complete string
   literal — so digits inside a `clientOrderId` or an error `msg` are unreachable
   (§4.4). Non-JSON and empty bodies pass through unchanged, matching axios (§4.5).
2. **`src/binance-custom/index.ts`.** Each exported client (`USDMClient`,
   `CoinMClient`, `MainClient`) gets a constructor that injects
   `transformResponse: [parseBinanceResponse]` into the vendor's `requestOptions`.
3. **`src/exchange/exchanges/binance/index.ts`.** `cancelOrderByOrderIdAndSymbol`
   (`:1230`) and `futures_cancelOrderByOrderIdAndSymbol` (`:1273`) pass the caller's
   id verbatim instead of `+orderId` (§4.7).

No type declaration is changed. Widening `RebateRecord.orderId` to `number | string`
was tried and **reverted** — see §3.4.

### Contract decisions the spec left open

- **Where the parser is injected.** At the `binance-custom` subclass rather than at
  the three `new …Client(...)` call sites in the exchange adapter. The vendor's third
  constructor argument is a documented `AxiosRequestConfig` passthrough
  (`BaseRestClient.d.ts:17`), verified to reach axios and to receive the raw body
  string. This covers every client the module exports, including any added later,
  and needs no change at the call sites. A caller that supplies its own
  `transformResponse` still wins.
- **Which keys are preserved.** `orderId` only. Widening `UNSAFE_INT_KEYS` retypes a
  field from number to string for every `BaseReturn<T>` consumer, so it is a
  deliberate per-key decision, not a default.
- **String, not BigInt.** `CommonOrder.orderId` is already `string | number` and both
  converters already stringify, so a string needs no downstream change. A `BigInt`
  would not survive `JSON.stringify` across the HTTP hop to main-app.
- **No new dependency.** `json-bigint` and friends were rejected: adding a runtime
  dependency to a shared `core/` submodule is a larger call than the fix, and the
  scanner is ~60 lines and exercised by 22 unit cases.

### Reuse check (before writing anything new)

`grep -rn "json-bigint\|JSONbig\|lossless\|BigInt(" core/src` → no hits, and
`core/src/utils/` holds only `adminConfig / math / mutex / redact / redis / sleepUtils`.
There is no existing lossless-parse or big-integer helper in this repo or its `core/`
to wire up, so the module is genuinely new rather than a duplicate.

### JIT legacy tier

**Tier 0 / Tier 1.** The two cancel paths are on the causal path but the change there
is one expression each; extracting them would be scope creep. The new parsing logic
is a pure module with no infra imports (Tier 2 by construction) — verified: it
imports nothing.

## 3. Blast Radius

1. **Other call sites of the changed code.** `grep -n "new USDMClient\|new CoinMClient\|new MainClient"`
   → `src/exchange/exchanges/binance/index.ts:223,236,244` only, all inside this
   adapter, all now covered automatically. `grep` for `+orderId` / `Number(orderId)`
   in the adapter → exactly the two sites fixed; every other Binance lookup addresses
   orders by `origClientOrderId` (a string) and is untouched.
2. **This is a `core/` submodule** (`exchange-connector-sh`), shared and deployed
   platform-wide. The parent pointer must be bumped at ship time.
3. **Contracts this repo owns** (`CLAUDE.md` → "What this service OWNS / EMITS"):
   - **`BaseReturn<T>` — Danger List #1, the most load-bearing shape on the platform.**
     Not restructured. The only change is that `CommonOrder.orderId` /
     `FuturesCommonOrder.orderId` may now be a `string` where a >2^53 id previously
     arrived as a rounded `number`. Both are **already declared** `string | number`
     (`src/exchange/types.ts:355,461`), and both converters already emit a string
     (`:3225` `` `${order.orderId}` ``, `:3296` `.toString()`), so no consumer sees a
     new shape. main-app stores the field in a mongoose `RequiredString`.
4. **`RebateRecord.orderId` — considered, deliberately left alone.** It is declared
   `number` and cast straight from the raw body (`:379`), so it *is* reachable by the
   transform. Widening it to `number | string` **breaks the parent repo's build**: the
   parent carries its own stale duplicate of `src/exchange/types.ts` (274 diff lines
   from core's at HEAD), and `src/exchange/exchange.service.ts:48` requires the two
   `RebateRecord`s to stay structurally identical. Keeping the type as-is is the right
   call anyway: rebate records come from Binance **spot**
   (`sapi/v1/apiReferral/rebate/recentRecord`), whose order ids are ~10 digits, so the
   `Number.isSafeInteger` guard means the transform never fires on that path. Recorded
   here rather than dropped silently — if a Binance spot rebate id ever crosses 2^53,
   this field would become a string while its type still says `number`, and the type
   (in **both** copies) would have to be widened together.
   Sole consumer is main-app `src/utils/orders.ts:193`, which builds
   `` `${d.orderId}-${d.asset}-${d.symbol}` `` and does no arithmetic, so it would be
   safe at runtime either way.
   - **Redis `exchangeLimits`** / **`admin-config`** — untouched.
   - **paper-trading contract mirror** — untouched; no endpoint or shape changed.
4. **Other tests on this path.** Whole `core/` suite: 453 passing, 0 failing.
   `describeBinanceError.spec.ts` and `venue-fee-capture.spec.ts` exercise the same
   adapter and stay green.

### Explicitly NOT covered by this change

The websocket-connector half (spec §5). `ORDER_TRADE_UPDATE` is parsed by a different
service's vendor WS client and main-app's `core/src/bot/main.ts:5101` overwrites the
stored id on every fill, so a filled order's id is re-rounded after this fix stores it
correctly. This change is nonetheless the required **first** step: §4.7 must be live
before the websocket side starts emitting exact ids, or the `+` in the cancel paths
would convert a newly-correct id into a wrong one.
