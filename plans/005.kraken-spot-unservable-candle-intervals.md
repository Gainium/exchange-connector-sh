# 005 — plan

Implements spec `005.kraken-spot-unservable-candle-intervals.md`.

## 1. Solution

Both changes live in the **spot** branch of
`KrakenExchange.getCandles` (`core/src/exchange/exchanges/kraken/index.ts`) plus
one new pure module beside it.

### 1.1 — new pure module `kraken/candles.ts` (spec §3.1, §3.2)

Tier 2 per the JIT-legacy runbook: the two decisions this bug is about are
arithmetic over plain data, so they go in a pure module with no client, no
`Logger`, no `this`. Precedent for a sibling module in this directory:
`fees.ts`, `limit.ts`.

- `KRAKEN_SPOT_OHLC_INTERVALS` — the venue's accepted `interval` values
  (`1,5,15,30,60,240,1440,10080,21600`). This is the set the existing inline
  cast at the call site only *names*; making it a value is what lets anything
  check it.
- `KRAKEN_SPOT_OHLC_MAX_CANDLES = 720` — the endpoint's fixed response cap,
  measured in spec §2.3.
- `krakenSpotCandleSource(interval)` → `{ baseMinutes, bucketMs } | undefined`.
  Native intervals return themselves with `bucketMs: 0` (no aggregation);
  `3m`/`2h`/`8h` return `1`/`60`/`240` plus the target bucket width;
  anything Kraken cannot express returns `undefined`.
- `krakenSpotWindowIsUnreachable(to, baseMinutes, now)` → boolean. True only
  when `to` is given and is strictly older than the oldest candle the endpoint
  can return (`now - (720 + 5) * baseMinutes * 60_000`; the +5 pad keeps a
  window that Kraken *could* have served from ever being short-circuited).
- `aggregateCandles(candles, bucketMs)` — buckets ascending base candles by
  `floor(time / bucketMs) * bucketMs`. open = first open, close = last close,
  high/low = numeric extremes emitted as the **original strings** (no reparse,
  so no precision loss), volume = sum.

### 1.2 — contract decisions the spec left open

- **Bucket origin is the Unix epoch, not `from`.** 3m/2h/8h all divide 24 h
  evenly (480/12/3 buckets per day) and epoch 0 is a UTC midnight, so
  epoch-anchored buckets land on the same boundaries every other venue uses.
  Anchoring on `from` would make the same bar different per caller.
- **Zero-volume filler contributes time and volume, never open/high/low/close**
  (spec §2.4). The first *traded* base candle in a bucket sets the open; a
  bucket that is entirely filler still emits a flat, zero-volume bar, which is
  how Kraken presents a no-trade bar natively.
- **A leading partial bucket is dropped; a trailing one is kept.** If the base
  data starts mid-bucket its open/high/low are missing minutes and the bar
  would be wrong. The trailing bucket is the live in-progress bar, which is
  what every connector already returns as its last candle.
- **Volume is summed as a float, then `round`ed to the widest decimal place
  seen among the inputs and stringified with `convertNumberToString`** — both
  already exist in `core/src/utils/math.ts`. Reusing them is what keeps
  `0.1 + 0.2` out of the response.
- **An unreachable window returns `returnGood([])`, not an error** (spec §4).
  Same bytes as today; only the venue request disappears.
- **An unexpressible interval returns `returnBad(KrakenError)` with code
  `400`** and no venue call — so it can never enter `handleKrakenErrors`'
  retry ladder. With the current `ExchangeIntervals` enum this branch is
  unreachable; it exists so that adding a twelfth interval fails loudly on our
  side instead of as `EGeneral:Invalid arguments` at 5 nodes × 30 s.
- **`count` applies to the aggregated result**, unchanged — it is already
  applied after the `from`/`to` filter.

### 1.3 — what is deliberately NOT done

Not paging Kraken to fill an aggregated request. A `count: 720` 3m request
needs 2160 1m candles = 3 calls, and §2.3 shows `since` cannot page backwards
anyway, so the extra calls would buy nothing and triple the public rate-limit
cost this bug is about. One base call, aggregate what came back.

## 2. Blast Radius

1. **Other call sites.** `intervalMap` has exactly one consumer
   (`index.ts:4010`, inside `getCandles`) — grepped. `getCandles` itself is the
   `AbstractExchange` method; the parent repo's
   `src/exchange/exchanges/kraken/index.ts` is a 95-line subclass that
   overrides only the constructor and `checkLimits`, so it inherits this
   change and needs no edit. Behaviour is unchanged for the eight natively
   supported intervals: `bucketMs` is 0, no aggregation runs, and the request
   sent to Kraken is byte-identical.
2. **`core/` submodule.** Yes — this is `exchange-connector-sh`, shared with
   the self-hosted platform. The parent's submodule pointer must be bumped at
   ship time. Per the memory note *"exchange-connector's parent src/ is a
   coupled stale copy"*, `tsc --noEmit` is run in **both** core and parent.
3. **Documented contracts** (root CLAUDE.md Danger List). `BaseReturn<T>` is
   item 1 — its *shape* is untouched here; only the `data` payload of
   `getCandles` changes, and only for the three intervals that currently return
   no payload at all. Nothing in the GraphQL schema, the socket.io event names,
   the Redis market-data channels or `ARCHIVE_QUEUES` is touched. No new
   dependency.
4. **Other tests on this path.** The kraken directory's existing specs
   (`rate-limit`, `outage-backoff`, `partial-fill`, `fill-price`,
   `phantom-order-status`, `cancel-verdict`, `ambiguous-userref`, `cl-ord-id`,
   `nonce-logging`, `spot-txid-lookup`) must stay green; none of them touch
   `getCandles`, but they share the module and the constructor.

## 3b. Verification against the live venue

`candle-intervals.spec.ts` runs offline against a stubbed client, so it can only
prove the aggregation is self-consistent. Correctness was established separately
against Kraken itself: Kraken has no native 3m/2h/8h to compare with, but it
does serve 5m/15m/30m/240m, so real base candles were pulled from
`/0/public/OHLC` and aggregated with the shipped `aggregateCandles`, then
compared bar-for-bar against Kraken's own native bars for the same windows —
including the exact ×3, ×2 and ×4 ratios the fix uses.

```
TAOUSD/XBTUSD/ETHUSD, 2026-09-08:
   1m ->   5m   144/144 exact     5m ->  15m   240/240 exact
   1m ->  15m    48/48  exact    15m ->  30m   360/360 exact
  60m -> 240m   179/179 exact
  => 3,462 / 3,462 bars identical to Kraken's native OHLC (all three pairs)
```

The first run of this comparison was **43/47**, and is what surfaced spec §2.4:
every mismatch was a bucket opened by a zero-trade filler bar. The probe scripts
were deleted after use — they hit the public venue and are not something to run
in CI.

## 4. Gate 4 — plan vs spec

Walked §1–§4. Every spec section appears above. The Solution fixes the two
causes §3 names (a unit map used as a capability map; no horizon check before
the call) rather than the symptom — it does not, for instance, merely add
`EGeneral:Invalid arguments` to `retryErrors`, which would have made the log
line quieter while sending strictly more doomed requests. The §4 non-goal
(Kraken has no deep spot history) is left explicitly unfixed and is called out
in the spec rather than silently absorbed.
