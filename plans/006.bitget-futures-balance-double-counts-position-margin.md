# 006 — plan

Spec: `specs/006.bitget-futures-balance-double-counts-position-margin.md`.

## 1. Solution

Change the anchor field in `BitgetExchange.futures_getBalance()`
(`src/exchange/exchanges/bitget/index.ts`) from `available` to the coin's
wallet balance, and derive both halves from it:

```
walletBalance = accountEquity - unrealizedPL        (fallback: available + locked)
committed     = locked + crossedMargin + isolatedMargin   (clamped to [0, walletBalance])
free          = walletBalance - committed
locked        = committed
```

This is the spec's Assumption applied directly: `free + locked` is the wallet
balance **by construction**, so it cannot double-count in either margin mode,
and only the split between the two fields depends on the margin terms. It is
the same shape Bybit already uses (`walletBalance - locked` / `locked`).

Three guards, each with a test:

- every term parsed through one local `num()` that maps a missing/blank/NaN
  field to `0` — `crossedMargin` / `isolatedMargin` are undeclared extras on
  this response and today produce `NaN` for the whole `locked` when absent;
- when `accountEquity - unrealizedPL` is not a positive number (fields absent
  on some product type), fall back to `available + locked` rather than
  reporting a zero balance — a zero reads as "the account was emptied";
- `committed` clamped to the wallet balance so `free` cannot go negative,
  keeping `free + locked == walletBalance` exactly.

### Not chosen

- *Keep `available` as the anchor and subtract `crossedMargin` from it.* Fixes
  the reported (crossed) case but leaves the isolated case resting on an
  undocumented, mode-dependent property of `available` — whether it nets
  isolated margin out. Evidence exists only for crossed accounts (spec §2.1),
  so this is a coin-flip on the other half of the venue.
- *Anchor on `accountEquity` itself.* Would make the total include unrealized
  PnL, which no other connector here does (Bybit anchors on `walletBalance`,
  not `equity`) and which is not the figure the reporter compared against.
- *A new shared "balance" helper.* Nothing to share: each venue's arithmetic
  is venue-specific and lives inline in its own `futures_getBalance`. The
  reuse here is of the existing **convention**, not of code.

### Legacy tier (Part 4)

**Tier 0.** The touched region is a self-contained ~10-line pure mapping from
one response row to one `FreeAsset` entry inside an otherwise I/O-shaped
method. Extracting it into its own module would not remove a smell — the
`.spec.ts` already drives the real method through a stubbed client with no
network — and would put a second Bitget file in a `core/` diff for no gain.

## 2. Blast Radius

1. **Other call sites.** `futures_getBalance` is reached from
   `AbstractExchange.getBalance()` (futures branch) and the `/balance`
   endpoint. No other Bitget method reads `available`, `accountEquity` or the
   margin fields — `grep -n 'accountEquity\|available' bitget/index.ts`
   confirms the account-assets response is consumed only here and in
   `futures_getSingleBalance`-style leverage checks that read other fields.
   Bitget **spot** balance (`spot_getBalance`) is untouched.
2. **`core/` submodule.** Yes — this is `exchange-connector-sh`, shared with
   the self-hosted platform. The parent repo's
   `src/exchange/exchanges/bitget/index.ts` is a thin subclass that does not
   override `futures_getBalance`, so the parent needs no mirrored edit; only
   its submodule pointer moves.
3. **Owned contracts (repo `CLAUDE.md`).** `FreeAsset` / `BaseReturn<T>`
   shapes are **unchanged** — same fields, same types, same endpoint. Only the
   *values* of `free` and `locked` for Bitget futures change, and only for
   accounts with an open position or venue-frozen funds. Downstream
   consumers of the values:
   - main-app `updateUserBalance` (`core/src/utils/user.ts`) writes them to
     the `balances` collection on the Bitget 2-minute poll — the sole producer
     of these rows for Bitget, so no second writer disagrees with the new
     split;
   - `getBalances` (dashboard Portfolio Balances widget) renders
     `free` / `locked` / `free + locked` as NOT IN LIMIT / IN LIMIT / TOTAL;
   - the bot engine funds check reads `free`. It gets **smaller** for
     accounts with open positions — that is the point: the margin is not
     spendable. It stays above the venue's own spendable figure (spec §2.1:
     ours 0.24 W vs the venue's 0.11 W), so this does not make the engine
     stricter than the exchange.
4. **Other tests on this path.** `bitget/position-mode-retry.spec.ts` (order
   placement, untouched) and the rest of `npm test` must stay green.

## 3. Traceability

| spec § | enforced by (`src/exchange/exchanges/bitget/futures-balance.spec.ts`) |
|---|---|
| §1.1 invariant, crossed | "crossed margin: the total is the wallet balance, not wallet + margin" |
| §1.1 invariant, isolated | "isolated margin: same invariant, whichever mode the margin is in" |
| §1.1 partition stays valid | "free never goes negative when the margin exceeds the balance" |
| §1.2 / §2.1 the defect itself | same crossed test — red at `8999.79` (= wallet + margin) before the change |
| §2.3 / §3 flat account unchanged | "a flat account is unchanged: free = the whole balance, locked = 0" |
| §3 fallback when equity absent | "no balance is invented or lost when the equity fields are absent" |
| §3 undeclared margin fields | "margin fields the venue omits never turn a balance into NaN" |
