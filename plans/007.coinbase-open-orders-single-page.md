# 007 — Plan: page Coinbase's open-orders list

Spec: [`specs/007.coinbase-open-orders-single-page.md`](../specs/007.coinbase-open-orders-single-page.md)

## Solution

One method changes: `CoinbaseExchange.getAllOpenOrders`
(`src/exchange/exchanges/coinbase/index.ts`). It keeps its overloads, its
`BaseReturn` shape and its `handleCoinbaseErrors` tail exactly as they are. What
changes inside it:

1. The query object gains an explicit `limit` (§4.1).
2. The first `callWithTimeout` result is accumulated into a local array; while
   the venue reports `has_next` **and** hands back a new `cursor`, the next page
   is requested with the same query plus that cursor and appended (§4.2).
3. `convertOrder` maps the accumulated array; the count shape returns its length
   (§4.3).
4. Each extra page re-enters `checkLimits('private', timeProfile)` first (§4.4).

## Contract decisions the spec left open

- **§5.1 page size → 250.** Reuses the number `getBalance` already uses in this
  file rather than inventing one. It is the largest value this connector has
  proven against Coinbase, and it turns the reporting account's ~300 resting
  orders into two requests instead of thirteen.
- **§5.2 cursor typing → a single local type alias**, `OrderPageQuery`, that is
  `OrderListQueryParam & { cursor?: string }`. `getOrders` forwards its whole
  query object into the request `params`, so `cursor` reaches the wire; the
  SDK's published interface simply never declared it. A named alias at the one
  construction site is narrower than an `as any` at the call site and states
  *why* the cast exists.

## Reuse check (no new helper)

- There is no pagination helper in `core/` to reuse — `grep -rn "has_next" core/src`
  returns only `getBalance` in this same file and one spec fixture. `getBalance`
  paginates by **recursing through its own public method**, which works there
  because `getBalance(pagination?)` already takes a pagination argument.
  `getAllOpenOrders(symbol?, returnOrders?)` does not, and adding one would
  widen a public, overloaded signature that eight call sites and
  `AbstractExchange` declare — for a value no caller should ever pass. So the
  page walk is an internal loop in the same shape, not a new exported utility
  and not a signature change.
- Rate limiting reuses the existing `checkLimits('private', …)`; the profiler
  reuses `startProfilerTime` / `endProfilerTime`. Nothing new is introduced.

## Legacy tier (Part 4 / JIT runbook)

**Tier 0 → 1 boundary, deliberately staying at Tier 0.** The method mixes a
venue call with the decision of when to stop paging, so a Tier 1 extraction
("pull the page walk into its own named, tested module") is arguable. It is
rejected here: the walk is eight lines, is bound to one SDK's pagination shape,
and the sibling `getBalance` expresses the identical logic inline four hundred
lines below. Extracting one of the two and leaving the other makes the file less
consistent, not more, and widens a `core/` diff that ships to every consuming
service. The test (below) gets its determinism from stubbing the HTTP layer
instead, which needs no extraction.

## Test approach

The spec's mechanism lives **inside the vendored SDK**, so a test that stubs
`client.rest.order.getOrders` would stub away the very thing under test and
could pass with the bug present. Instead the spec builds a **real
`OrderAPI`** (`new OrderAPI(fakeAxios)` — `OrderAPI` is exported from the
package root) over a fake axios client, and hands it to the exchange as
`client.rest.order`. The SDK's `limit`-defaulting and its
`formatPaginationFromResponse` both run for real; only the network is fake. The
fake serves a 300-order book in `has_next`/`cursor` pages honouring whatever
`limit` it is asked for, and records every request's params.
