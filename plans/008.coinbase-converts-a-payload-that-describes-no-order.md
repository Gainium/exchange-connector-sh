# Plan 008 — refuse a Coinbase payload that describes no order

Spec: `specs/008.coinbase-converts-a-payload-that-describes-no-order.md`.

## 1. Build order

1. `src/exchange/exchanges/coinbase/orderPayload.ts` — new, pure (Tier 2 per
   the JIT runbook: the decision is a predicate over a payload, so it extracts
   cleanly with no infra left attached). Two functions:
   - `unstatedOrderFields(order?)` → the identity fields the payload does not
     state (spec §4.1/§4.3);
   - `unreadableOrderPayload(askedFor, unstated)` → the reason string.
2. `src/exchange/exchanges/coinbase/unreadable-order-payload.spec.ts` — the
   red test, driving the real `getOrder` / `cancelOrder` / `getAllOpenOrders`
   over a stubbed `client.rest.order`.
3. `src/exchange/exchanges/coinbase/index.ts` — `convertOrder` gains the
   precondition and a second `askedFor` argument; the two single-order call
   sites pass the id they asked about.

## 2. Contract decisions the spec left open

- **How the refusal is raised.** `throw new CoinbaseError(...)` from inside
  `convertOrder`, rather than changing three call sites to return early. All
  three already terminate in `.catch(this.handleCoinbaseErrors(...))`, so one
  throw becomes a `returnBad` at every one of them and the guard cannot be
  forgotten at a call site added later. This is what satisfies §4.5 with the
  minimum diff.
- **Why it is not retried (§4.4).** `handleCoinbaseErrors` retries on a code in
  `retryErrors` or a message matching its `reasons` list. The refusal carries
  no code and its wording matches no entry, so it falls through to the plain
  `returnBad`. Checked explicitly by the "one venue call, no retry ladder"
  assertion rather than left to inspection — the list is edited often.
- **`askedFor`.** The reason must name a subject. `order_id` comes from the
  payload, which in the general case may not state one either, so the
  single-order paths pass the id they asked the venue about and the payload's
  own id is only the fallback. `getAllOpenOrders` has no single subject and
  uses the fallback.
- **Which fields are identity fields.** `order_id`, `product_id`, `side`,
  `order_type`, `created_time`. Deliberately not `filled_size` /
  `average_filled_price` / `filled_value` / `total_fees` — a resting order
  states none of those and must keep converting (§4.2), which is the
  distinction main-app spec `028` draws as "fill evidence".
- **"Stated" is a non-empty string, not a recognised value** (§4.3).
  `order_type: 'STOP'` is a statement; `convertOrder` has always mapped it to
  `MARKET` and still does. Tightening that is a different change.

## 3. Blast Radius

1. **Other call sites of the changed function.** `convertOrder` is private with
   exactly three call sites (`cancelOrder` L423, `getAllOpenOrders` L569,
   `getOrder` L718) — all three are covered and asserted. `unstatedOrderFields`
   is new, so it has none.
2. **`core/` submodule.** Yes — this file is under `core/`
   (`exchange-connector-sh`), so the change is shared, public and deployed
   platform-wide. The parent repo's
   `src/exchange/exchanges/coinbase/index.ts` is a 145-line subclass of
   `CoreCoinbaseExchange` that overrides neither `convertOrder` nor any caller,
   so it inherits the fix; `tsc --noEmit` was run in BOTH the parent and `core`
   because the parent compiles `core`'s sources directly.
3. **Contracts this repo owns** (`CLAUDE.md` → *What this service OWNS*).
   `BaseReturn<T>` is untouched in SHAPE — no field added, removed or retyped.
   What changes is WHICH answer a caller gets for one class of input: a
   payload that previously produced `status: OK` with fabricated values now
   produces `status: NOTOK` with a reason. That is the fix, and it is the
   direction the contract already defines (`NOTOK` = we do not have an answer).
   Consumers affected, all of which already handle `NOTOK` on these endpoints:
   - **main-app order reconcile** — `getOrderForReconcile` retries, then records
     the order in `unresolved` and warns. The order keeps its local state and
     stays polled. This is the behaviour spec `028` §4.2 wants and never got,
     because the connector never said no.
   - **main-app `getActiveOrders`** (count shape of `getAllOpenOrders`) — an
     error makes the bot-start ceiling check refuse rather than under-count.
     Conservative direction.
   - **dashboard Open orders view / order import** — shows an error instead of
     a fabricated `MARKET BUY` row.
   - **`cancelOrder`** — the cancel itself has already succeeded at the venue
     before `convertOrder` runs; only the post-cancel re-read is refused, so
     nothing is left uncancelled.
   Not affected: paper-trading (mirrors the contract, does not call this code),
   market-archive (candles/trades only), exchange-balancer (routes by
   `exchangeLimits`, does not read order bodies).
4. **Other tests on this path.** `open-orders-pagination.spec.ts` (spec `007`)
   walks `getAllOpenOrders` end to end and its fixtures are complete orders;
   `unauthorized-retry.spec.ts` exercises `handleCoinbaseErrors`. Both must
   stay green — full suite run below.
