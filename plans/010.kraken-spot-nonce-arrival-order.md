# 010 plan — Kraken spot: sign and send in order per key

Spec: [`specs/010.kraken-spot-nonce-arrival-order.md`](../specs/010.kraken-spot-nonce-arrival-order.md)

## Build order

1. `src/kraken-custom/nonce.ts` — add `inKrakenKeyOrder(apiKey, send, maxHoldMs)`:
   a per-key promise chain. `send` runs once the previous request on the same
   key has settled, or once that request has held the key for `maxHoldMs`.
2. `src/kraken-custom/SpotClient.ts` — override `_call`: a private call on the
   `main` client with a key runs `super._call` inside `inKrakenKeyOrder`; public
   or keyless calls go straight through.
3. `src/exchange/exchanges/kraken/index.ts` `handleKrakenErrors` — the nonce
   class (`EAPI:Invalid nonce`, `invalid nonce`, `duplicate nonce`) gets
   `maxAttempts = 3` with the generic backoff ramp.
4. Release: version 1.20.25, CHANGELOG entry.
5. Deployment wrapper (private repo): its `checkLimits` override delegates to
   core's `checkLimits` and then publishes usage, instead of re-implementing
   the limiter.
6. Wrapper repo: bump the `core` pointer and its own version.

## Decisions the spec left open

- **Where the ordering lives: around `_call`, not in `checkLimits`.** The nonce
  is assigned inside `_call` (`buildRequest` → `signRequest`), so only a gate
  around the whole call covers assignment *and* dispatch. Rate-limit waits
  happen in `checkLimits`, before `_call`, so a saturated budget never holds a
  key's place in line.
- **Hold bound: 10 s.** A private spot call normally answers in well under a
  second; provider stalls have been observed at over a minute. Ten seconds keeps
  a stalled request from stalling the key for that long, and a late answer from
  it is covered by the retry.
- **Nonce retry depth: 3, generic ramp (1 s, 2 s).** Same depth as the
  rate-limit and outage classes. With in-process ordering, remaining rejections
  come from another process on the same key (§3.3); a couple of spaced attempts
  clear that without piling strikes on the key. Not 0: a real one-off
  rejection should still self-heal (§3.3).
- **Wrapper: delegate, don't re-implement.** Core's `checkLimits` already
  charges a deferred call when it is admitted (§1.5), costs heavy endpoints, and
  passes the account key. The wrapper only adds usage publishing.

## JIT extraction tier

**Tier 1** for the ordering gate: a named, single-purpose export colocated with
the existing per-key nonce source (`nextKrakenNonce`, same file, same shape),
testable without the SDK. Not Tier 2 — it is inherently async scheduling, not a
pure decision. Not Tier 3 — no new port; the SDK client is already the adapter.
The wrapper change removes a stale duplicate rather than extracting anything.

## Blast Radius

1. **Call sites.** `SpotClient` is constructed only by the Kraken exchange class
   (`src/exchange/exchanges/kraken/index.ts`), which the verify and
   additional-API helpers also use. Every private spot call now queues behind
   earlier calls *on the same key in the same process*. Calls on one key that
   used to overlap now run back to back — including batched order lookups for
   one account. Different keys and public calls are unaffected. The derivatives
   client is untouched.
2. **`core/` submodule.** Public and shared; the wrapper repo's pointer is
   bumped deliberately in step 6. Paper-trading mirrors the HTTP contract, not
   this client, so it is unaffected.
3. **Owned contracts.** `BaseReturn<T>` unchanged. Usage still goes out on the
   `exchangeLimits` channel (consumer: the balancer); values now reflect calls
   charged on admission, so they no longer under-count deferred calls.
4. **Tests that must stay green.** Full mocha suite, in particular
   `nonce-logging.spec.ts`, `rate-limit.spec.ts`, `outage-backoff.spec.ts`,
   `serializeParams.spec.ts`, `spot-txid-lookup.spec.ts`.
   `outage-backoff.spec.ts` used a nonce rejection as its sample "ordinary
   transient" for the 10-attempt ladder; §1.3 deliberately takes nonces off
   that ladder, so the sample becomes `EService:Timeout` (still ordinary). The
   test's intent — ordinary transients keep the full ladder — is unchanged.
5. **Known, not addressed.** Ordering across processes (§3.3). Whether
   per-account accounting activates depends on the `KRAKEN_PER_ACCOUNT_LIMITS`
   environment flag where the wrapper runs; delegating makes it reachable but
   does not switch it on.
