# 011 — plan

Spec: `specs/011.bitget-coinm-balance-mixes-usd-pnl-into-a-coin-balance.md`.

## Solution

One expression in `core/src/exchange/exchanges/bitget/index.ts`
`futures_getBalance`. The equity anchor keeps the `unrealizedPL` term only on
the linear product types, where the margin coin is the contracts' quote
currency:

```ts
const equityBased = this.coinm
  ? num(d.accountEquity)
  : num(d.accountEquity) - num(d.unrealizedPL)
```

Everything downstream of `equityBased` — the `available + locked` fallback,
the `committed` clamp, the `free`/`locked` partition — is spec 006's and is
untouched, so spec 006's behaviour on USDT-M/USDC-M is bit-identical.

This fixes the root cause the spec's Assumption names (a cross-currency term
being subtracted from a coin figure) rather than the symptom: it does not
clamp, sanity-check or bound the resulting number, it stops reading the
wrongly-denominated field for the product type on which it is wrongly
denominated.

### Why not convert the PnL instead

`accountEquity / usdtEquity` would give a coin↔USDT rate in the same payload,
so `unrealizedPL × accountEquity / usdtEquity` would recover the true wallet
balance. Rejected: spec 011 §2.5 proves only that `unrealizedPL` is **not** in
the margin coin — that it is specifically USD/USDT is inference from
magnitude, and a conversion would silently re-introduce a (smaller) unit error
if the real unit is anything else. It also adds a division by a field that can
be `0`. Dropping the term depends on nothing.

### Why not `this.productTypes` / a string test on `productType`

`this.coinm` is the connector's existing, already-used accessor for exactly
this distinction (`get coinm() { return this.futures === Futures.coinm }`) and
is what `productTypes` is itself derived from. A `productType.endsWith(...)`
test would be a second, parallel source of truth for the same fact.

## Reuse

No new helper. `this.coinm` already exists and is used by `productTypes` /
`getProductTypeBySymbol`; the local `num()` guard is spec 006's and is reused
as-is. No formatting/precision utility is involved — the value is a raw
number handed to `FreeAsset`.

## JIT extraction tier

**Tier 0.** The causal path is a single arithmetic expression already inside
the mapper spec 006 introduced, and it is covered by a unit spec that needs no
network, no auth and no DB — the smell this ladder exists to remove is not
present. Extracting the mapper into a pure module would be a rewrite of
deploy #218's code sprung on a P1 balance fix, i.e. exactly the drive-by the
runbook forbids.

## Blast Radius

1. **Other call sites.** `equityBased` is local to the `data.map()` in
   `futures_getBalance`. `getBalance()` (same file) dispatches to it for
   futures connections; nothing else reads it. `grep -n "equityBased"` →
   one file, one function.
2. **`core/` submodule — YES.** This is `exchange-connector-sh`, shared and
   deployed platform-wide (cloud + self-hosted). The parent repo's
   `src/exchange/exchanges/bitget/index.ts` is a 96-line subclass and does
   **not** carry `futures_getBalance`, so the parent needs only its submodule
   pointer bumped at ship time.
3. **Contracts this repo owns (`CLAUDE.md` "What this service OWNS / EMITS").**
   `BaseReturn<FreeAsset>` shape: unchanged — same fields, same types, same
   row count. `/balance` endpoint: unchanged. Redis `exchangeLimits` /
   `admin-config`: untouched. paper-trading mirrors the HTTP contract, not
   this mapper, and has its own balance implementation — no lockstep change.
   What changes is the *value* for `bitgetCoinm` connections only:
   `free + locked` stops being inflated by the open PnL. main-app's
   `balance.handler.ts` (`total = free + locked`) and the dashboard's
   Portfolio Balances widget consume that number, and `% of Total` /
   `% of Available` base-order sizing derives from it — which is the defect
   being fixed, not a new coupling.
4. **Other tests on this path.** `src/exchange/exchanges/bitget/futures-balance.spec.ts`
   is the only one; its five spec-006 cases must stay green unmodified. Full
   `npm test` baseline before the change: 581 passing.
