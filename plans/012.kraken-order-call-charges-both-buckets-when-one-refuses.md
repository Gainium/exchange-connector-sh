# Plan 012 — charge Kraken's two order budgets atomically

## Solution

Spec §3: two budgets gate **one** request, so they must be spent together.

`addOrderCall` currently asks each bucket in turn through its own mutex-guarded
method, and each charges itself the moment it admits. Restructure so the whole
two-bucket decision happens **synchronously inside one mutex acquisition**:

1. Factor the un-decorated bodies out as `restVerdict(accountKey, cost, commit)`
   and `engineVerdict(accountKey, pair, cost, commit)` — same arithmetic as
   today, plus a `commit` flag that decides whether the cost is actually added.
   Decay is applied either way (decay is just clock accounting and is
   idempotent).
2. `checkRestLimit` keeps its decorator and its `krakenRest:<account>` key, and
   delegates to `restVerdict(…, commit = true)`. `addRestCall` is untouched —
   a single-bucket call has no atomicity problem: refused means uncharged,
   admitted means sent.
3. `addOrderCall` takes over the **same** `krakenRest:<account>` mutex key (so it
   serialises against plain REST calls on the same account, which share that
   bucket) and runs:
   - probe both buckets with `commit = false`;
   - if either refuses, charge **neither** and return `Math.max()` of the waits,
     exactly as the caller expects today;
   - only when both admit, commit both and return 0.
   Because the body between probe and commit contains no `await`, the decision
   is atomic — nothing can take the last token in between.
4. Delete the now-unreachable `checkMatchingEngineLimit` wrapper (private, and
   `addOrderCall` was its only caller) along with its `krakenPair:<…>` mutex key.
   Its arithmetic moves verbatim into `engineVerdict`.

Nothing about the **budgets** changes: same tiers, same decay rates, same
thresholds, same costs, same wait arithmetic, same `getUsage()` shape.

### JIT legacy tier

**Tier 1** (runbook): the charge logic is pulled into two named, directly-tested
functions but stays coupled to this module's counter maps. Not Tier 2 — the
counters are module-level mutable state and making them pure would mean
threading state through every caller, which is a rewrite of the file, not the
radius of this bug.

## Blast Radius

1. **Other call sites.** `limit.ts`'s public surface is `addRestCall`,
   `addOrderCall`, `getUsage`, `noteRateLimited` (the default export). Only
   `kraken/index.ts` imports it (`import limitHelper from './limit'`), through
   `checkLimits` and `getUsage`. `checkMatchingEngineLimit` is private and had
   exactly one caller. Verified with a repo-wide grep for `./limit` and for each
   method name.
2. **`core/` submodule.** Yes — this file is inside `exchange-connector-sh`, so
   it is shared/public and the parent pointer must be bumped at ship time. It is
   **Kraken-only** code: no other venue, and no shared type, reads it.
3. **Owned/emitted contracts** (repo `CLAUDE.md`, root Danger List):
   - `BaseReturn<T>` — **untouched**.
   - HTTP endpoints — **untouched**.
   - Redis `exchangeLimits` (Danger List #7) — `getUsage()` is **not modified**;
     it returns the same `[{rest},{matching_engine}(,{krakenAccounts})]` array
     with the same `[0,1]` ratio semantics. The *values* will read lower, which
     is the point: they stop reporting load Kraken never saw. The balancer
     consumes them as a congestion ratio, so a truthful lower number routes
     better, not worse.
   - No GraphQL, socket, queue or Mongo surface is involved.
4. **Other tests on this path.** `kraken/rate-limit.spec.ts` (stubs
   `noteRateLimited`, drives `handleKrakenErrors`) and the rest of
   `src/**/*.spec.ts` must stay green. Full `npm test` in `core/`, plus
   `tsc --noEmit` in **both** `core/` and the parent — a change under `core/`
   has to compile against the parent's coupled `src/` copy too.
