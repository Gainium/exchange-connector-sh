# Plan 013 — Kraken spot's cancel reports a fabricated order

Spec: [`../specs/013.kraken-spot-cancel-reports-a-fabricated-order.md`](../specs/013.kraken-spot-cancel-reports-a-fabricated-order.md)

## Solution

One file: `src/exchange/exchanges/kraken/index.ts`.

Extract the spot cancel into a private `spotCancelByTxid(order, lastSeen, timeProfile)`
and route both entry points into it:

| entry point | who calls it | `lastSeen` |
|---|---|---|
| `cancelOrder({ symbol, newClientOrderId })` | the bot engine, via main-app `cancelOrderOnExchange` | the `getOrder` it already does to resolve the txid (spec §4.1) |
| `cancelOrderByOrderIdAndSymbol({ symbol, orderId })` | main-app terminal cancel (`graphql/handlers/orders.handler.ts`) | none — re-read after the cancel (spec §4.2) |

The report is then built from whichever order was established, with
`status: 'CANCELED'` (spec §3 — the cancel is the only thing observed). When
neither is available, report the cancel with `price` / `executedQty` / `type` /
`side` **omitted** (spec §4.3) rather than asserting `'0'`.

### Contract decisions the spec left open

1. **No signature change anywhere.** `lastSeen` is threaded through a *private*
   helper, not through the public `cancelOrderByOrderIdAndSymbol`. Widening that
   method — which is `abstract` in `abstractExchange.ts` and mirrored by
   `paper-trading` — would put a Danger-List contract in the diff for no gain.
   `cancelOrder` keeps delegating to `cancelOrderByOrderIdAndSymbol` for
   **futures**, so that branch is byte-for-byte untouched.
2. **Reuse, don't add.** The post-cancel re-read is the existing
   `querySpotOrderByTxid` (exact QueryOrders lookup, one REST token,
   authoritative for open *and* closed orders, already produces a `CommonOrder`
   via `convertSpotQueryOrder`). Its three-way `found` / `unknown` / `failed`
   answer is exactly the distinction §4.3 needs. No new helper, no new lookup.
3. **The §4.3 response is a deliberate partial `CommonOrder`.** Every field the
   type requires is present except the four we cannot establish; those are
   omitted so main-app's `hasOwnProperty` copy loop skips them. Expressed with
   one local cast at the construction site and a comment naming why, because the
   absence *is* the contract here.
4. **`status` is never derived from the re-read.** A re-read that says `closed`
   would map to `FILLED`, and `resolvers.ts` rejects the terminal cancel on
   anything but `CANCELED` ("Order was not canceled on exchange"). Promotion
   stays the engine's decision (`setFilledInsteadOfCanceled`, #717's opt-out).

### JIT legacy extraction tier

**Tier 1** — `spotCancelByTxid` is a named, tested unit, but it stays coupled to
`this.spotClient` / `this.checkLimits` / `this.handleKrakenErrors`. Not Tier 2:
the logic under test *is* the venue round trip and its ordering (read, cancel,
report), so there is no pure decision to lift out that would still exercise the
defect. Not Tier 0: the causal path runs straight through it.

## Blast radius

1. **Other call sites.** `cancelOrderByOrderIdAndSymbol` has two: the abstract
   declaration (`abstractExchange.ts:579`) and `exchange.service.ts:688`
   (`/order` DELETE by id). Neither signature changes. `cancelOrder`'s futures
   delegation is unchanged. Nothing else in the repo calls the spot branch.
2. **`core/` submodule** — yes, this file is in `exchange-connector-sh`, shared
   and deployed platform-wide. The change is confined to the Kraken **spot**
   class; no other exchange, and not `BaseReturn`/`CommonOrder`.
3. **Contracts this repo owns** (`CLAUDE.md` → OWNS/EMITS): `BaseReturn<T>`'s
   *shape* is untouched. Its Kraken-spot **contents** change, which is the fix.
   The consumer that reads them — main-app `cancelOrderOnExchange` — is
   venue-agnostic and already handles a truthful cancel answer from every other
   venue. Two of its branches become reachable for Kraken spot for the first
   time and must be left alone, not neutralised:
   - `+order.executedQty !== 0 && status === 'CANCELED'` → the promotion /
     `convertOrderExecutedQty` path (#717, #820);
   - `removeFromLocal && +request.data.executedQty === 0` → a
     partially-filled cancelled order now correctly stays in the local map.

   This is the whole risk of the change: Kraken spot stops being the one venue
   that reports nothing, and starts exercising engine paths every other venue
   already exercises daily. **Measured exposure** (prod, 30 days to
   2026-09-19): of 524,193 cancelled take profits on all *other* venues, 46
   carried fills — 0.009%. So the price/side/type correction applies to 100% of
   the affected rows while the newly reachable promotion branch is expected to
   fire on roughly one Kraken spot cancel in ten thousand.
4. **Rate limits.** Kraken private REST is 20 tokens at 0.5/s per account, and
   grid teardown cancels in bursts. The engine path — 100% of the 9,152
   production cancels in the last 30 days — spends **no extra call**; only the
   terminal cancel adds one.
5. **Other tests on this path.** `cancel-verdict.spec.ts` (futures cancel),
   `spot-txid-lookup.spec.ts` + `ambiguous-userref.spec.ts` (`getOrder`, which
   `cancelOrder` calls), `partial-fill.spec.ts`, `phantom-order-status.spec.ts`,
   `rate-limit.spec.ts`, `order-call-atomicity.spec.ts`. On the consumer side,
   in main-app: `settleCancelNoFillReport.harness.spec.ts` and
   `resizeCancelPromotion.spec.ts` pin #820 and #717 against the *old* Kraken
   answer and must stay green — they assert the engine still copes with a cancel
   answer that reports no fill, which remains a legitimate answer (§4.3).
