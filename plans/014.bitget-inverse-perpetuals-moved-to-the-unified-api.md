# 014 — Bitget inverse perpetuals moved to the unified API

## Build order

1. `uta.ts` — the boundary vocabulary: `COINM_PERP_NEEDS_UTA`,
   `utaCoinmSymbol`/`platformCoinmSymbol` (`BTCUSD` ⇄ `BTCUSD_CM`),
   `coinmContracts`/`coinmBase` (§3.4 rounding), `utaInverseQtyUnit`
   (the self-checking read-back, §3.4), and the `inverse` arm of
   `convertUtaOrder`/`convertUtaPosition`.
2. `index.ts` public surface — `futures_getAllExchangeInfo` merges the v3
   `COIN-FUTURES` instruments into the `bitgetCoinm` listing under their
   historic names; `futures_getAllPrices`, `getPrice` and `futures_getCandles`
   serve those pairs from v3 (`market/tickers`, `market/candles`), since v2
   returns nothing for them (§2.1).
3. `index.ts` private surface — `utaRequest` stops refusing COIN-M;
   `utaCategory`/`utaCategories` answer `COIN-FUTURES` for `Futures.coinm`;
   orders, positions and leverage go through the symbol and quantity
   boundary; a perpetual on a classic key is refused with
   `COINM_PERP_NEEDS_UTA`, and a delivery contract on a unified key keeps
   `UTA_COINM_UNSUPPORTED`, which now means only "the unified line does not
   carry this contract".
4. `uta.spec.ts` — §3.2 mapping, §3.4 conversion both ways including the
   contradictory-venue case, the two refusals, and a listing that carries
   both lines.

## Blast radius

1. Other call sites: `bitgetCoinm` only. `utaCategory()` is shared with spot
   and USDT/USDC-M, so its COIN-M arm must not change what those answer.
2. `core/` submodule: this IS the submodule; the parent bumps the pointer.
3. CLAUDE.md contracts: `BaseReturn<T>` shapes unchanged. `ExchangeInfo` for
   these pairs is new data, not a new shape. Pair names stay in the platform's
   existing `bitgetCoinm` vocabulary (§3.2), so stored bots, deals and Redis
   candle channels keep resolving.
4. Other tests: `uta.spec.ts` (spec 013) and spec 011's balance spec both
   touch COIN-M; neither changes behaviour here.

## Traceability

| Spec section | Test |
|---|---|
| §3.1 listing carries both lines | `lists inverse perpetuals from v3 beside the classic delivery contracts` |
| §3.2 name mapping | `a perpetual keeps its historic name and is sent as _CM` |
| §3.3 refusals | `a classic key is told the perpetual needs a unified account`, `a delivery contract stays off the unified line` |
| §3.4 outgoing conversion | `base quantity becomes whole 1-USD contracts` |
| §3.4 read-back | `reads quantity back in base, from whichever unit the venue's own figures agree with` |
