# Plan 018 — Scope the atomicity spec's virtual clock to its own suite

Implements spec `018.virtual-clock-leaks-out-of-the-spec-that-installs-it.md`.

---

## Solution

Spec §3 names the root cause as **when** the clock is installed and
removed. The change is exactly that, in one file:

`core/src/exchange/exchanges/kraken/order-call-atomicity.spec.ts`

1. At module scope, **declare** `VNOW` and a `previousDateNow` slot —
   do not patch `Date.now` there (removes spec §1.2's lines 31-33).
2. In a **top-level `before()`** of the outermost `describe`
   (`'spec 012 — Kraken order calls charge both buckets atomically'`),
   capture `Date.now`, anchor `VNOW` on real `Date.now() + SETTLE_MS`
   and install the virtual clock.
3. In the **matching `after()`**, drain the counters this file charged
   and hand `Date.now` back.
4. Delete the stray restore from the nested `before()` at line 269
   (spec §1.2), keeping the `KRAKEN_PER_ACCOUNT_LIMITS` toggle it also
   performs — that toggle is that case's own setup and is unrelated.
   The mode restore moves to the top-level `after()` with the clock, so
   the file hands back both things it borrowed in one place.

`SETTLE_MS` per spec §4.3: `batch-limit.spec.ts` leaves the shared
limiter's timestamps ~58.5 min ahead of real time, so the anchor needs
to clear an hour with headroom. **24 h.** Virtual time is free, the
clock only moves forward, and every account key this file uses is
`freshKey()` — so a larger margin is strictly safer, never tighter.
Chosen as an order-of-magnitude bound rather than a tuned value,
precisely so it does not need re-tuning when a sibling spec's own
advance grows.

Shape copied from the sibling that already does this correctly,
`kraken/batch-limit.spec.ts:92-111` — including its `after()` drain,
which asks `getUsage()` in **both** `KRAKEN_PER_ACCOUNT_LIMITS` modes
because each mode applies decay to a different set of entries.

### Deliberately NOT done

The original report's "or better" option — give `limit.ts` an injected
clock function so no global is patched at all — is the right
dependency-inversion move, and it is **out of scope here**: it edits
production code the brief ring-fences (spec §4.2). Recorded as a
follow-up, not attempted.

No new helper is introduced. The anchoring/restore/drain idiom already
exists in this directory (`batch-limit.spec.ts`); this change wires up
that existing shape rather than inventing a second one.

## Blast Radius

1. **Other call sites of what is changing.** The changed lines are
   module-scope statements and hook bodies inside one `.spec.ts`. No
   production code imports a spec file. `grep -rn "order-call-atomicity"
   --include=*.ts src` returns only the file itself and prose
   references in `batch-limit.spec.ts`'s header comment.
2. **Is the file under `core/`?** Yes — `core/` is the shared
   `exchange-connector-sh` submodule, deployed platform-wide. But the
   file is a `*.spec.ts`: `tsconfig.build.json` excludes specs from the
   build, so nothing in `dist/` changes and no consuming service can
   observe this. Verified by building and diffing `dist/` (gate 6).
3. **Contracts this repo owns.** None touched. `BaseReturn<T>`,
   `exchangeLimits` in Redis, and the connector's HTTP surface are all
   untouched — no production file is edited. Danger List items 1, 7 and
   11 are not in play.
4. **Other tests on this path.**
   - `kraken/order-call-atomicity.spec.ts` — its own 9 assertions must
     stay green (spec §4.1).
   - `kraken/batch-limit.spec.ts` — shares the `limit.ts` singleton and
     runs *before* this file; its restore stops being a no-op
     (spec §2.1).
   - `kraken/rate-limit.spec.ts` — shares the singleton and runs
     *after*; clock-insensitive (spec §4.4).
   - The other 22 previously-skewed files move from 2027 to today. Any
     of them that was passing *because* of the future clock will now
     fail — that is the fix working, and each such failure would be a
     real defect to file separately. (Measured: none. 782 → 782.)
