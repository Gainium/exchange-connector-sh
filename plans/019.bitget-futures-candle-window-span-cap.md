# 019 — plan

Spec: [`../specs/019.bitget-futures-candle-window-span-cap.md`](../specs/019.bitget-futures-candle-window-span-cap.md)

## Solution

All of it in `src/exchange/exchanges/bitget/index.ts`, `futures_getCandles`.

1. **`BITGET_FUTURES_MAX_SPAN_MS`** — a module constant, 90 days, carrying the
   §2.1 measurement and how to re-measure it, in the style of the existing
   `getSpotIntervalLookbackMs` doc block (same class of measured-not-documented
   venue limit).
2. **Page span = `min(200 × interval, BITGET_FUTURES_MAX_SPAN_MS)`.** At `4h`
   and below `200 × interval` is the smaller of the two, so those intervals keep
   exactly the pages they had (spec §1.5).
3. **Drive the loop off the window, not off a bar count.** `candlesSize` and
   `i = ceil(candlesSize / 200)` go: once pages are span-limited they carry
   fewer bars than that arithmetic assumes (a `1w` page drops from 200 bars to
   ~12), so `i` would be far too small and the series would truncate silently.
   The loop now runs to `maxPages` and breaks when `from` reaches the original
   `to`, captured as `windowEnd` before the first page is clamped. `maxPages`
   stays 400, so the worst-case request count is unchanged.
4. **The overhang stays.** The next page's `to` is `from + pageSpan`,
   deliberately not clamped to `windowEnd` — spec §1.6. Clamping it was tried
   and measurably dropped the in-progress candle from every multi-page read.
5. **An empty or inverted range returns `[]` without a request**, which is what
   the old `ceil(candlesSize / 200) = 0` did implicitly.
6. **Delete the false half of the comment** at :1667-1672 (spec §2.2), keeping
   the true half — there is no date floor here, #225 stays fixed.

Not done, deliberately: the cursor advances `from = to + interval` where the
venue's window is `[start, end)`, so one bar is dropped at every page boundary
(730d at 4h returns 4360 bars where 4380 exist). That predates #225 and is a
separate defect, filed on its own; changing it here would alter `8h` and below,
which this fix is required to leave untouched.

## JIT legacy tier

Tier 0. The causal path is ten lines of arithmetic inside an existing method;
there is no decision/IO seam worth cutting here and the runbook's radius rule
does not reach the rest of the method.

## Blast radius

1. **Other call sites.** `futures_getCandles` is called by `getCandles`
   (:3079), by itself for the `8h` → `4h` merge (#913), and by the controller
   through `getCandles`. `coinm_getCandles` (v3 inverse) is a different method
   with its own 1000-row pager and is untouched — whether v3 has a span cap of
   its own is not established here.
2. **`core/` submodule.** Yes — this is `exchange-connector-sh`, shared and
   deployed platform-wide. The parent repo only subclasses the file
   (`src/exchange/exchanges/bitget/index.ts` is a 2.7 KB subclass), so nothing
   there changes; `tsc --noEmit` run in both.
3. **Owned/emitted contracts.** None. `BaseReturn<T>`, the HTTP surface, the
   Redis channels and the paper-trading mirror are all unchanged — this only
   changes which windows get asked of Bitget and, at `1d`/`1w`, whether the
   answer is `OK` instead of `NOTOK`.
4. **Other tests on this path.** `bitget/candle-intervals.spec.ts` (#913, spec
   017) exercises the same loop, including its multi-page test; it stays green.
   Full suite: 787 passing.
