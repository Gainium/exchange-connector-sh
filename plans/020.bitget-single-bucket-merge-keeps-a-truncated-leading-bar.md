## 3. Blast Radius

**1. Other call sites of the function.** Two, both the merge-up path added for
#913, both in the same file family:
- `bitget/index.ts:1673` — `futures_getCandles`, `8h` read at `4h`.
- `bitget/index.ts:3201` — `spot_getCandles`, `8h` read at `4h`, spot `2h` read
  at `1h`, and the Reality-token widths from `realityBaseInterval`.

Native intervals never reach it. Kraken's identically-named helper is a
separate function in a separate file and is not touched.

**2. `core/` submodule.** Yes — this file is in `exchange-connector-sh`, which
is shared, public and deployed platform-wide. The parent pointer is bumped at
ship time. Nothing outside this repo imports `aggregateCandles`.

**3. Owned/emitted contracts** (repo `CLAUDE.md` → "What this service OWNS /
EMITS"). `BaseReturn<T>` is unchanged in shape; `/candles` still answers
`status: 'OK'` with a `CandleResponse[]`. What changes is that for one window
shape the array can now be **empty** where it previously held one wrong bar.
Checked every consumer of that possibility:

- `market-archive src/backfill/client.ts:330-347` — `status === 'OK'` with
  `data: []` is not an error (`!res.data.data` is false for `[]`); it maps to
  `[]` and returns. It then calls `addEmptyRange` **only** when
  `isFullyHistorical(key, to)`, i.e. `to + 2 × interval <= now`. The defect's
  own signature is that it is always the NEWEST bucket, which is inside that
  two-bar margin, so the live-edge case is explicitly never negative-cached —
  the comment on `isFullyHistorical` says so. It stays a gap and is retried.
- `market-archive src/backfill/backfiller.ts:181` — `if (!candles.length)
  break`: nothing is written, the gap is not marked covered, and `gapsInRange`
  re-emits it on the next read. This is the "treat it as a gap to retry"
  requirement, and it holds.
- `main-app src/exchange/additionalAPIs.ts:53-72` — the archive branch already
  has an explicit `rows === [] → fall through to the exchange` arm; the direct
  branch returns `coreMethods.getCandles` verbatim, and an empty candle array
  is that function's ordinary "no candles in this window" answer for every
  venue.

One thing this does NOT fix, and that is the other half of the production
route in spec §2.3: the backfiller's last round of every gap asks for a 2 ms
window (`cursor === gap.to`, window `[gap.to - 1, gap.to + 1]`), and Bitget
answers a window by the bars that CLOSED inside it, so it hands back the
PREVIOUS bar. That is wasted on every venue and actively harmful here. It
belongs to `market-archive`'s window arithmetic, in another repo, and it is
not what makes the answer wrong — with this change that window yields nothing,
the loop breaks, and the correct row the earlier round wrote stands. Recorded
as a finding on the issue rather than fixed here.

`addEmptyRange` cannot turn that into a permanent hole: `hasEmptyRange` only
refuses a request CONTAINED in a remembered range, so remembering a 2 ms
window never blocks a real one; and the case actually observed is the newest
bucket, which `isFullyHistorical` keeps out of the cache by design.

**4. Other tests on this path.** `bitget/uta.spec.ts` "aggregates 4h candles
into UTC days and Monday weeks" already exercises the multi-bucket
leading-partial drop and must stay green; `kraken/candle-intervals.spec.ts`
exercises the other copy and is untouched. Whole `core/` suite is the gate.
