# Plan 022 — dedup the Bitget futures candle series

Spec: [`specs/022.bitget-futures-candles-repeat-the-overhanging-page.md`](../specs/022.bitget-futures-candles-repeat-the-overhanging-page.md)

## Solution

The spec's Assumption (§3) names the cause as the missing dedup on the
accumulated page buffer, and §2.3 establishes that the repetition cannot be
prevented at request time — the overhang is mandatory (§1.4) and the venue
decides how far back it slides. So the fix is at the only place it can be:
`futures_getCandles`'s return.

Give it the tail `spot_getCandles` has already had since 2026-04-07 (spec
§4.1): a `seen` Set keyed on `c.time` keeping the first occurrence, then
`.sort((a, b) => a.time - b.time)`. Nothing else — not the cursor, not the
page span, not the loop bound.

Keep-first is deliberate and is not interchangeable with keep-last here:
every page but the final one has a window entirely in the past, so it only
ever serves closed bars, and the final page's copies of those same bars are
identical. Keep-first also matches spot, so the two readers cannot drift.

Also correct the false clause in the cursor comment at :1758–1760 (spec §3).
It currently tells the next reader that the series needs no dedup, which is
how this defect survived three consecutive fixes to the same loop.

## Reuse check

No new helper. The dedup+sort idiom already exists twice in this repo and is
being applied, not written:

- `spot_getCandles`, same file, the block at :3467–3473.
- `aggregateCandles` in `bitget/uta.ts`, which deduplicates its own input.

Rejected alternative: extracting a shared `dedupeCandles()` and rewiring spot
onto it. That edits a second, working, live code path in a `core/` submodule
for tidiness — wider blast radius than the defect. Spec 022 does not ask for
it. If a third caller ever needs it, that is the moment.

## JIT extraction tier

**Tier 0.** `futures_getCandles` mixes decision with I/O throughout, but the
causal path is a single expression at the function's return — there is no
business rule tangled with a client call to pull out, and the radius rule in
the runbook does not make a 500-line venue pager "already being touched"
because one return statement changed.

## Blast radius

1. **Other call sites.** `futures_getCandles` is reached from
   `getCandles` (:3122, the `/candles` controller path), from itself for the
   merged `8h` width (:1661), and from `handleBitgetErrors`' retry (:1741,
   :1773). All three want a series satisfying §1.1; none can want repeats.
   `coinm_getCandles` (:1816) is a different endpoint with its own pager —
   **not touched**: it clamps each page's `end` to `to` (:1830) so it never
   overhangs, and no duplicate was measured on it.
2. **`core/` submodule.** Yes — this is `exchange-connector-sh`, shared and
   deployed platform-wide. The parent repo's pointer needs bumping at ship.
3. **Owned contracts** (`exchange-connector/CLAUDE.md`). `BaseReturn<T>` is
   untouched: same status, same `CandleResponse[]` element shape, same
   `timeProfile`. Only the array's contents change, and only by removing
   repeated entries and ordering the rest. `/candles` keeps its signature.
   No Redis channel, no rate-limit accounting, no request count changes —
   the venue sees the identical calls.
4. **Downstream readers.** main-app charts/indicators, the client-side and
   server-side backtester, and market-archive's backfill all consume this
   array. Every one of them is better off: a repeated timestamp is a bar
   counted twice by an indicator and a row written twice by the archive.
   The risk is the reverse of the usual one — a consumer that had silently
   compensated for the duplicates would now double-correct. Nothing in the
   platform does: `aggregateCandles` deduplicates defensively and is
   idempotent under an already-unique input, which test §6.4 pins.
5. **Tests that must stay green.** `candle-page-boundary.spec.ts` (#918
   cursor + #914 span cap), `candle-span-cap.spec.ts`,
   `candle-intervals.spec.ts` (#913), `uta.spec.ts`, and the rest of the
   suite. Note `candle-page-boundary.spec.ts` already dedups before it
   measures holes (`[...new Set(raw)]`), so it is insensitive to this change
   by construction — except its own "cursor makes consecutive pages disjoint"
   assertion, which tests the cursor and must not be weakened into a test of
   the new dedup. It uses a start-anchored stub, so it still measures only
   the cursor. Left alone.
