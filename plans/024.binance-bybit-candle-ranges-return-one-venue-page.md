# 024 — plan

Spec: [`../specs/024.binance-bybit-candle-ranges-return-one-venue-page.md`](../specs/024.binance-bybit-candle-ranges-return-one-venue-page.md)

## Solution

The spec's Assumption is "there is no pager". Three call sites need the same
walk, so it goes in ONE place and the adapters supply only the venue call:

**`src/exchange/helpers/candlePager.ts`** (new) — `pageCandleRange({from, to,
step, pageSize, fetchPage})`. Pure control flow; the only I/O is the injected
`fetchPage(start, end, limit)`. Walks `[from, to]` forward:

- chunk span = `(pageSize - 1) * step`, because both venues' windows are
  INCLUSIVE at both ends (spec §2.2) — that is exactly `pageSize` bars, so the
  limit never binds and neither end of a chunk is dropped;
- `cursor = chunkEnd - step` (the #918 rule) — one bar of deliberate overlap so
  nothing falls between pages whichever way a venue reads its bounds;
- stop as soon as a chunk reached `to`; `totalChunks + 5` as the runaway cap;
- dedup by `time` + sort ascending on the way out (the #920 rule), which the
  bybit side needs anyway since its rows arrive newest-first.

Deliberately NOT reused for Bitget: its pager switches endpoint per chunk
(recent vs historic, different page sizes and a lookback retry) and is not the
same walk. Refactoring it is not this fix.

### Call sites

Each gets the same guard and nothing else changes:

```
from && to && !countData && step > 0 && to > from   →  page
otherwise                                           →  today's single call
```

- **`bybit/index.ts` `getCandles`** — page size 1000 (measured; `limit: countData
  || 200` today leaves 80% of the page unused). `futures_getCandles` already
  delegates here, so linear and inverse come along.
- **`binance/index.ts` `spot_getCandles`** — page size 1000.
- **`binance/index.ts` `futures_getCandles`** — page size 1500, inserted after
  the existing rate-limit weight is computed and BEFORE the COIN-M 200-day
  branch, so a range read with no count no longer reaches that branch.

Both adapters coerce `from`/`to` into locals (`+from`) for the guard and the
walk. This is a precondition, not a second fix (spec §3): the pager is the
first code in either adapter to ADD to them and they are strings in production.
The locals are used ONLY by the new branch — the existing single-call paths
keep passing `from`/`to` through exactly as they do today.

Errors keep each adapter's own shape: the walk runs in a `try`, and the `catch`
hands the error to `handleBybitErrors` / `handleBinanceErrors` with the same
argument tail the single-call path uses, so a retry replays the same read.

## Blast Radius

1. **Other call sites of the changed methods.** `bybit.futures_getCandles`
   (:415) → `getCandles`; `binance.getCandles` (:2188) → `spot_`/`futures_`.
   `exchange.service.ts:126` is the only other entry, from `/candles`. No other
   caller in `core/` or the parent `src/` reaches these.
2. **`core/` submodule** — yes. This is `exchange-connector-sh`, shared and
   deployed platform-wide. The new file exports one new function and changes no
   existing type, so nothing downstream recompiles differently. The parent repo
   keeps a coupled stale copy of `src/exchange/exchanges/*` — it does NOT
   contain these methods (the parent's binance/bybit `index.ts` are 4–10 KB
   subclasses), so `tsc` must still pass in BOTH.
3. **Owned contracts** (`CLAUDE.md` → OWNS/EMITS). `BaseReturn<T>` is unchanged
   — same `status`/`data`/`reason`, same `CandleResponse` rows. The `/candles`
   HTTP shape is unchanged. No Redis channel, no queue payload.
   Consumer-visible behaviour changes in exactly two ways, both intended:
   a range read with no count now returns the WHOLE window instead of one page,
   and on bybit that window is ascending where one page used to be descending.
   Every count-passing caller (spec §3.1) is byte-identical.
4. **Venue-call volume.** Up per request, by construction. Bybit's page goes
   200 → 1000, so a bybit range costs a FIFTH of the calls a Bitget-style pager
   at 200 would. market-archive's backfiller is the consumer that starts paging
   (spec §3.1) and the wall-clock ceiling it now runs under is recorded there.
5. **Other tests on this path.** `bitget/candle-*.spec.ts` (5 files) must stay
   green — the Bitget pager is untouched, and they are the regression net that
   says so.
