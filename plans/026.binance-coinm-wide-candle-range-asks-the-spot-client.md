# Plan 026 — route the COIN-M >200-day window through the existing pager

Spec: `specs/026.binance-coinm-wide-candle-range-asks-the-spot-client.md`
(bug #925).

## 1. Build order

One file, one method: `core/src/exchange/exchanges/binance/index.ts`,
`futures_getCandles`.

1. Widen the condition on the `pageCandleRange` block #923 added (spec 024) so
   it also takes the COIN-M >200-day window:

   ```ts
   const coinmWideRange =
     this.coinm && !!fromMs && !!toMs && toMs - fromMs > 200 * DAY
   if (fromMs && toMs && step > 0 && toMs > fromMs && (!countData || coinmWideRange))
   ```

   For `binanceUsdm` and spot, `this.coinm` is false, so the condition reduces
   to today's `!countData` — spec 026 §1.7.

2. Inside that block's `fetchPage`, restore the in-queue timeout bail-out the
   COIN-M loop had, gated on `coinmWideRange` so the paths #923 shipped are
   untouched. It `throw`s instead of returning `returnBad`, which the enclosing
   `catch` turns into the same `notok` + `Response timeout` as before.

3. Delete the `if (this.coinm) { if (> 200 days) { … } }` loop entirely.

No new helper: `pageCandleRange` (`core/src/exchange/helpers/candlePager.ts`)
already does the chunking, the `pageSize - 1` span, the `cursor = end - step`
advance, the dedup and the sort, and `FUTURES_CANDLE_PAGE_SIZE = 1500` already
holds this endpoint's measured cap. Adding a second walker for COIN-M is the
defect the helper was extracted to prevent.

## 2. Contract decisions the spec left open

- **Trigger stays at 200 days, not "wider than one page".** The natural
  condition for a bar-count pager would be "more bars than `pageSize`", but
  that would pull COIN-M windows between ~1500 bars and 200 days into the
  pager, and §1.7 forbids changing them. Keeping the literal 200-day test makes
  the diff's reach exactly the branch that is broken.
- **`step > 0` is required.** `pageCandleRange` divides by it. An interval
  absent from `timeIntervalMap` falls through to the single call below, which
  is what every other width-unaware read already does.
- **The count is not a cap on the total.** This branch has always returned the
  whole window and used `countData` only as a per-chunk row limit (spec 026
  §3.1); the pager keeps the window and replaces the row limit with the
  endpoint's own page size.

## 3. Blast Radius

1. **Other call sites.** `grep` for the 200-day literal and for
   `this.client.getKlines` in this file: the loop being deleted is the only
   one. `pageCandleRange` has two callers today (binance `futures_getCandles`,
   bybit `getCandles`); this adds no third — it widens an existing one.
2. **`core/` submodule.** Yes — `exchange-connector-sh`, shared with the
   self-hosted build. The parent pointer is bumped at ship time. The parent's
   own stale `src/` copy of this adapter is not touched (it has its own tree;
   see the repo's note on the coupled copy) — verified by building both.
3. **Owned contracts.** None change shape. `BaseReturn<CandleResponse[]>` is
   the same; the only difference is that a wide COIN-M window that reads
   nothing now returns `notok` with the venue's reason instead of `OK` with
   `[]`. Consumers already branch on `status` — main-app's backtest loader
   `throw`s on `notok`, market-archive's backfiller logs and returns `[]`
   (`market-archive/src/backfill/client.ts:321`), neither of which can be
   reached by a worse path than today's silent empty series. market-archive
   passes no count and so does not enter this branch at all.
4. **Other tests on this path.** `candle-range-paging.spec.ts` (#923) — its
   `binance usdm` / `binance spot` cases, including
   "leaves a count-passing read at exactly one page", must stay green; none of
   its venues is COIN-M.
