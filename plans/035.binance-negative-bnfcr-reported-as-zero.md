# 035 — plan: keep a negative BNFCR in the Binance futures balance read

Spec: [035](../specs/035.binance-negative-bnfcr-reported-as-zero.md).

## Solution

Root cause per spec §3: `futures_getBalance` maps `free = maxWithdrawAmount`
and zeroes `locked` for a non-positive wallet balance, so a negative BNFCR
reads `0/0`. The per-asset mapping moves into a pure function
`futuresAssetBalance` (`binance/futuresBalance.ts`, JIT Tier 2: it is plain
arithmetic on one row, no client involved) which returns the negative wallet
balance as `free`, `locked 0`, for BNFCR only. `futures_getBalance` maps
through it; nothing else in the method changes.

Why BNFCR only (spec §4): the change this pairs with (main-app-sh spec 158)
prices only BNFCR, and other negative rows are unverified.

## Build order

1. `exchange-connector-sh` (this repo): function + spec, release 1.27.12.
2. `exchange-connector` parent: bump the `core/` pointer, release 2.21.7.
3. main-app needs nothing new: it stores the REST `free` verbatim
   (`updateUserBalance`), and its snapshot values BNFCR at 1 USD since
   main-app-sh spec 158.

## Blast Radius

1. Call sites: `futures_getBalance` is the only mapper of
   `FuturesAccountAsset`; `getMarginAvailableUsd` reads the same endpoint but
   only `availableBalance`, unchanged.
2. Under `core/` — shared by every connector deployment; behaviour changes
   only for a BNFCR row with a negative wallet balance.
3. Contract: `BaseReturn<FreeAsset>` shape unchanged; one value can now be
   negative. main-app's user stream already writes that same negative `free`
   for BNFCR (`ACCOUNT_UPDATE` → `crossWalletBalance`), so every reader of the
   stored row already sees it between refreshes. Bot funds checks read BNFCR
   as their USDT/USDC row and widen it by the pooled margin with `Math.max`,
   so 0 and a negative value give the same answer whenever a pool is
   reported; with no pool both are insufficient.
4. Tests: `binance/pooledMargin.spec.ts` (same endpoint) and the full suite.
