# 039 — plan: keep the caller's client id on a late Kraken spot read-back

Spec: [039](../specs/039.kraken-spot-late-readback-answers-with-txid-as-client-id.md).

## Solution

Root cause per spec §3: `openOrder`'s last-resort `getOrder` is routed by txid,
and the txid path labels the order with the id it was asked for. After that
call, when it succeeded, a txid was used and the caller sent a client id, set
`data.clientOrderId` back to the caller's id. Routing is unchanged: the read
still goes by txid (§1.3), so the exact QueryOrders lookup and the
no-userref-scan rule for a txid both stand.

Threading a separate client id into `getOrder`'s txid path was the
alternative; it changes the public `getOrder` signature for one caller, so
the override at the only call site is the smaller change.

JIT tier 0: one assignment after an existing call.

## Build order

1. `exchange-connector-sh` (this repo): fix + spec, release.
2. `exchange-connector` parent: bump the `core/` pointer, release.

## Blast Radius

1. Call sites: only the spot `openOrder` last-resort branch. `getOrder`
   itself is untouched, so status polling / reconcile by txid answer as before.
2. Under `core/` — shared by every connector deployment. Behaviour changes
   only for a Kraken spot placement whose three read-backs all miss.
3. Contract: `BaseReturn<CommonOrder>` shape unchanged; `clientOrderId` now
   echoes the request in that case, as it already does on every other path.
   Consumers that pin the answer to the sent id see no change; any that read
   the answer's id now get the id they sent.
4. Tests: new `kraken/spot-late-readback-client-id.spec.ts`, the other Kraken
   specs, and the full suite.
