# 050 — plan: Bybit list reads follow nextPageCursor

Spec: `specs/050.bybit-list-reads-stop-at-first-page.md`.

## Solution

One protected helper on `BybitExchange`, `readAllPages(read, maxPages = 100)`,
calls `read(cursor)` sequentially until `nextPageCursor` is empty. It returns
`{ ok, list, retMsg, retCode }`: `ok: false` with an empty list on the first
non-OK page, on a repeated cursor, or once `maxPages` is reached. A rejected
request propagates to the caller's `.catch`. The return type is one flat shape
because core compiles without `strictNullChecks`, where a boolean-discriminated
union does not narrow.

Wired into the four reads that share the defect:

| Method | Branch | Page size |
|---|---|---|
| `getAllOpenOrders` | linear settle-coin loop | `limit: 50` |
| `getAllOpenOrders` | single request (spot / inverse / symbol) | `limit: 50` |
| `futures_getPositions` | linear settle-coin loop | `limit: 200` (unchanged) |
| `futures_getPositions` | single request | `limit: 200` (unchanged) |

`cursor` is only added to the params when set, because bybit-api serialises an
`undefined` key.

The `getAllOpenOrders` linear loop now takes the same error path as the
positions loop (spec 009): non-OK or rejection → `handleBybitErrors` with
`symbol, returnOrders, timeProfile` (whole-read retry for a retryable error,
otherwise NOTOK). Its count overload sums every page instead of answering 0.
The single-request positions branch now hands `symbol` to `handleBybitErrors`,
so its retry does not take the TimeProfile as the symbol.

JIT tier: 1. The paging loop is pulled into its own named, tested method; it
stays on the class because it is driven by the venue client.

## Contract decisions

- `BaseReturn<CommonOrder[]>`, `BaseReturn<number>` and
  `BaseReturn<PositionInfo[]>` are unchanged: same fields, same row shape.
- `maxPages = 100` (5,000 orders at 50 per page). Exceeding it is a NOTOK
  rather than a truncated OK.

## Blast Radius

1. Call sites: `getAllOpenOrders` is reached via `futures_getAllOpenOrders` and
   the controller's open-orders endpoint (main-app GraphQL `getAllOpenOrders`,
   bot engine per-symbol reads). `futures_getPositions` via `/positions`
   (position reconciler, dashboards). Only the number of rows changes, plus
   one request per extra page.
2. `core/` submodule (`exchange-connector-sh`): public repo. Changelog and
   commit text describe the mechanism only.
3. Owned contract: `BaseReturn<T>` shape unchanged. Rate limits: one
   `checkLimits` per method call as before. Extra pages are sequential and
   only exist for accounts with more than 50 open orders per request.
4. Other tests on this path: `linear-positions-settle-coin-errors.spec.ts`
   (spec 009) and the full core mocha suite.
5. Other Bybit reads checked: orderId / orderLinkId / single-symbol reads
   (`getOrder`, `cancelOrder`, the client-id lookup, single-symbol
   `getPositionInfo`) return at most a couple of rows. `getAllExchangeInfo`
   already follows the cursor. `/v5/account/fee-rate` has no cursor. None of
   them change.
