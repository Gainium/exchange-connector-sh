# 001 — Wire real mocha to the scattered hand-rolled unit specs

## §1. Behaviour today

17 `*.spec.ts` files live next to the modules they cover, each a
regression test pinning a specific production incident. No test runner
exists (§1.1) — every file is a standalone script with its own
hand-rolled `expect`/`check` helper, `console.log`s PASS/FAIL, and calls
`process.exit(1)` on failure, run individually via `npx ts-node --files`
per its own header comment (§1.2). 10 of the 17 involve `await` calls
made either inline or before assertions inside an unawaited top-level
async IIFE (§1.3) — none run in CI, or even together.

## §2. Desired behaviour

`npm test` runs all 17 spec files through a single real test runner
(mocha, matching the `describe`/`it` convention used elsewhere in this
sweep) and exits non-zero if any assertion fails (§2.1). CI runs `npm
test` on every PR (§2.2). Each hand-rolled assertion becomes its own
`it()` (§2.3). Files stay where they are, next to the modules they cover
(§2.4).

## §3. Open questions / assumptions

- §3.1 New devDependencies: `mocha`, `@types/mocha` (this repo already
  had `ts-node`). No `chai` — every file's own comparator (`===` or
  `JSON.stringify` equality) is preserved exactly via a thin wrapper
  around `it()`, not replaced with a different assertion library, to
  avoid the JSON.stringify-vs-deep-equal drift risk documented in the
  sibling `main-app-sh` conversion earlier in this sweep. Public repo
  (`Gainium/exchange-connector-sh`); per this task's brief, pre-authorized.
- §3.2 **Async-safe conversion, not just a header/footer edit.** For the
  7 files whose original `expect()`/`check()` calls were purely
  synchronous, the helper was redefined in place to call `it(label, () =>
  {...})`, and every individual assertion call site was left completely
  untouched — cheapest and safest. For the 10 async files, that pattern
  is unsafe: mocha needs every `it()` registered *synchronously* during
  the file's collection pass, but the original files called
  `expect()`/`check()` from inside an unawaited top-level async function
  (`async function main() {...}; main()`), so `it()` calls after the
  first `await` would fire in a later microtask — mocha might finish
  collecting before they run, silently dropping tests with no error.
  Those 10 files were restructured with a `before(async () => {...})`
  hook that performs the exact same computation as the original function
  body, storing results in outer-scope variables, followed by ordinary
  synchronous `it()`s reading those variables through a lazy getter
  (`expect(label, () => value, want)`) — the standard, robust mocha
  pattern for "compute once, assert many times." One file
  (`venue-fee-capture.spec.ts`) was restructured slightly differently:
  each `it()` is itself `async` and awaits its own computation, since its
  assertions don't share expensive setup.
- §3.3 `hyperliquid/index.ts` fails TypeScript's full type-check on
  `@nktkas/hyperliquid/signing` (no `moduleResolution` override in this
  repo's `tsconfig.json`, so the classic resolver can't see the
  package's `exports`-mapped subpath types) — a pre-existing condition,
  invisible before because nothing ever ran a type-checking TS loader
  across the whole `src/**/*.spec.ts` tree at once. `npm test` runs with
  `TS_NODE_TRANSPILE_ONLY=1` to sidestep it, matching
  `websocket-connector-sh`'s existing `node:test` script in this same
  sweep. Fixing the underlying resolution gap (if one is even wanted,
  given the package resolves fine at runtime) is separate, out of scope.
- §3.4 `hyperliquid/bad-address.spec.ts` makes real network calls to
  `api.hyperliquid.xyz` (documented in its own header) — unchanged by
  this PR, but worth flagging: CI needs internet egress for this one
  suite, and it is the one file in the run that could flake on a
  Hyperliquid outage.
