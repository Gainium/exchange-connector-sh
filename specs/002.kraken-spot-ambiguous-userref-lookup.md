# 002 — Kraken spot `getOrder` resolves a colliding userref to an arbitrary order

Bug spec (existing behaviour is wrong). Issue #657, split out of #535.

## §1 Definition

`KrakenExchange.getOrder({symbol, newClientOrderId})` is asked about ONE order.

### §1.1 Expected

When `newClientOrderId` is a Gainium client order id (not a Kraken txid), the
spot path must either resolve **the order that was asked about** or fail. It
must never return a *different* order's `orderId`, because `cancelOrder()`
feeds that `orderId` straight to `cancelOrder({txid})` and the bot engine
copies it onto the order row it holds.

### §1.2 Actual

Kraken spot has no client-order-id lookup. The connector encodes the client id
as `userref = parseInt(clientOrderId.substring(0, 8), 16)`. Every Gainium
client id shares a non-hex prefix, so `parseInt` stops at the first `-` and

- every `D-*` id (base / safety / reduce / take-profit) collapses to userref **13**
- every `CMB-*` id collapses to userref **12**

The open-orders scan (`src/exchange/exchanges/kraken/index.ts:2503`) and the
closed-orders scan (`:2562`) both `return` on the **first** entry whose
`userref` matches. "Matches" therefore means "is some Gainium order on this
account", not "is this order". The answer is whichever order Kraken happened to
list first — an arbitrary pick, silently presented as an exact resolution.

## §2 Evidence

### §2.1 The collision is arithmetic, not probabilistic

```
D-RO-o54rqRLIW9rTGgeSaVaepKlstZBZpY -> userref 13
D-RO-abcdefghijklmnop               -> userref 13
D-SO-1234                           -> userref 13
D-BO-xyz                            -> userref 13
CMB-RO-aaa                          -> userref 12
```

### §2.2 It materialised in production

Read-only aggregate over prod `orders` (kraken, `orderId` matching a spot txid),
2026-09-05:

```
sharedTxids: 163   rows: 326   crossBot: 117   newest: 2026-08-27T20:00:55Z
```

163 distinct Kraken txids are each claimed by ≥2 order rows; 117 of those are
claimed by **more than one bot**. e.g. txid `OMV6YL-VVGDX-CRUVXR` is carried by
both `D-BO-2hZJUI42yQT8IiRDrXtOACvRR9hlVF` and
`D-RO-Bm9fAToDOqM6UpOb855cs8KzUsiu9Q`.

### §2.3 The producer main-app fixed; the connector's is still open

main-app `cancelOrderOnExchange` was switched to address Kraken spot by txid
(main-app-sh `2b765a0`, issue #535) and the corruption stops dead at that
deploy — nothing newer than 2026-08-27. That closes the *dominant* caller, not
the defect: `getOrder` still answers a colliding userref with an arbitrary
order, and main-app still reaches it with a raw client id from at least

- `core/src/bot/main.ts:7230` — the `Order not found after execution` retry
  after `openOrder`, which passes `requestData.newClientOrderId` untranslated;
- `core/src/bot/main.ts:1029` `venueOrderId()` — falls back to
  `return clientOrderId` whenever the order is not in the local order map;
- any self-hosted main-app older than `2b765a0`.

## §3 Assumption (hypothesis)

The root cause is the `return`-on-first-match in the two userref scans. A
userref match is not evidence of identity, and the code treats it as if it
were. Removing the ambiguity is impossible here — Kraken's open/closed order
payloads carry no client order id — so the only correct answers are "exactly
one match, here it is" or "ambiguous, I refuse".

## §4 Required behaviour

- **§4.1** Exactly one userref match in the open list → resolve it, unchanged.
- **§4.2** Two or more userref matches in the open list → fail, naming the
  client id, the userref and the number of colliding orders.
- **§4.3** Exactly one userref match in the closed list → resolve it, unchanged.
- **§4.4** Two or more userref matches in the closed list → fail, same wording.
- **§4.5** Zero matches → unchanged (`Order not found in open orders` →
  closed-orders fallback → `Order not found in history`).
- **§4.6** An ambiguity failure must NOT be readable as a venue "no such order".
  Its reason must match none of main-app's `unknownOrderMessages`
  (`core/src/bot/main.ts:200`) and must not satisfy
  `isDefinitiveOrderNotFound` (`:403`) — otherwise `cancelOrderOnExchange`
  routes it to `_handleUnknownOrder` and a live order gets retired as a
  phantom, which is the failure mode #535's sibling bug already caused.
- **§4.7** The txid path (`isKrakenSpotTxid` → `querySpotOrderByTxid`) is
  untouched. It is exact and is what every current caller uses.

## §5 Open questions / non-goals

- **§5.1** Narrowing candidates by `descr.pair` would shrink the ambiguous set,
  but Kraken pair naming (`XXBTZUSD`) needs `normalizeSymbol` per candidate and
  a mismatch would silently re-introduce a wrong answer. Not done.
- **§5.2** The 326 already-corrupted rows are a data cleanup. Out of scope; the
  code fix does not retire them.
- **§5.3** Trade-off accepted: a Kraken spot account with ≥2 open Gainium orders
  that is still asked by client id now gets a hard failure where it used to get
  a silently-wrong answer. That is the point — see §1.1.
