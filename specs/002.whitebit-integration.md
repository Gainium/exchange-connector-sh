# 002 — WhiteBit exchange integration (spot + USDⓈ-M perps)

## §1. Context

New exchange onboarding, scoped per the internal `new-exchange-integration`
runbook to this repo + `websocket-connector-sh` only for this pass —
`exchange-connector`, `app-sh`, dashboards, backtester, etc. are deliberately
**not** touched here; they pick this adapter up in a later PR once it exists.
Feasibility (Step 0 of the runbook) already ran: WhiteBit is **Go** — spot +
USDⓈ-M linear perps only (no Coin-M), standard HMAC-SHA512 key/secret auth,
confirmed historical-candle endpoint, and (after a second research pass,
§2.2) confirmed leverage/margin/hedge/position endpoints for the perp side
too. Broker/affiliate code
is an explicit **no-op for this PR** (§2.8) — WhiteBit's Broker ID requires
account-manager onboarding outside engineering's control; the plumbing point
is left in place but not wired to a real code.

## §2. Desired behaviour

### §2.1 Enum & family (§2.1)

Two live variants, matching the Kraken precedent of "declare only the
variants you actually wire" (Kraken's `types.ts` has a `krakenCoinm` member
that was never registered in `exchangeChooser.ts` — this spec avoids
repeating that half-declared state):

```ts
whitebit = 'whitebit'          // spot
whitebitUsdm = 'whitebitUsdm'  // USDⓈ-M linear perps
```

No `whitebitCoinm` — WhiteBit has no inverse-contract product.

### §2.2 `Exchange` interface coverage (§2.2)

**Architecture correction, confirmed after deeper research: WhiteBit has no
separate futures account.** Perp futures and leveraged-margin-on-spot-pairs
are the *same product* — a unified "collateral account" — differentiated
purely by market symbol: `BTC_USDT` (plain, no suffix) routes as
leveraged-margin on a spot pair, `BTC_PERP` routes as a perpetual future.
Both trade through the same `/api/v4/collateral-account/*` endpoint family.
This means `whitebitUsdm` in this integration = "collateral-account trading
restricted to `_PERP`-suffixed markets," not a structurally separate futures
API the way Binance/Kraken/Bybit have one. WhiteBit's plain "leveraged
margin on spot pairs" product (non-`_PERP` collateral-account trading) has
no matching slot in Gainium's spot/usdm/coinm family convention and is
**out of scope** — this adapter never sends a non-`_PERP` symbol through the
collateral-account endpoints.

**Go verdict solidified for `whitebitUsdm`**: leverage, margin-mode context,
hedge-mode, and positions are all real, confirmed endpoints — the earlier
"might need to cut usdm to a follow-up" contingency (spec §1) is
withdrawn. The two remaining gaps (§3.1 leverage scope, §3.2 margin-type
endpoint) are implementation-detail unknowns, not existence unknowns.

### §2.3 Candle response shape (§2.3)

`GET /api/v1/public/kline` returns each candle as
`[time, open, close, high, low, volume_stock, volume_money]` — **open/close
before high/low**, unlike the `[time, open, high, low, close, volume]` order
most other adapters in this repo assume. The parser must map by explicit
index, not by copying another exchange's column order.

### §2.4 Symbol mapping (§2.4)

WhiteBit's public Market Info endpoint returns spot and futures markets in
one list, disambiguated by a `_PERP` suffix on the market name — confirmed:
spot `BTC_USDT`, perp `BTC_PERP` (base + `_PERP`, no quote asset segment;
all perps are USDT-margined so the quote is implicit, not spelled out in
the symbol). Design mirrors
`KrakenSymbolMapper`: one cached singleton per variant (`getSpotInstance()`
/ `getUsdmInstance()`, no coinm instance), built from a single Market Info
fetch filtered by the confirmed suffix pattern, exposing `toOurSymbol` /
`toWhitebitSymbol`. No `wsnameToNormalized`-style asset renaming is expected
(WhiteBit market names read as already using standard asset tickers), but
that assumption gets verified against real API responses in gate 5, not
assumed permanently correct here.

### §2.5 Custom client & signing (§2.5)

No suitable npm WhiteBit client was found (unlike Kraken's
`@siebly/kraken-api`). Hand-roll a client under `src/whitebit-custom/`
(mirroring the `src/kraken-custom/` sibling-directory convention),
implementing the confirmed auth scheme directly:

- Body: `{ request: '<path>', nonce: <ms epoch, strictly increasing>,
  nonceWindow?: boolean, ...params }`
- Headers: `Content-Type: application/json`, `X-TXC-APIKEY`,
  `X-TXC-PAYLOAD` (base64 of the JSON body), `X-TXC-SIGNATURE` (hex
  `HMAC_SHA512(payload, secret)`)
- No existing shared HMAC-signing utility exists in this repo (confirmed —
  every exchange's SDK signs its own way); this is a new, WhiteBit-only
  signer, not a refactor of shared code.

### §2.6 Rate limits (§2.6)

Confirmed, all **per IP address** (not per API key): public `/api/v1/*` at
1000 req/10s; private trade-account endpoints at 12,000 req/10s; private
main-account endpoints at 1,000 req/10s. The rate-limits page also states
"scope-specific limits override the default where listed" — meaning some
individual endpoints (order placement is the likely candidate, given every
other exchange in this repo has a tighter matching-engine budget than its
general REST budget) may carry a stricter override not covered by the three
numbers above; confirm per-endpoint overrides for `openOrder`/`cancelOrder`
specifically during `limit.ts` implementation, don't assume the blanket
12,000/10s applies to order placement the way it applies to reads.

### §2.7 Registration (§2.7)

Same four files as every prior integration, `whitebit`/`whitebitUsdm`
branches added to each:

- `src/exchange/types.ts` — `ExchangeEnum` members (§2.1). No `wsCode` field
  unless §3.6 finds WhiteBit's WS market naming diverges from REST (nothing
  found so far to suggest it does).
- `src/exchange/helpers/exchangeChooser.ts` — factory branches,
  `Futures.null` / `Futures.usdm`.
- `src/exchange/helpers/verify.ts` — `verifyWhitebit()`, calls `getBalance`
  the same way `verifyKraken` does, no WhiteBit-specific extra permission
  check known yet (Kraken's has one for its WS-interface API permission;
  confirm whether WhiteBit's API-key scopes need an equivalent check during
  gate 5).
- `src/exchange/helpers/additionalApis.ts` — `getPrices()` / `getCandles()`
  cases, unauthenticated client construction (`key`/`secret` empty strings,
  matching every other exchange's pattern here).

### §2.8 Broker code — explicit no-op (§2.8)

The adapter still accepts `authHeaders.code` (interface-level — every
adapter receives it) but does not attach it to any request in this PR. No
`verify`/order-placement branch references a WhiteBit broker/affiliate
mechanism. This is a deliberate scope cut per instruction, not an oversight
— revisit once/if a WhiteBit Broker ID exists.

### §2.9 `.env.sample` / `package.json` (§2.9)

No global API host env expected (WhiteBit's dual `.com`/`.eu` host toggle is
currently disabled on WhiteBit's own docs site — `.com` only, no
`supportsHostSelection` design needed for v1, per Step 0 research). No new
runtime dependency if §2.5's client is hand-rolled with Node's built-in
`crypto`; if a WhiteBit npm client turns out to exist after a closer look in
gate 5, that supersedes §2.5's hand-rolled design and this section's
package.json note.

  - **§3.2 (new)** Where/how is cross-vs-isolated margin type actually set

    `collateral-*-order` endpoints at order-placement time?
- ~~§3.4 futures market-name suffix~~ — confirmed, `_PERP` (§2.4), no
  quote-asset segment in the symbol.
- ~~§3.5 private rate limits~~ — confirmed, §2.6 (12,000/10s trade-account,
  1,000/10s main-account, both per-IP; per-endpoint overrides possible,
  still need checking for order placement specifically).
- §3.6 Whether any WhiteBit WS channel uses a market-name form different
  from the REST market name — **downgraded, likely no**: `websocket-
  connector-sh` spec 003's research found WS channels (`trades_subscribe`,
  `candles_subscribe`) address markets by the same plain string
  (`BTC_USDT`, `ETH_BTC`) as REST. No `wsCode` field planned.
- §3.7 Whether WhiteBit API keys carry scoped permissions (like Kraken's
  "WebSocket interface" permission) `verifyWhitebit()` should check beyond
  a bare `getBalance` call — the docs' "Endpoint access restrictions" key
  setting (Authentication guide) suggests keys **can** be scope-limited by
  the user, but nothing found yet on how to detect a too-narrow key from
  a failed/successful call shape. Low priority — `getBalance` succeeding is
  already a meaningful verify signal, same floor Kraken's `verifyKraken`
  starts from before its extra WS-permission check.
- §3.8 (new) `getAccountFills`, `getBalance` (usdm variant), and the
  `collateral-account-balance`/`-summary` endpoints were confirmed to
  *exist* via the docs index but not read in full — low-risk (same
  request/auth envelope as everything already confirmed), but their exact
  field names need a final read during gate 5, step 4.
