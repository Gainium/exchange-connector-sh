# 003 — Kraken spot orders are not addressable by client order id

Bug spec (existing behaviour is wrong). Issue #657, follow-on to spec 002.

Spec 002 stopped the connector from *guessing* when a client-order-id lookup
was ambiguous. It did not make the lookup work. This one does: Kraken spot has
a native client order id (`cl_ord_id`) and the connector never used it.

## §1 Definition

`KrakenExchange` must be able to address a spot order it placed by the Gainium
client order id it placed it with — at submit, at `getOrder`, and at
`cancelOrder`.

### §1.1 Expected

`submitOrder` attaches an identifier Kraken can resolve back to *that one
order*, and `getOrder`/`cancelOrder` resolve exactly that order from a Gainium
client order id, or fail. Never a different order.

### §1.2 Actual

The connector encodes the client id as
`userref = parseInt(clientOrderId.substring(0, 8), 16)`
(`src/exchange/exchanges/kraken/index.ts:1892`, `:2534`, `:2603`). `parseInt`
stops at the first non-hex character, and every Gainium client order id starts
with a shared non-hex prefix, so the encoding is not injective — it is barely a
function of the id at all:

| client order id | derived `userref` |
|---|---|
| `D-BO-2hZJUI42yQT8IiRDrXtOACvRR9hlVF` | `13` |
| `D-RO-o54rqRLIW9rTGgeSaVaepKlstZBZpY` | `13` |
| `D-SO-…`, `D-TP-…` (every DCA order) | `13` |
| `CMB-RO-…` (every combo order) | `12` |
| `GRID-RO-roa6DwlXK15XEWuphyR6c4aejKj` | **`NaN`** |

Consequences, in the code as it stands today:

- **`D-*` / `CMB-*`** — all of a bot's orders share one userref. Pre-002 the
  scans returned the first match, i.e. an arbitrary order; post-002 they refuse
  as ambiguous. Either way the order asked about is never resolved.
- **`GRID-*`** — `parseInt` yields `NaN`, which `JSON.stringify` sends to
  Kraken as `userref: null`, so the order carries no client identifier at all.
  The scan then compares `'NaN'` against `null` and matches nothing, for a
  *single* open order as much as for ten. Grid orders on Kraken spot have never
  been resolvable by client id.

### §1.3 The venue was never the constraint

Kraken spot AddOrder / OpenOrders / ClosedOrders / CancelOrder all take a
native `cl_ord_id`, and OpenOrders/ClosedOrders return it on every row. It is
present in the pinned SDK, `@siebly/kraken-api@1.0.6` — no dependency bump:

```
types/request/spot.types.d.ts   SpotSubmitOrderParams.cl_ord_id?: string
                                SpotGetOpenOrdersParams.cl_ord_id?: string
                                SpotGetClosedOrdersParams.cl_ord_id?: string
types/response/spot.types.d.ts  SpotOpenOrder.cl_ord_id: string | null   (:154)
SpotClient.d.ts                 cancelOrder({ txid?, cl_ord_id? })       (:257)
```

`userref` was never the only option; it was a workaround for a capability the
connector had not adopted.

## §2 Evidence

### §2.1 The encoding, arithmetically

```
parseInt('D-RO-o54'.substring(0,8), 16)  === 13    // stops at '-'
parseInt('CMB-RO-r'.substring(0,8), 16)  === 12    // stops at 'M'
parseInt('GRID-RO-'.substring(0,8), 16)  === NaN   // 'G' is not hex
```

### §2.2 Live production population (read-only aggregate, 2026-09-05)

Kraken spot orders (`exchange: 'kraken'`, `orderId` matching a spot txid):
**7,495 orders across 105 bots** all time.

Currently live (`status` `NEW`/`PARTIALLY_FILLED`), by client-id family:

| prefix | live orders | bots | users | derived userref |
|---|---|---|---|---|
| `D-*` | 132 | 37 | 11 | 13 |
| `CMB-*` | 78 | 11 | 5 | 12 |
| `GRID-*` | 132 | 9 | 5 | NaN → sent as `null` |

**49 of 57 bots with live Kraken spot orders (18 users, 334 orders) have two or
more resting at once**, which is the whole population for whom every
client-order-id lookup is ambiguous.

### §2.3 The damage it already did

163 distinct Kraken spot txids in prod are each claimed by ≥2 order rows (326
rows, 117 of them across more than one bot) — the pre-002 arbitrary resolution
writing one order's txid onto another's row. That count has not grown since
main-app switched Kraken spot cancels to txid, which closed the dominant caller
without fixing the lookup.

### §2.4 The lookup is still reachable by client id

- main-app `core/src/bot/main.ts:7230` — the `Order not found after execution`
  retry re-asks `getOrder` with the raw `requestData.newClientOrderId`.
- main-app `core/src/bot/main.ts:1029` `venueOrderId()` — returns
  `clientOrderId` whenever the order is not in the local order map.
- any self-hosted main-app older than the txid switch.

## §3 Assumption (hypothesis)

The root cause is that the connector derives a lossy `userref` instead of
sending Kraken's native `cl_ord_id`. Fix the *identifier*, and both the
collision (002) and the grid-orders-never-resolve case disappear together;
patch anything downstream of it and they do not.

Kraken constrains `cl_ord_id` to three forms — long UUID (8-4-4-4-12 hex),
short UUID (32 hex, no dashes), or free ASCII text of at most 18 characters —
and a Gainium client order id (~35 mixed-case alphanumerics) is none of them.
So the identifier has to be *encoded*, and the encoding is the load-bearing
design decision: it must be deterministic (recomputable at every call site with
nothing stored) and injective (no two client ids share one `cl_ord_id`).

## §4 Required behaviour

- **§4.1 Encoding.** `clOrdId(id) = sha256(id).hex.slice(0, 32)` — Kraken's
  short-UUID form. Deterministic: submit, `getOrder` and `cancelOrder` derive
  the same value from the same client id with no stored mapping. 128 bits, so
  distinct client ids do not collide. Truncating the client id to 18 characters
  is explicitly rejected: `D-RO-` plus 13 characters is not unique across a
  bot's orders and would rebuild §1.2 in a new shape.
- **§4.2 Mutual exclusion.** `cl_ord_id` and `userref` are mutually exclusive on
  Kraken's AddOrder. No request the connector sends may carry both; `submitOrder`
  drops `userref` in the same change that adds `cl_ord_id`.
- **§4.3 Submit.** `submitOrder` sends `cl_ord_id: clOrdId(newClientOrderId)`,
  and no `userref`.
- **§4.4 Open-orders resolution.** `getOrder` resolves a client order id against
  the `cl_ord_id` carried on each open-order row. An exact match resolves that
  order regardless of how many other orders are open.
- **§4.5 Closed-orders resolution.** The closed-orders fallback asks
  `getClosedOrders({ cl_ord_id })` — server-side filtering matters here because
  ClosedOrders is paginated — and confirms the returned rows carry that
  `cl_ord_id`.
- **§4.6 Legacy orders.** Orders placed before this change carry a `userref` and
  no `cl_ord_id`, and stay resting on live accounts until they drain. When the
  `cl_ord_id` lookup finds nothing, the existing userref scan runs as a fallback,
  unchanged, including its ambiguity refusal (002 §4.2/§4.4) and that refusal's
  exact wording (002 §4.6). A row that carries *some other* `cl_ord_id` is not a
  legacy candidate and is excluded from that scan.
- **§4.7 Cancel.** `cancelOrder` continues to resolve the order through
  `getOrder` and cancel by the venue txid. See §5.3 — this is deliberate, not an
  omission.
- **§4.8 Txid path untouched.** `isKrakenSpotTxid` → `querySpotOrderByTxid`
  (QueryOrders) is exact and is what every current main-app caller uses. It has
  no `cl_ord_id` parameter and needs none.

## §5 Open questions / non-goals

- **§5.1 Not verified against a live Kraken account.** The connector has no
  Kraken credentials on this host and production is out of bounds. The encoding
  is verified to satisfy Kraken's documented short-UUID grammar (32 hex, no
  dashes) and the pinned SDK's types; it is not verified by a real AddOrder.
  This is the one residual risk in the change.
- **§5.2 One extra venue call on a genuine miss.** A client-id lookup that finds
  nothing now costs two ClosedOrders calls (the `cl_ord_id` filter, then the
  legacy `userref` filter) instead of one, until legacy orders drain. Open
  orders are unaffected — that call was already unfiltered, so both matches read
  the same payload.
- **§5.3 `cancelOrder` is not switched to a direct `cancelOrder({cl_ord_id})`.**
  It would save a round trip, but the spot cancel's `CommonOrder` carries the
  venue txid in `orderId`, and main-app's `cancelOrderOnExchange` copies every
  field of that response onto the order row it holds
  (`core/src/bot/main.ts:7974`) — `orderId` included. That write is the exact
  mechanism behind §2.3's 163 shared txids. Resolving through `getOrder` (now
  exact) and cancelling by the real txid keeps `orderId` truthful; a direct
  `cl_ord_id` cancel returns no txid and would have to invent one.
- **§5.4 `getAllOpenOrders` reports `clientOrderId: order.userref?.toString()`**
  (`:2973`). New orders have no `userref`, so that display field becomes `''`
  where it used to read `'13'`. Both are meaningless — it is a userref, not a
  client order id — and it feeds only the dashboard's open-orders panel
  (`main-app core/src/graphql/handlers/orders.handler.ts:33`), never order
  matching. Left alone; emitting the 32-hex `cl_ord_id` there would be no more
  useful and no more matchable.
- **§5.5** The 326 already-corrupted order rows remain a data cleanup, out of
  scope, unretired by this code change (002 §5.2).
