# 004 — Binance order ids lose precision before they are stored

## 1. Definition

### 1.1 Expected

A Binance exchange order id is an integer chosen by the venue. For USDM futures it
is now routinely above `Number.MAX_SAFE_INTEGER` (2^53 − 1 = 9,007,199,254,740,991)
— e.g. `8389766269723522123`, 19 digits. The connector must hand the caller the
**exact** id the venue issued, digit for digit, as a string.

### 1.2 Actual

The connector returns the id rounded to the nearest IEEE-754 double. The venue's
`8389766269723522123` is reported as `8389766269723522000`. Because the rounding is
many-to-one, two genuinely distinct venue orders can be reported under one id.

### 1.3 Expected — order lookup by id

When the caller asks the connector to cancel an order by its exchange order id, the
id the connector sends to Binance must be the id the caller passed.

### 1.4 Actual — order lookup by id

`cancelOrderByOrderIdAndSymbol` and `futures_cancelOrderByOrderIdAndSymbol` convert
the caller's id string back to a JS number with the unary `+` operator before
sending it. For any id above 2^53 that rounds it to a different integer, so the
request addresses an order the caller did not name.

## 2. Evidence

### 2.1 Production

Measured read-only on prod `orders` (non-paper, `created >= 2026-08-01`) and reported
on issue #672:

- 60 duplicate `(orderId, symbol, exchange, userId)` groups, **all `binanceUsdm`**,
  149 rows, **63 of them filled** (`executedQty > 0`). 35 groups have every row filled;
  `orderId 633327759322459900` on `RSRUSDT` carries 4 filled rows.
- All 673 `binanceUsdm` order ids since Aug 1 with 17+ digits satisfy
  `String(Number(id)) === id` — i.e. every one of them is the shortest decimal form of
  a double. A venue-issued id has no reason to be; a value that passed through a JS
  double always is.
- 5 distinct users affected, last occurrence `2026-08-28T14:30:14Z`.
- Prod log `Gainium <-> Binance user stream connector`, `2026-09-03T14:48:12.382Z`,
  carries an `ORDER_TRADE_UPDATE` for `8389766269723522000` — a value ending in three
  zeros, which is the signature above.

### 2.2 Reproduced locally against the real vendor client

`node /tmp/rc1.js` (see plan §5) serves a real Binance USDM `GET /fapi/v1/order` body
containing `"orderId":8389766269723522123` and drives the **actual** `binance@3.5.10`
`USDMClient` the connector uses:

```
RAW VENUE BODY orderId field -> 8389766269723522123
VENDOR CLIENT RETURNED orderId -> 8389766269723522000 (typeof number)
```

So the id is already a rounded `number` by the time
`core/src/exchange/exchanges/binance/index.ts:3296` calls `.toString()` on it. The
`.toString()` is not the defect and stringifying earlier cannot help — the digits are
gone before any connector code runs.

## 3. Assumption (hypothesis, not fact)

The rounding happens in **axios's default `transformResponse`**, which is a bare
`JSON.parse` of the HTTP body. `JSON.parse` has no representation for an integer
outside the double range, so it silently returns the nearest double. The vendor
`binance` client passes no custom `transformResponse`, so every REST response the
connector receives has already lost the digits.

The connector's own `BaseReturn<T>` mapping is **not** implicated: both
`convertOrder` (`:3225`) and `futures_convertOrder` (`:3296`) already stringify, and
`CommonOrder.orderId` is already typed `string | number`.

## 4. Required behaviour

- **§4.1** Parsing a Binance REST body whose `orderId` exceeds 2^53 yields the exact
  digits, as a string.
- **§4.2** An `orderId` at or below 2^53 is unchanged — it stays a JSON number, so the
  ~690k existing sub-2^53 ids and every consumer of them behave exactly as today.
- **§4.3** No other field is retyped. In particular a number that merely *looks* large
  (timestamps, quantities, prices) is untouched.
- **§4.4** Digits that appear **inside a JSON string value** are never rewritten — a
  `clientOrderId` or an error `msg` that happens to contain `"orderId":123…` must not
  be corrupted.
- **§4.5** A body that is not JSON (an HTML error page, an empty body) is returned
  unchanged rather than throwing, matching axios's own default behaviour.
- **§4.6** Binance error bodies (`{"code":-2011,"msg":"Unknown order sent."}`) still
  parse to an object, because the vendor's error handler reads `response.data.code`
  and `response.data.msg`.
- **§4.7** `cancelOrderByOrderIdAndSymbol` and `futures_cancelOrderByOrderIdAndSymbol`
  send the caller's order id unchanged — no `Number` round trip.

## 5. Out of scope for this change

- **The websocket-connector half.** `ORDER_TRADE_UPDATE` arrives over a separate
  service (`websocket-connector-sh`) whose vendor WS client also `JSON.parse`s the
  frame, and main-app's `core/src/bot/main.ts:5101` (`order.orderId = msg.orderId`)
  overwrites the stored id on every fill event. Until that is fixed too, a filled
  order's id is re-rounded after this fix stores it correctly. This change is still
  strictly an improvement and is the **prerequisite**: §4.7 must land before the
  websocket side starts storing exact ids, or the `+` in the cancel paths would
  convert a newly-correct id into a wrong one.
- **Backfilling the 673 existing rows.** Their low digits are unrecoverable locally;
  they would have to be re-fetched from Binance.
