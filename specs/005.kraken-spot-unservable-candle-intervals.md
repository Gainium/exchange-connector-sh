# 005 — Kraken spot candles: 3m/2h/8h are rejected by the venue, and
# unreachable windows still cost a public API request

Bug #709 ("Failed Backtesting, Kraken"). Reporter: Kraken TAO/USD backtests
return partial or no history; older periods (February–March 2026) complete with
zero deals and zero results.

## 1. Definition

### 1.1 — expected

`KrakenExchange.getCandles(symbol, interval, from, to, count)` on the **spot**
path returns candles at the requested `interval` for every value of
`ExchangeIntervals`, for as much of `[from, to]` as Kraken can actually serve.

### 1.2 — actual

For `interval` ∈ {`3m`, `2h`, `8h`} it returns **zero** candles and a
`KrakenError`, for every symbol and every window, because the request Kraken is
sent is malformed.

### 1.3 — expected

When the requested window lies entirely outside the history Kraken's OHLC
endpoint can reach, the connector does not spend a public (per-egress-IP) API
request discovering that.

### 1.4 — actual

Every such request is sent to the venue and comes back useless. The caller
re-requests on its own 30s cadence, across all five egress connector nodes, so
the doomed requests keep consuming the public rate-limit budget the *servable*
requests need — the budget whose exhaustion is `EGeneral:Too many requests`
(already a retryable class here, see `retryErrors`).

## 2. Evidence

### 2.1 — the venue rejects 3, 120 and 480

`intervalMap` (`core/src/exchange/exchanges/kraken/index.ts:139`) maps
`3m`→`3`, `2h`→`120`, `8h`→`480`. Kraken spot `/0/public/OHLC` accepts only
`1, 5, 15, 30, 60, 240, 1440, 10080, 21600` minutes. Probed directly
(2026-09-08, no auth needed):

```
GET /0/public/OHLC?pair=TAOUSD&interval=3    -> {"error":["EGeneral:Invalid arguments"]}
GET /0/public/OHLC?pair=TAOUSD&interval=120  -> {"error":["EGeneral:Invalid arguments"]}
GET /0/public/OHLC?pair=TAOUSD&interval=480  -> {"error":["EGeneral:Invalid arguments"]}
GET /0/public/OHLC?pair=TAOUSD&interval=60   -> {"error":[],"result":{"TAOUSD":[[...]]}}
```

The call site sends `intervalMinutes` straight through, with a cast that
*names* the valid set but cannot enforce it (`index.ts:4074`):

```ts
interval: intervalMinutes as 1 | 5 | 15 | 30 | 60 | 240 | 1440 | 10080 | 21600,
```

### 2.2 — it is happening in production, on the reporter's pair

`Gainium--exchange-connector---62.84.191.{108,109,110,111,112}-error.log`,
2026-09-08 (read-only prod `logs` helper):

```
10:31:09 AM ERROR [Details: {"error":["EGeneral:Invalid arguments"],"httpStatus":200},
  getCandles called with params: ["TAO-USD","3m","1772035200000","1772164800000","720"]]
  [62.84.191.108] [200] Kraken API error: EGeneral:Invalid arguments
```

All five nodes, ~110 lines. Every window is 129,600,000 ms = 36 h = 720 × 3m,
i.e. the archive backfiller chunking the reporter's range; the `from`/`to`
values span 2026-02-10 → 2026-04-11 — verbatim the "February–March" the
reporter said returns nothing. Timestamp histogram on node .108 shows the
caller's cadence:

```
2 09/08/2026, 10:31:09 AM
9 09/08/2026, 10:31:39 AM
1 09/08/2026, 10:32:09 AM
```

30 s apart. `EGeneral:Invalid arguments` matches nothing in `retryErrors`, so
the *connector* does not retry it — the 30 s repeat is the caller's own loop,
and each pass costs one public Kraken request per window per node.

### 2.3 — Kraken spot OHLC cannot reach old history at all

`since` does not page backwards: the endpoint always answers with the ~720 most
recent candles. Probed 2026-09-08 with `since` = 2026-02-10:

| interval | rows | first candle | last candle |
|---|---|---|---|
| `1`  | 721 | 2026-09-08T01:50Z | 2026-09-08T13:50Z |
| `60` | 721 | 2026-08-09T13:00Z | 2026-09-08T13:00Z |

So the reachable horizon is `720 × interval`: 12 h at 1m, 30 d at 1h, 120 d at
4h. `getCandles` then post-filters with `c.time >= from` / `c.time <= to`, so a
window older than the horizon yields `status: OK` with `[]` — after the request
has already been paid for. This is also the mechanism behind the reporter's
"Partial history — 15 of 29 days": 720 × 30m = 15 days.

### 2.4 — Kraken's 1m series contains zero-trade filler that its own aggregation ignores

Found while validating the fix (§3.1) against a natively-supported interval,
not predicted up front. A minute with no trades comes back as a bar with
`volume = 0`, `count = 0` and `open = high = low = close` at a carried price.
On TAO/USD, 2026-09-08, **115 of 721** 1m rows were filler.

Kraken's own native 15m bars do **not** count them. Where a filler opened a 15m
window, the native bar took its open from the next traded minute — and in one
case the filler's price sat outside the native bar's entire range:

| 15m bucket | filler 1m at bucket start | Kraken's native 15m bar |
|---|---|---|
| 11:30Z | O=H=L=C `254.6719`, vol `0.00000`, count `0` | open `254.2689`, high `254.4356` |

So "aggregate the base interval" is only equivalent to a native bar if filler
is excluded from open/high/low/close. Counting it produces bars Kraken itself
disagrees with — silently wrong backtest input, which is worse than the
`EGeneral:Invalid arguments` this bug started as.

## 3. Assumption (hypothesis)

Two distinct causes, both in the spot branch of `getCandles`:

- **3.1** `intervalMap` is a *unit conversion* (`'2h'` → 120 minutes) being used
  as a *venue capability map*. Three of its eleven entries are not values Kraken
  accepts. Kraken can still serve those bars, just not natively: each is an
  exact integer multiple of a supported base (`3m` = 3 × 1m, `2h` = 2 × 60m,
  `8h` = 2 × 240m), so fetching the base and aggregating is lossless — provided
  zero-trade filler bars are excluded from OHLC, per §2.4.
- **3.2** Nothing consults the `720 × interval` horizon before calling out, so a
  provably unreachable window is discovered at the cost of a public API request,
  once per window per node per caller-retry.

## 4. Scope / non-goals

- **Spot only.** The `usdm` branch uses a different client and passes `interval`
  through as `resolution`; no production evidence implicates it, and it is not
  touched.
- **Not fixed here:** that Kraken serves no deep spot candle history at all.
  That is a venue ceiling, not our defect — after this change a February 3m
  backtest still returns no data, it just does so without a doomed venue
  request. Making Kraken backtests reach further needs the ClickHouse archive to
  hold that history, which is `market-archive`'s problem, not the connector's.
- **No contract change.** An unreachable window keeps returning
  `status: OK` + `[]`, exactly as a supported interval does today; only the
  network call disappears. Turning it into an error would change what every
  caller of `BaseReturn<CandleResponse[]>` sees.
