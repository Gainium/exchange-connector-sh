# 007 — Coinbase `getAllOpenOrders` returns only the first page of resting orders

## §1 Definition

`CoinbaseExchange.getAllOpenOrders()` is the venue-backed answer to "what is
resting on this Coinbase account right now?". It has two shapes, both wrong in
the same way:

- **§1.1 list shape** (`returnOrders = true`) — MUST return **every** order the
  venue reports as `OPEN` for the account (or for `symbol`, when given).
  Actually: it returns at most the **first page** the venue hands back and
  silently drops the rest.
- **§1.2 count shape** (`returnOrders = false`) — MUST return the **true number**
  of open orders for `symbol`. Actually: it returns the length of that same
  first page, so the number is capped at the page size.

"Silently" is the load-bearing word. There is no error, no warning, no partial
flag — `status: OK` with a truncated array is indistinguishable from `status: OK`
with a complete one.

### §1.3 Who reads this

- `main-app` `core/src/graphql/handlers/orders.handler.ts` calls
  `getAllOpenOrders(undefined, true)` — this is the dashboard's **Open orders**
  view and the order-import flow. Account-wide, so it is the shape that
  truncates in practice.
- `main-app` `core/src/bot/main.ts` `getActiveOrders(symbol)` calls the count
  shape; `core/src/bot/helper.ts` and `comboHelper.ts` compare that count against
  `ExchangeInfo.maxOrders` (500 for Coinbase) before letting a bot start. An
  under-count makes that guard too permissive.

## §2 Evidence

Captured live 2026-09-09, read-only, against the reporting account's real
Coinbase connection (`api.gainium.io` GraphQL as the reporter).

### §2.1 The venue-backed list is capped at exactly 25

`getAllOpenOrders(input:{exchangeUUID:"…"})` →

```
status: OK   rows: 25   distinct pairs: 11
```

The 25 rows are a **contiguous time slice**, oldest `2026-09-03T22:32:13.942Z`,
newest `2026-09-07T22:39:14.667Z` — i.e. the list ends two days before the call.

### §2.2 Orders that are unambiguously live at the venue are absent from it

The same account has 50 `open` deals across 50 distinct pairs. Reading four of
them (`getDealOrders`, pairs `SWELL-USDC`, `SAPIEN-USDC`, `AVAX-USDC`,
`XYO-USDC` — none of which appear in §2.1) shows 6 `NEW` orders each, placed
minutes before the §2.1 call:

```
XYO-USDC  BUY  … SELL   2026-09-09T15:21:18Z … 15:21:21Z
AVAX-USDC BUY  … SELL   2026-09-09T15:23:11Z … 15:23:12Z
```

The §2.1 call ran at `2026-09-09T15:31Z`. A take-profit SELL placed eight
minutes earlier and still `NEW` cannot be an orphaned record — it is resting at
the venue. It is not in the list. **More than 25 open orders exist, and the list
stops at 25.**

### §2.3 25 is not a venue number, it is our SDK's default

`coinbase-advanced-node@4.1.0`, the version installed and running,
`dist/order/OrderAPI.js`:

```js
getOrders(query) {
    if (!query) { query = {}; }
    if (!query?.limit) { query.limit = 25; }          // ← unconditional
    const response = yield this.apiClient.get(`${resource}`, { params: query });
    return { data: response.data.orders,
             pagination: formatPaginationFromResponse(response) };
}
```

Our caller (`coinbase/index.ts:486-496`) builds `{ product_id, order_status }`
and never sets `limit`, so every call is a `limit=25` call. A page that comes
back holding exactly its own ceiling is a page at its ceiling.

### §2.4 The same file already knows how to do this

`getBalance` (`coinbase/index.ts:558-601`) reads `pagination.has_next`, and
re-requests with `{ cursor: pagination.cursor, limit: 250 }` until the venue
says there is no next page. `getAllOpenOrders` reads `orders.data` and nothing
else. The pagination metadata is present on both responses —
`formatPaginationFromResponse` populates `has_next` / `cursor` from
`/orders/historical/batch` exactly as it does from `/accounts`.

## §3 Assumption (hypothesis)

The root cause is a **missing `limit` plus a missing page loop in our caller**,
not anything venue- or credential-side:

1. Because the caller omits `limit`, the vendored SDK substitutes `25`. The
   ceiling is unconditional and applies to both the list and the count shape.
2. Because the caller ignores `pagination.has_next` / `pagination.cursor`,
   whatever the first page does not contain is discarded.

Predicted, therefore: with `limit` set and the `has_next`/`cursor` loop added,
the same stubbed venue that today yields 25 rows yields all of them, and the
count shape reports the accumulated total rather than the first page's length.

## §4 Behaviour required of the fix

- **§4.1** Every `getOrders` request this method makes carries an explicit
  `limit`, so the SDK's `25` default can never apply.
- **§4.2** While the venue reports `has_next` and hands back a `cursor`, the
  method requests the next page and accumulates it, before any conversion.
- **§4.3** The count shape counts the accumulated rows, not the first page.
- **§4.4** Each additional venue request passes through the same rate-limit gate
  (`checkLimits('private', …)`) as the first, so paging cannot outrun the
  connector's own Coinbase budget.
- **§4.5** The loop terminates on a malformed or hostile pagination reply — a
  missing cursor, a repeated cursor, an empty page, or an implausible number of
  pages — rather than spinning against the venue.
- **§4.6** No change to the method's signature, its `BaseReturn` shape, or its
  error handling. Callers are untouched.

## §5 Open questions / assumptions not resolved here

- **§5.1** Page size. `getBalance` uses `250` against `/accounts`, whose
  documented maximum is 250. `/orders/historical/batch` documents a higher
  ceiling, but 250 is the number this file has already proven against the venue
  and is left as the plan's decision.
- **§5.2** `OrderListQueryParam` (the SDK's own query type) declares no `cursor`
  field even though `getOrders` forwards the whole query object to the request's
  `params`. Threading a cursor needs a cast; how to express it narrowly is the
  plan's decision.
