# 008 — `convertOrder` fabricates an order out of a Coinbase payload that describes none

Issue #727. Bug spec (existing behaviour is wrong).

Downstream of this defect are main-app specs `028` (#719) and `029`. Both are
about what main-app does *with* the answer. This spec is about the answer
itself: who wrote the rows.

## 1. Definition

### 1.1 Expected

`CoinbaseExchange.convertOrder` translates a Coinbase order into the platform's
`CommonOrder`. Translation presupposes something to translate. A payload that
does not state what the order *is* — its id, its pair, its side, its type, when
it was created — is not an order, and the connector must say so
(`status: NOTOK`) rather than answer `status: OK` with values it invented.

This is the `BaseReturn<T>` contract (root `CLAUDE.md` Danger List §1):
`status: OK` means "here is the venue's answer". Every consumer — main-app's
order reconcile, the dashboard's Open orders view, market-archive — reads it
that way and has no second source to check it against.

### 1.2 Actual

`convertOrder` has three unconditional fallbacks, and every one of them turns
"the venue did not say" into a confident statement:

| field | code | result when the payload is silent |
|---|---|---|
| `type` | `orderType()`'s final `return 'MARKET'` | `MARKET` |
| `side` | `order.side === OrderSide.SELL ? 'SELL' : 'BUY'` | `BUY` |
| `transactTime` | `+new Date(order.created_time)` | `NaN` |
| `updateTime` | `+new Date(order.last_fill_time ?? order.created_time)` | `NaN` |
| `price` | `limitPrice` off an absent `order_configuration` | `undefined` |

`status` is copied verbatim, so a payload that says `FILLED` and nothing else
comes back as a **fully formed, FILLED, MARKET BUY order**, under `status: OK`.

The `NaN` timestamps do not survive as `NaN`: the answer crosses
exchange-balancer → main-app as JSON, and `JSON.stringify(NaN)` is `null`. So
main-app receives literal `null`s, which mongoose stores as BSON `null` rather
than refusing them.

### 1.3 Production evidence

A single short window on one venue rewrote a set of live order rows — across
several accounts and every deal order kind the engine uses (safety orders,
take-profits, grid legs, manual orders) — to a byte-identical stamp. Read
read-only from production, the shape is:

```
orderId <a real venue uuid>   status FILLED   type MARKET   side BUY
price '0'   executedQty '0'   cummulativeQuoteQty '0'   fills []
transactTime null (BSON null, $type: 'null')   updateTime null
origPrice / origQty  = the values the order was placed with
```

Several of those rows are take-profits, placed **SELL LIMIT** and now recorded
`BUY MARKET`. A venue payload describing a real order cannot produce that;
`convertOrder`'s defaults can, and do.

`price '0'` / `executedQty '0'` are consumer-side consequences already
documented in main-app spec `028`: the merge collapses its `NaN` price
derivation to `0`, and an `executedQty` the payload never stated is simply
absent from the update, leaving the row's own `'0'` standing.

The window, the unrelated accounts and the unrelated order kinds are all one
venue-side episode; what makes it OUR defect is that a payload we could not
read was answered as one we could.

## 2. Evidence

Driving the real `CoinbaseExchange.getOrder` over a stubbed
`client.rest.order.getOrder` that returns `{order_id, status: 'FILLED'}` — the
minimum payload consistent with the persisted rows (each row's `orderId` is a
real venue uuid, so the venue did name the order):

```
status: OK | reason: null
{"orderId":"<uuid>","transactTime":null,"updateTime":null,
 "status":"FILLED","type":"MARKET","side":"BUY","fills":[]}
```

Every field the connector supplies matches the production row exactly,
including the `null` timestamps once the answer is JSON-encoded for transport.

The same harness with a complete Coinbase order payload returns the order
unchanged — `type LIMIT`, `side BUY`, real timestamps, real quantities — which
is what §4.2 has to keep true.

## 3. Assumption (hypothesis)

The root cause is that **`convertOrder` has no precondition**: it maps whatever
it is handed, substituting defaults for everything the payload omits, and its
callers wrap the result in `returnGood`. If that is right, a guard that refuses
a payload which states none of `order_id` / `product_id` / `side` /
`order_type` / `created_time` removes the entire stamp at the producer, for
every order kind and every caller at once, and changes nothing for a payload
that states them.

## 4. Required behaviour

- **§4.1** A payload that does not state `order_id`, `product_id`, `side`,
  `order_type` or a parseable `created_time` is refused. The connector answers
  `status: NOTOK` with a reason naming the order id it was asked about and the
  fields the payload did not state.
- **§4.2** A payload that states them converts exactly as it does today —
  field for field, including partially filled and resting orders, whose
  `filled_size` / `average_filled_price` / `total_fees` may legitimately be
  absent or zero. Those are *fill* facts, not identity facts, and are not part
  of the precondition.
- **§4.3** "States" means the payload says something, not that it says
  something we recognise. An `order_type` of `STOP` is stated; mapping it to
  `MARKET` is pre-existing behaviour and is not changed here.
- **§4.4** The refusal is not retried by `handleCoinbaseErrors`. A payload the
  venue already sent does not improve by asking the connector's own ladder
  again; the caller's reconcile is what re-asks. (main-app's
  `getOrderForReconcile` ladder does exactly that, and its `unresolved` warn is
  the health signal this episode never produced.)
- **§4.5** All three call sites are covered by the one guard — `getOrder`,
  `cancelOrder`'s post-cancel re-read, and `getAllOpenOrders`. A fabricated row
  inside an open-orders LIST is the same defect as a fabricated answer about
  one order, and both reach users.

## 6. Out of scope (stays open)

- **The already-corrupted rows and the deals holding them.** Nothing here
  rewrites existing state. Repairing them is a production database write.
- **Why Coinbase answered that way.** A venue-side episode is not something
  this repo can fix; refusing to launder it is.
- **main-app's merge still rebuilding `type` and `side` from the payload.**
  Spec `028` §4.3 stopped an unstated *quantity* from erasing ours; `type` and
  `side` are not covered by it and are still taken from `{ ...co }`. This fix
  removes the producer that exercised that hole. Closing the hole itself
  belongs in main-app and is left open.
