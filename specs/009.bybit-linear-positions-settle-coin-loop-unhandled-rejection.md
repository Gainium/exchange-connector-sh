# 009 — Bybit linear `futures_getPositions` settle-coin loop escapes the `BaseReturn` contract

Bug spec (existing behaviour is wrong).

## §1 Definition

`futures_getPositions()` is the connector's `/positions` handler for a futures
account. Like every other connector method it owes its caller a
`BaseReturn<PositionInfo[]>` — `{status: 'OK', data}` or `{status: 'NOTOK',
reason}` — **for every outcome, including a venue rejection**. It must never
reject its own promise, and it must never answer `OK` with a list it knows is
incomplete.

For a USDT-margined (linear) account with no `symbol` argument, Bybit has no
"all positions" call: the connector loops the account's settle coins and asks
`getPositionInfo({category:'linear', settleCoin})` once per coin.

### §1.1 Expected

- A settle-coin call that **rejects** (HTTP-level failure — the bybit-api client
  rethrows `{code, message}` out of `parseException`) is handled: the whole call
  answers `{status: NOTOK, reason: <venue message>}`.
- A settle-coin call that answers with a **non-`OK` `retMsg`** is handled the
  same way — a `BybitError(retMsg, retCode)` through the same handler.
- A **retryable** venue error (a code in `retryErrors`) retries the whole read,
  and the retry re-enters the **settle-coin** branch — not the per-symbol branch.
- When every settle coin answers `OK`, the positions of all coins are returned
  with `status: OK` (unchanged).

### §1.2 Actual

- A rejection escapes the loop entirely: `futures_getPositions()` rejects, the
  Nest layer turns it into `Internal Server Error`, and main-app's position
  reconciler logs `Internal Server Error … endpoint: positions, method: get,
  exchange: bybitLinear` while the connector node logs `[ExceptionsHandler]`.
- A non-`OK` `retMsg` is silently swallowed by `if (result.retMsg === 'OK')`
  with no `else`: that coin contributes nothing and the call still returns
  `{status: OK}` with a **short list**. To the reconciler a missing symbol is
  indistinguishable from a position that was closed.

## §2 Evidence

- Code: `core/src/exchange/exchanges/bybit/index.ts` L350-362 — the loop body is
  `await this.client.getPositionInfo(...).then(...)` with **no `.catch`** and no
  `handleBybitErrors`. The per-symbol branch 15 lines below (L367-390) has both.
- Venue client: `bybit-api@4.6.4` `BaseRestClient.parseException` throws
  `{code: response.status, message: response.statusText, body, …}` for any
  non-2xx — e.g. the production `code: 401 'API key is invalid.'`. Nothing in
  the loop catches it.
- Production: 48 error lines, 100% of the position-reconciler error log,
  `Internal Server Error … endpoint: positions, method: get, exchange:
  bybitLinear`, in 4 clusters over 1.3h, with matching `[ExceptionsHandler]`
  bursts at the same timestamps on three connector nodes and no restart or
  deploy in the window.
- Reproduced headlessly in §3's test: the current code **rejects** instead of
  returning a `BaseReturn`.

## §3 Assumption (hypothesis)

The root cause is the missing error handling on the settle-coin loop, not
anything in the reconciler or in `handleBybitErrors` itself. Routing both
failure shapes of the loop through `handleBybitErrors` — and failing the whole
call rather than returning the coins that did answer — restores the
`BaseReturn` contract, removes the 500, and stops a partial read being read as
"these positions are gone".

The retry path is part of the assumption: `handleBybitErrors` retries by calling
`cb.bind(this)(...args)`, so the args handed to it decide which branch the retry
re-enters. `symbol` must be passed explicitly (it is `undefined` in this branch)
or the retry would receive the `TimeProfile` as its `symbol` and issue a
per-symbol request for a non-existent symbol.

## §4 Out of scope

- The per-symbol branch (L380-389) omits `symbol` from its `handleBybitErrors`
  args and has the retry defect described above. It is a *different* call path
  (a `symbol` was supplied) and not the cause of this incident; left untouched,
  recorded here.
- main-app `src/positionReconciler/venue.ts` logs the per-account failure at
  `debug`, so the failing `exchangeUUID` is unnameable in production. Separate
  repo, separate change.
