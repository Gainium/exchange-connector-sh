# 010 — Kraken spot: concurrent signed requests on one key arrive out of nonce order

Bug spec (Definition / Evidence / Assumption).

## §1 Definition

**§1.1 Expected.** Kraken spot private requests issued on one API key by one
connector process are accepted by Kraken however many callers issue them at
once. A nonce rejection is never caused by the connector's own request
scheduling.

**§1.2 Actual.** Private calls issued close together on one key are signed with
strictly increasing nonces but dispatched simultaneously. Network latency
reorders them; Kraken accepts a later nonce first and rejects the earlier ones
with `EAPI:Invalid nonce` (Kraken requires each nonce on a key to be strictly
greater than the last one it accepted, judged on arrival).

**§1.3 Expected.** A nonce rejection that still occurs is retried a small,
bounded number of times. Every rejected attempt counts toward Kraken
temporarily locking the key, so retrying must not multiply them.

**§1.4 Actual.** Nonce rejections ride the generic retry ladder (10 attempts),
and each retry can be rejected again.

**§1.5 Expected.** A call the local rate limiter defers is charged against the
budget when it is finally admitted, so deferred calls are released gradually,
not all at the same instant.

**§1.6 Actual (deployment wrapper).** The private deployment wrapper overrides
`checkLimits` with an older copy that computes one wait, sleeps, and sends
without charging. Every deferred call gets the same wait and all are released
together — a burst of simultaneous signed requests on one key, which is exactly
the input §1.2 needs. The override also bypasses the per-account accounting and
heavy-endpoint costing that core's `checkLimits` implements.

**§1.7 Consequence.** Enough rejections in a short window and Kraken answers
every request on the key with `EGeneral:Temporary lockout`, which stops every
bot trading on that account until the lockout expires.

## §2 Evidence

**§2.1 Logs.** Bursts of `EAPI:Invalid nonce` on a single connector process,
followed within minutes by `EGeneral:Temporary lockout` for the same account.
The logged nonces show the inversion: a nonce is accepted and the nonce one
lower, from the same process, is rejected moments later. Rejected nonces cluster
in groups roughly every two seconds at the same millisecond offset — consistent
with deferred calls being released together (§1.6).

**§2.2 Not duplicates.** The shared per-key nonce counter (`nextKrakenNonce`,
spec'd in its own header) is deployed; the rejected nonces are unique.

**§2.3 Code path.** `@siebly/kraken-api` `BaseRestClient._call` calls
`buildRequest` (which signs, assigning the nonce) and dispatches immediately;
nothing orders dispatch per key. `retryErrors` includes `EAPI:Invalid nonce`,
and `handleKrakenErrors` falls through to `this.retry` (10) for it.

**§2.4 Reproduction, before the fix.**
- `src/kraken-custom/key-order.spec.ts`: ten concurrent private calls on one key
  through the real `SpotClient`, against a fake Kraken that enforces the nonce
  rule with uneven latency → 6 of 10 rejected, up to 9 in flight at once.
- `src/exchange/exchanges/kraken/rate-limit.spec.ts`: sustained nonce rejections
  run 10 attempts.

**§2.5 Wrapper.** The deployed exchange factory instantiates the wrapper class,
whose `checkLimits` predates core's per-account accounting and
charge-on-admission loop.

## §3 Assumption (hypothesis)

**§3.1** The rejections are caused by concurrent dispatch on one key within one
process. Serializing signing and dispatch per API key — a request is signed only
after the previous request on that key has been answered — eliminates them
in-process.

**§3.2** The serialization needs a bounded hold, so one request that never
answers cannot stall every other call on that key.

**§3.3** Several processes serving the same key can still interleave. That is
not addressed here; the bounded retry (§1.3) remains the backstop, which is why
the bound is small rather than zero.

**§3.4** Public (unsigned) requests carry no nonce and must not be serialized.

## §4 Out of scope

- The derivatives (futures) client, which signs with an empty nonce.
- How the platform classifies or displays the lockout error to users.
- Cross-process ordering (§3.3).
