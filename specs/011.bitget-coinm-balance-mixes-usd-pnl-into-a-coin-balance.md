# 011 — Bitget COIN-M balance subtracts a USD PnL from a coin equity

Bug #772 ("Exchange balance is incorrect"). Symptom: a `bitgetCoinm`
(COIN-FUTURES / inverse) connection's BTC balance is reported 6–24× too high
and oscillates every refresh, so a bot sizing its base order as
**`% of Total`** opens deals several times too large and the venue then
rejects them for insufficient balance.

This is the **COIN-M half of spec 006**. Spec 006 replaced the `available`
anchor with `accountEquity - unrealizedPL` for *every* Bitget futures product
type; it was written, reproduced and verified entirely against a **USDT-M**
account, where the margin coin *is* the contracts' quote currency. On an
inverse account the two terms are not in the same currency.

## 1. Definition

### 1.1 — expected

`BitgetExchange.futures_getBalance()` returns, per margin coin, a
`{ free, locked }` pair whose sum is that coin's balance **on the venue, in
that coin** — spec 006 §1.1, unchanged. For a COIN-FUTURES account whose BTC
balance is ~`0.0074 BTC`, `free + locked` must be ~`0.0074`, not ~`0.18`.

### 1.2 — actual

```ts
const equityBased = num(d.accountEquity) - num(d.unrealizedPL)
```

`accountEquity` is quoted in the margin coin for every product type.
`unrealizedPL` is **not**: on COIN-FUTURES the contracts are USD-quoted
inverse contracts, and the account endpoint reports their unrealized PnL in
the contracts' quote currency, not in the margin coin. The subtraction
therefore mixes units and moves the balance by roughly **`|PnL in USD|` whole
coins** — for BTC, an error of ~1 BTC per 1 USD of open PnL.

## 2. Evidence

All figures below are the reporter's own production account
(`bitgetCoinm`, margin coin BTC), read over the dashboard GraphQL
(`getBalances`, `getBotDeals`) and from the daily
`snapshotsperexchanges` totals quoted by triage.

### 2.1 — the reported balance, against the balance the bot actually has

| | BTC |
|---|---|
| ours: `free` | `0.17624668510500002` |
| ours: `locked` | `0.00005992` |
| ours: `free + locked` (the Total the bot sizes from) | **`0.17630660510500002`** |
| the account's real balance, as the bot's own deals record it (`balanceStart` on 36 deals, every one before the onset) | `0.0065`–`0.0074` |

The same account's sibling connection — same user, same venue, same product
type, **no open position** — reports `0.00735383 BTC` and is correct. With
`unrealizedPL == 0` the formula degenerates to `accountEquity`, which is
right; the account only goes wrong while a position is open. That is the
reporter's "updating balances sometimes works".

### 2.2 — the sizing failure, in the bot's own event log

Deal `6aa42c8bd5173402105a464d` was created 2026-09-11 16:30:03Z with
`balanceStart = 0.044475174432 BTC`; the next deal 13 minutes later recorded
`0.00736833 BTC` — 6.04× lower. The bot sizes `% of Total` (9.6%, leverage 2):
`0.044475174432 × 0.096 × 2 = 0.008539` → the deal's recorded `size = 0.0086`,
where the correct size is `~0.0014`. One second later the venue disagreed:

```
2026-09-11T16:30:04Z | bot 69931b72eedf3d7447c9fa97 | error
"Not enough balance … balance total - 0.0030495 BTC, free - 0 BTC, required - 0.0115 BTC"
```

### 2.3 — the missing term can only be USD, never BTC

Our reported balance minus the account's real balance is
`0.1763 - 0.00737 ≈ 0.169`, and that residue is `-unrealizedPL`.

- **As BTC** it would be an unrealized loss of `0.169 BTC ≈ 13,000 USD` on an
  account holding `0.0074 BTC ≈ 580 USD` — 23× the entire wallet. An account
  cannot carry an unrealized loss 23× its own balance; it is liquidated long
  before that. It is also 4 orders of magnitude away from what this bot's
  positions actually do: its 36 deals realize `~1e-5 BTC` (`$0.6`–`$7.6`)
  each.
- **As USD** it is a `-$0.17` open PnL on a position whose committed margin is
  `0.00005992 BTC ≈ $4`. Ordinary.

Triage sampled the stored balance three times two minutes apart —
`0.175956695105`, `0.181806615105`, `0.174386715105` — a `±0.007` swing per
sample. `±$0.007` of PnL drift on that position is a sub-0.1% price move;
`±0.007 BTC` would be `±$500`, which the position cannot produce.

### 2.4 — the onset matches our own deploy, and only the inverse half moved

Daily `snapshotsperexchanges` totals for the affected account:
`09-07 $580`, `09-08 $581`, **`09-09 $83,974`**, `09-10 $464`,
**`09-11 $62,498`**, **`09-12 $70,316`**, `09-13 $872`, **`09-14 $11,424`**,
**`09-15 $13,028`**. Last good snapshot 09-08 22:00Z, first bad 09-09 22:00Z;
deploy **#218** (2026-09-09 15:02Z, exchange-connector, bug #594) shipped
`e2ff108` / core `d046400`, which introduced the line in §1.2. The corrupted
values also carry that line's fingerprint — 12 significant decimals where the
venue quotes 8. The USDT-M behaviour deploy #218 was written for is not
implicated and must not be reverted.

### 2.5 — what could NOT be captured

The raw `/api/v2/mix/account/accounts` body for a COIN-FUTURES account was
not captured: we cannot call Bitget with the reporter's keys and prod file
reads are not available. Bitget's own field table documents `unrealizedPL`
only as "Unrealized profit and loss", with no currency; `ccxt`'s Bitget
`parseBalance` does not use the field at all for swap accounts (it takes
`total = accountEquity`, `free = maxTransferOut`). §2.3 therefore establishes
the denomination by arithmetic contradiction — that `unrealizedPL` is **not
in the margin coin** on COIN-FUTURES is proven; that the other unit is
specifically USD is inference, and the fix below deliberately does not depend
on it.

## 3. Assumption (hypothesis)

The root cause is that `unrealizedPL` is only subtractable from
`accountEquity` when the **margin coin is the contracts' quote currency** —
true for USDT-FUTURES and USDC-FUTURES (linear), false for COIN-FUTURES
(inverse), where the margin coin is the base asset.

For inverse, the correct coin-denominated anchor available in the same
payload is `accountEquity` itself: it is the only account-wide figure the
venue quotes in the margin coin, §2.1 shows it is right whenever the PnL term
is zero, and it is exactly the anchor `kucoin/index.ts` `futures_getBalance`
already uses (spec 006 §1.1's own comparison table). Using it means the
inverse total is account **equity** rather than wallet balance — it differs
from the wallet balance by the position's PnL *in coin terms*, which for this
account is `~1e-5 BTC` (0.1%) against the 2,300% error it removes — and it
cannot reintroduce a unit mix, because no cross-currency term is read at all.

Consequence if true: a COIN-FUTURES account with no position is unchanged
(`unrealizedPL == 0` already), every USDT-M/USDC-M account is unchanged
(spec 006's tests keep passing byte-for-byte), and only inverse accounts with
an open position move — back down to the coin balance the venue holds.
