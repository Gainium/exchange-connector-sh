# 011 — Retry log lines print the plaintext API key

Bug spec (existing behaviour is wrong).

## §1 Definition

When a venue call is rate-limited or blocked, the adapter's error handler waits
and retries, and logs one line saying so. That line needs to say *which
account* is being throttled, so an operator can tell one hot account from a
platform-wide limit.

### §1.1 Expected

- The line identifies the account by a **fingerprint** of its API key: short,
  stable for a given key, and not reversible to the key.
- The same key fingerprints identically on every venue, and identically to the
  account id the Kraken adapter already derives (`hashKrakenKey`).
- No retry line contains the API key or the API secret.
- The rest of each line (venue, reason, wait, attempt, method name) is unchanged.

### §1.2 Actual

These lines interpolate `this.key` — the adapter's API key, which the service
has already decrypted before constructing the adapter — verbatim:

| Adapter | Handler | Line |
|---|---|---|
| Bybit | `handleBybitErrors` | `Bybit Too many visits wait …` |
| Bitget | `handleBitgetErrors` | `Bitget Too many visits wait …` |
| Bitget | `handleBitgetErrors` | `Bitget too many requests wait …` (from the 2nd attempt) |
| Bitget | `handleBitgetErrors` | `Bitget 403 block wait …` |
| Binance | `handleBinanceErrors` | `Too many new order …` (code `-1015`) |

Rate limiting is routine, so these lines are among the most frequent the
connector writes, and every one carries a live key id into process logs that
are retained, rotated, searched and read by people and tooling.

## §2 Evidence

- Code: each line above ends its template literal with `${this.key}`
  (`bybit/index.ts` `handleBybitErrors`; `bitget/index.ts`
  `handleBitgetErrors`, three branches; `binance/index.ts`
  `handleBinanceErrors`, the `-1015` branch).
- The Kraken adapter shows the intended pattern already: its account-scoped
  caches and its trade-volume log lines use `hashKrakenKey(this.key)`, a djb2
  hash rendered in base36, with the comment that the raw key should not be
  retained.
- Reproduced headlessly by §3's test against the unmodified adapters: each
  handler, driven with an error that reaches its logging branch, logs
  `… retried <the synthetic key>`.

## §3 Assumption (hypothesis)

The key reaches these log lines only through the `${this.key}` interpolations
listed in §1.2. Replacing each with a fingerprint of the same key removes the key
from every retry line without losing the ability to correlate lines for one
account. The secret is never interpolated on these paths; the test asserts that
too, so a regression that adds it fails.

## §4 Out of scope

- **Hyperliquid** retry lines also interpolate `this.key`, but on that venue
  the key is the account's **public wallet address**, not a credential. It is
  already public on chain, and it is the identifier an operator looks up in an
  explorer. Left unchanged deliberately.
- **Kraken** already logs `hashKrakenKey(this.key)`. It is not refactored onto
  the new helper; the helper reproduces the same scheme, so the two agree.
- Credentials stapled onto *thrown SDK errors* are a different path, handled by
  `redact.ts` and the global exception filter.
