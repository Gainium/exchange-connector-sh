# 012 — A Kraken order call that is deferred still spends a token in the bucket that admitted it

## §1 Definition

Kraken meters two independent budgets for a private order call
(<https://docs.kraken.com/api/docs/guides/spot-rest-ratelimits>,
<https://docs.kraken.com/api/docs/guides/spot-ratelimits>):

- a **private-REST counter** per API key (Intermediate: max 20, decay −0.5/s), and
- a **matching-engine counter** per pair per account (Intermediate: threshold 125,
  decay −2.34/s).

`limit.ts`'s `addOrderCall` models both. A call may only be sent when **both**
budgets admit it.

### §1.1 Expected

One `AddOrder` / `CancelOrder` request that is actually sent to Kraken must spend
**exactly one** REST token and **exactly one** matching-engine charge. A request
that is *deferred* (the limiter told the caller to wait) was never sent, so it
must spend **nothing** in *either* bucket — that is already the stated design of
`checkRestLimit` / `checkMatchingEngineLimit`, which deliberately do not charge a
refused call.

### §1.2 Actual

`addOrderCall` consults the two buckets independently and returns `Math.max()` of
their waits. Each bucket charges itself the moment *it* admits, without regard to
whether the *other* bucket refused. `checkLimits` (`index.ts`) then re-asks —
`await sleep(waitTime); waitTime = await charge()` — so the bucket that admitted
on the previous attempt is charged **again**, for a request that still has not
been sent.

Measured against the shipped module under a virtual clock, at steady state on one
account/pair:

| operation | REST charges per sent call | matching-engine charges per sent call |
|---|---|---|
| `cancel` | **1.70** | 1.00 |
| `add`    | 1.00 | **2.00** |

Both should be 1.00. The surplus is load Kraken never saw.

## §2 Evidence

### §2.1 The venue is not the one throttling us

Fixed-string search of the whole prod connector fleet's live + archived pm2 logs
(`logs -n 200 Gainium--exchange-connector---62.84.191.{108,109,110,111,112}
EAPI:Rate`): 37 hits in total, the most recent on **2026-08-25**. The reported
sweep happened 2026-09-18. Kraken has not rate-limited the fleet in 24 days, so
every second of the reported lag is the *local* limiter's own pacing.

### §2.2 The shape reproduces exactly

`checkLimits`' charge loop replayed against the real `limit.ts` under a virtual
clock, modelling the two REST calls the spot cancel path actually makes
(`cancelOrder` resolves the txid with `getOrder`, then `cancelOrderByOrderIdAndSymbol`):

| | harness | reported in prod |
|---|---|---|
| 48-order grid placement | 152.3 s | 2 m 45 s |
| 48-order teardown | 180.3 s | 2 m 54 s |
| opening burst | first 8 ops ~0.3 s apart | first 10 cancels ~0.1 s apart |
| steady cadence | 4000 ms | exactly 4.0 s (occasionally 6.0 s) |

Identical numbers with `KRAKEN_PER_ACCOUNT_LIMITS` on and off, so the diagnosis
does not depend on that flag.

### §2.3 The matching-engine cancel cost is NOT what paces the sweep

Counterfactual on the same harness — hold everything else and set the
matching-engine cancel cost to 0 (Kraken's real charge for an order resting
> 300 s):

| | 48-order teardown |
|---|---|
| as shipped (`CANCEL_ORDER_COST = 8`) | 180.3 s |
| matching-engine cancel cost 0 | 152.3 s |

28 s of 180 s. The remaining 152 s is the private-REST bucket, and the *placement*
half — which has no matching-engine pressure at all (`ADD_ORDER_COST` 1 against a
threshold of 125, ~1 % usage) — paces at the same 4000 ms. **The private-REST
bucket is what meters both halves.**

### §2.4 `CANCEL_ORDER_COST = 8` is still wrong, just not dominant

Kraken's published matching-engine penalty is scaled by how long the order has
rested: `< 5 s` +8, `< 10 s` +6, `< 15 s` +5, `< 45 s` +4, `< 90 s` +2,
`< 300 s` +1, and **0 above 300 s**. A grid order rests for minutes to hours, so
the flat `8` (the `< 5 s` worst case, as its own comment says) is fictional load —
worth the 28 s in §2.3, and no more. Charging it needs the order's age at the
cancel call site, which the connector does not currently have: `cancelOrder`'s
pre-flight `getOrder` never plumbs Kraken's `opentm` into `convertOrder`, so
`CommonOrder.transactTime` for Kraken spot is `Date.now()`. Out of scope here —
see §4.

## §3 Assumption (hypothesis)

`addOrderCall` treats two budgets that gate a single request as two independent
requests. Making it atomic — ask both without charging, and charge both only when
both admit — removes the surplus in §1.2 without loosening either budget, and
restores the property the 2026-08-31 re-ask loop was written to guarantee (a call
is charged when and only when it is sent).

The test must fail because the per-sent-call charge counts are > 1, not because
of any wait-time arithmetic.

## §4 Out of scope (named, not fixed here)

1. **Age-scaled matching-engine cancel/amend cost** (§2.4). Needs the order's open
   time at the cancel site; every route to it either adds a field to `CommonOrder`
   (root Danger List #1) or duplicates `getOrder`'s resolution logic. Worth 28 s
   of 180 s — not worth that blast radius inside this fix.
2. **The real bottleneck: 2 private-REST calls per order operation against a
   0.5 call/s budget.** Removing it is cross-repo and cannot land here:
   - a batched cancel (`SpotClient.cancelBatchOrders`, up to 50 `cl_ord_ids` in
     one REST call) needs a connector endpoint **and** a main-app deal-close call
     site — no bulk-cancel exists on the Exchange interface or the controller
     today (only `binance/index.ts:1370`, unrouted);
   - dropping `cancelOrder`'s `getOrder` pre-flight needs main-app to call the
     already-exposed `cancelOrderByOrderIdAndSymbol` with the txid it already
     holds. The pre-flight is deliberate (`index.ts:2866-2876`) and removing it
     unilaterally re-opens the duplicate-txid incident it prevents.
