# 013 — Kraken spot's cancel reports a fabricated order

Bug spec. The spot branch of `cancelOrderByOrderIdAndSymbol` answers a
successful cancel with a `CommonOrder` it invented, and every consumer that
reads the answer takes it as the order.

## 1. Definition

`cancelOrderByOrderIdAndSymbol` returns `BaseReturn<CommonOrder>`. The
`CommonOrder` is the contract's statement of **what the cancelled order was and
what it traded**.

### 1.1 Expected

After a successful Kraken **spot** cancel the returned `CommonOrder` describes
the real order:

- `price` — the price the order rested at (or its average fill price)
- `origQty` — the quantity it was placed for
- `executedQty` — the quantity it had traded when it died
- `side` — the side it was placed on
- `type` — the order type it was placed as
- `status` — `CANCELED`, because that is the outcome we observed

### 1.2 Actual

Every field but `status` is a constant:

```ts
this.convertOrder({
  orderId, symbol, clientOrderId: '',
  price: '0', origQty: '0', executedQty: '0',
  status: 'CANCELED', type: 'LIMIT', side: 'BUY',
})
```

So a cancelled SELL limit at 565.72 that had traded nothing is reported as a
**BUY** at **0**, and a cancelled SELL that had traded half its size is
reported as having traded **nothing**.

### 1.3 Why it reaches the stored order row

`main-app` `core/src/bot/main.ts` `cancelOrderOnExchange` copies **every** field
of the response onto the order row it holds (`Object.keys(order)` loop; it
excludes only `clientOrderId`, `origQty` and `origPrice`), then `setOrder`s and
`updateOrderOnDb`s it. So `price`, `executedQty`, `type` and `side` on the
persisted row become the constants above.

The engine's own reconciliations are downstream of that copy and are therefore
fed the constants:

- `+order.executedQty !== 0 && order.status === 'CANCELED'` — never true, so a
  partial fill on a cancelled Kraken-spot order is never promoted, never
  re-counted, and the row is deleted from the local map
  (`removeFromLocal && +request.data.executedQty === 0`).
- #717's `promotePartialToFilled: false` guard compares
  `+order.executedQty < +order.origQty` — `0 < origQty` is true for the wrong
  reason.
- #820's `settledBaseEntryFill` exists **only** because of this fabrication: it
  re-reads the fill the settle had already observed, for the one caller
  (`settlePartialBaseEntry`) that knows what the row held before it asked.

## 2. Evidence

### 2.1 The venue genuinely says nothing (so the synthesis is forced)

`@siebly/kraken-api` `SpotClient.cancelOrder` →
`Promise<SpotAPISuccessResponse<{ count: number; pending?: boolean }>>`. Kraken
spot's REST cancel carries no order detail at all. The data has to come from
somewhere else; today it is invented.

### 2.2 A production order, placed and then rewritten (observed, not inferred)

`Gainium-DCA-bot-out__2026-09-19_20-38-05.log.gz`:

```
2026-09-19T20:29:24.277Z | Worker 9 | Bot (dca) … |
  Processing msg XMR-USD D-TP-0000000000013, NEW, 565.72, base: 0, quote: 0 SELL, …
```

The same row in prod `orders` two minutes later:

```
clientOrderId D-TP-0000000000013   orderId OAAAAA-BBBBB-CCCCCC
price '0'   origPrice '565.72'   side 'BUY'   type 'LIMIT'   status 'CANCELED'
updateTime 2026-09-19T20:31:20.504Z
```

Placed as a **SELL at 565.72**; stored as a **BUY at 0**. `price` and `side` are
written onto an existing row from exactly one place — the copy loop in §1.3 —
and the values written are exactly the constants in §1.2.

### 2.3 Scale, and the signature that rules out any other writer

Prod `orders`, `exchange: 'kraken'`, last 30 days (read-only, 2026-09-19):

```
kraken orders                                    14774
  status CANCELED                                 9152
  CANCELED & price == '0'                         3665   ← 40% of all kraken cancels
  …with a real origPrice                          3665/3665
```

Broken down by `typeOrder`, **every one of the 3665 carries `side: 'BUY'`**:

```
dealRegular 2633 · dealGrid 344 · regular 333 · dealStart 197 · dealTP 158
```

The 158 `dealTP` rows are the ones that cannot be explained any other way: a
take profit on a long spot deal is a SELL. Across the same window the healthy
`dealTP` cancels are `side: 'SELL'` with a real price (227 of them); the 158
with `price: '0'` are all `side: 'BUY'`. There is no code path that places a BUY
take profit on a long spot deal.

## 3. Assumption (hypothesis)

The root cause is the synthesis in §1.2 and nothing downstream of it. Fixing it
where the fabrication happens — reporting the real order — makes every consumer
correct at once, including the ones (#717, #820) that currently exist to work
around it.

Corollary the fix must respect: the *only* thing we genuinely observed is that
the cancel succeeded, so `status` stays `CANCELED`. Promotion of a
cancelled-with-fills order to `FILLED` is the engine's decision
(`setFilledInsteadOfCanceled`, and #717's opt-out), and it must keep being the
engine's decision.

## 4. Behaviour required

### 4.1 The order we already read

`cancelOrder({ symbol, newClientOrderId })` — the path the bot engine uses —
resolves the txid with a `getOrder` round trip immediately before cancelling.
That answer IS the order. Report its `price`, `origQty`, `executedQty`, `type`,
`side` and `symbol`, with `status: 'CANCELED'`.

No extra venue call: Kraken spot's private REST budget is 20 tokens decaying at
0.5/s per account, and a grid teardown cancels many orders back to back.

### 4.2 The entry with nothing in hand

`cancelOrderByOrderIdAndSymbol({ symbol, orderId })` is also reachable directly
(main-app's terminal cancel, `graphql/handlers/orders.handler.ts`). There is no
pre-cancel read there, so re-read the txid **after** the cancel with the exact
`QueryOrders` lookup (`querySpotOrderByTxid`), which is authoritative for open
and closed orders and costs one token.

### 4.3 When nothing can be established

If §4.2's re-read cannot answer (the venue denies the txid, or the call fails),
the cancel still succeeded and must still be reported as success — a refusal
would send `cancelOrderOnExchange` down its unknown-order ladder and retire a
live order.

Report the cancel **without asserting what we do not know**: omit `price`,
`executedQty`, `type` and `side` from the response object. `cancelOrderOnExchange`
copies a field only when `Object.prototype.hasOwnProperty.call(request.data, key)`,
so an absent field leaves the row's own value alone. Asserting `'0'` is worse
than saying nothing.

### 4.4 Unchanged

- `status` is always `CANCELED` on a successful cancel (§3). `resolvers.ts`
  rejects the terminal cancel with "Order was not canceled on exchange" on
  anything else, and the engine's promotion logic keys off `CANCELED`.
- The futures branch. It already reports the real outcome (`cancel-verdict`).
- The error/retry path: `handleKrakenErrors(this.cancelOrderByOrderIdAndSymbol, …)`.
- `BaseReturn` and `CommonOrder` shapes, the abstract signature, and every other
  exchange. This is a Kraken-spot-local change.

## 5. Out of scope

- `main-app`. #717's guard and #820's `settledBaseEntryFill` stay exactly as
  they are: both are correct in their own right (a cancel answer may still
  legitimately report no fill), and reverting either as "now redundant" would
  re-open the issue it closed.
- `transactTime`/`updateTime`, which `convertOrder` already stamps with
  `Date.now()` for every Kraken spot order, not just cancels.
- `clientOrderId`, which the consumer's copy loop excludes.
