# 014 — Bitget inverse perpetuals moved to the unified API

Forum: "Bitget switched to Unified trading" (2026-09-18). Symptom: a Bitget
inverse (`bitgetCoinm`) connection shows a `$0` balance, and the pair list of
a bot on that connection offers **two** symbols — `BTCUSDU26` and `ETHUSDU26`
— where it used to offer the inverse perpetuals the bots were built on.

Spec 013 (unified accounts, v3) covers spot and USDT/USDC-M. It deliberately
refused COIN-M, on the reading that the unified COIN-M line was a *different
product* we did not list. That reading is now wrong in one direction that
matters: the classic COIN-M line no longer carries the perpetuals at all.

## 1. Definition

### 1.1 — expected

A `bitgetCoinm` connection lists Bitget's inverse **perpetual** contracts and
can trade them, whichever account system the key belongs to, with quantities
in the same unit the connector has always reported for this product type —
the **base coin** (spec 011 §1.1: a COIN-M pair's `baseAsset` is `BTC`,
`step` `0.001`).

### 1.2 — actual

- The listing is whatever `GET /api/v2/mix/market/contracts?productType=COIN-FUTURES`
  returns, which is now two quarterly delivery contracts.
- Every private classic call from a unified account is refused
  ("you are in unified account mode…"), so the balance resolves to nothing.
- The v3 path refuses COIN-M by construction: `utaRequest()` returns
  `UTA_COINM_UNSUPPORTED` before it sends anything.

## 2. Evidence

Public endpoints, read 2026-09-20 from the production host.

### 2.1 — the perpetuals are only on v3

| Endpoint | Result |
|---|---|
| `GET /api/v2/mix/market/contracts?productType=COIN-FUTURES` | `BTCUSDU26`, `ETHUSDU26` — both `symbolType: delivery` |
| `GET /api/v3/market/instruments?category=COIN-FUTURES` | 22 symbols, all `_CM`-suffixed, `BTCUSD_CM` … `HYPEUSD_CM`, `type: perpetual` |
| `GET /api/v2/mix/market/ticker?productType=COIN-FUTURES&symbol=BTCUSD_CM` | `data: []` |
| `GET /api/v3/market/tickers?category=COIN-FUTURES&symbol=BTCUSD_CM` | quotes, index price, funding |

So for the perpetuals both the **private** and the **public** v2 surfaces are
empty: candles, tickers and instrument data have to come from v3 as well.

### 2.2 — the production symptom

`Fee Update transient error, remote Bitget COIN-M futures are not supported
for Unified Trading Accounts yet…` — one `bitgetCoinm` key, 32 occurrences on
2026-09-20, i.e. our own refusal, not the venue's.

### 2.3 — the quantity unit differs between the two lines

| | classic `BTCUSDU26` (v2) | unified `BTCUSD_CM` (v3) |
|---|---|---|
| minimum order | `minTradeNum: 0.001` (BTC) | `minOrderQty: 1`, `minOrderAmount: 5` |
| quantity step | `sizeMultiplier: 0.001`, `volumePlace: 3` | `quantityMultiplier: 1`, `quantityPrecision: 0` |
| documented unit | base coin | **quote coin** — "`COIN-Futures` The unit is **quote coin**" (v3 place-order) |

A v3 inverse quantity is therefore a whole number of 1-USD contracts, and the
venue's own book confirms it: `BTCUSD_CM` quotes `bid1Size: 7500` against a
24h `volume24h: 111.3103` (BTC) / `turnover24h: 9001977` (USD).

### 2.4 — what the venue does **not** say

The v3 response fields are documented once for every category: `qty` and
`cumExecQty` "base coin", `cumExecValue` "quote coin" — which cannot be true
for a line whose request quantity is the quote coin. The read-back unit is
therefore **unverified** and must not be assumed from the documentation;
§3.4 makes the connector derive it from data that is internally consistent.

## 3. Decision

### 3.1 — the perpetuals are listed from v3, for every account

`bitgetCoinm` lists the v3 `COIN-FUTURES` instruments alongside the classic
delivery contracts. The listing is public, so it does not depend on the key's
account mode.

### 3.2 — pair names keep their historic form

The venue's `_CM` suffix is an artefact of the two lines coexisting. A pair is
listed, stored and streamed as `BTCUSD` — the name the classic perpetual had,
and the name existing bots and deals already carry — and the suffix is added
at the v3 boundary and stripped on the way back.

### 3.3 — a classic account is told what to do

The perpetuals cannot be traded from a classic account at all. An order for
one from a classic key is refused with the same shape as a Reality token's
(`REALITY_NEEDS_UTA`): a sentence naming the upgrade, not the venue's error.
The delivery contracts keep the classic path and are refused for a unified
account, since the unified line does not carry them.

### 3.4 — quantities convert at the v3 boundary, and the conversion checks itself

Outgoing: `contracts = round(base × price)`, at least `minOrderQty`, where
`price` is the order's own price, or the venue's last price for a market
order.

Incoming: the unit is derived per order rather than assumed. For an order
with fills, exactly one of `qty × avgPrice ≈ cumExecValue` (qty is base) or
`qty / avgPrice ≈ cumExecValue` (qty is contracts) holds; the connector uses
whichever does, and logs once when the venue contradicts §2.3. Without fills
it reads back what §2.3 documents for the request — contracts.

## 4. Out of scope

- The classic delivery contracts' own behaviour, which is unchanged.
- Price and candle streams for `_CM` symbols (websocket-connector; the v3
  public client added for Reality tokens already carries `kline`).
- Funding-rate history for the perpetuals, which is a v2 read and answers
  these symbols with nothing. It feeds statistics, not trading.
- Verification against a live unified account, which §3.4 is designed to
  survive but not replace.
