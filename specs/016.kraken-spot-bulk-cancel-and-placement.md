# 016 — Kraken spot order operations are paced by the REST bucket, one order at a time

Design note. Kraken spot has bulk endpoints for both cancel and placement; the
connector had no way to reach them, so every order operation cost two calls out
of a budget that refills twice a second.

## §1 Definition

Kraken meters private REST per API key: a counter of **20** that decays at
**0.5/s** on the Intermediate tier
(<https://docs.kraken.com/api/docs/guides/spot-rest-ratelimits>). Every call
costs **+1**, whatever it carries.

### §1.1 What one order costs today

- **Cancel** — `cancelOrder({symbol, newClientOrderId})` resolves the venue txid
  with a `QueryOrders` read and then sends `CancelOrder`: **2 tokens**.
  The pre-flight read is deliberate (spec 013: the reply is `{count}` and
  nothing else, so the order has to be read to be reported).
- **Placement** — `AddOrder`, then a `QueryOrders` re-read so the answer is the
  real order rather than a submit acknowledgement: **2 tokens**.

So a group of N orders costs **2N tokens against a bucket of 20 refilling at
0.5/s**. The first few go out at once, then the bucket empties and the rest are
paced at one call per two seconds — 4 s per order, entirely local pacing, with
the venue never having refused anything. Spec 012 measured this shape and named
the bulk endpoints as the only real fix (§4.2 there).

### §1.2 What the venue offers instead

| endpoint | limits | reply |
|---|---|---|
| `CancelOrderBatch` | max 50 unique ids | `{count}` |
| `AddOrderBatch` | 2..15 orders, ONE pair | `{orders: [{txid?, error?, descr?}]}`, positionally aligned |

Both cost **one** REST token. `AddOrderBatch` validates the whole batch before
submitting any of it, so a validation rejection places nothing.

The matching-engine counter (per pair per account, threshold 125, decay 2.34/s,
<https://docs.kraken.com/api/docs/guides/spot-ratelimits>) is charged per ORDER:
`+1` per added order, and for a cancel a penalty scaled by how long the order
has rested — `< 5s` +8, `< 10s` +6, `< 15s` +5, `< 45s` +4, `< 90s` +2,
`< 300s` +1, and **0** from 300 s.

## §2 What makes this different from `getOrdersBatch`

Spec-wise this is the same move as the batch lookup already in the connector
(`POST /orders/batch`): a venue-native multi-id call, declining everywhere else,
with the caller's per-order path left exactly as it is for anything not
answered. Two things make cancel and placement harder than a lookup.

### §2.1 A bulk cancel reply describes nothing

`CancelOrderBatch` answers `{count}`. It does not say WHICH ids it cancelled, so
a count that disagrees with what was sent leaves the caller holding an answer it
cannot attribute. Inventing an attribution is the defect spec 013 exists to
stop.

### §2.2 A bulk placement cannot be retried

A rejected batch placed nothing; a batch whose RESPONSE was lost may have placed
everything. From the connector those two are the same event, and the recovery
for the first (send it again) is a duplicate live order under the second.

### §2.3 The limiter cannot admit a bulk cancel at all

`addOrderCall` admits a call when `counter + cost <= threshold`. A batch cancel
of 46 fresh orders costs 46 x 8 = 368 against a threshold of 125, so that test
is false at every counter value: no amount of waiting makes it true, and
`checkLimits`' bounded re-ask loop would simply give up on every attempt.
Kraken itself does not work that way — it ACCEPTS the batch and lets the counter
overshoot, which delays what comes next.

## §3 Behaviour

### §3.1 `POST /orders/cancelBatch` → `BaseReturn<CommonOrder[]>`

Request `{symbol, newClientOrderIds}` (for Kraken these are venue txids, which
is what main-app addresses Kraken spot orders by).

The answer lists **only the orders this call observed as cancelled**, each a
real order with `orderId` = txid and `status: 'CANCELED'`. Anything absent means
"I did not cancel this / cannot vouch for it" and the caller runs its normal
per-order cancel for it — which is safe, because cancelling an already-cancelled
order goes down the existing unknown-order path.

Per chunk of at most 50:

1. ONE `QueryOrders` for the chunk. This is both the `lastSeen` each reported
   order is described by and the filter for what is worth sending: rows the
   venue reports as `open`/`pending` are cancellable, and rows that are already
   `closed`/`canceled`/`expired` — or that the venue does not answer about at
   all — are left out and never sent. Their semantics (a fill that raced the
   cancel, an id the venue no longer knows) belong to the per-order path, which
   has the unknown-order ladder for exactly that.
2. Fewer than two left: leave the chunk to the per-order path. One order in a
   batch costs the same two calls as the ordinary path and skips its handling.
3. Charge the matching-engine cost the venue will actually charge — the summed
   age-scaled costs from §1.2, read from each row's `opentm`. A row with no
   `opentm` is charged the worst case, never nothing.
4. ONE `CancelOrderBatch`.
5. `count === sent`: report every id sent, described by the row read moments
   earlier, with `status: 'CANCELED'`. Never promoted to `FILLED` even when the
   row carries fills — that is the engine's decision (spec 013 §3).
6. Anything else — a count that disagrees, an error, a thrown transport failure:
   re-read the chunk and report ONLY rows the venue now calls `canceled`,
   converted from that FRESH read so a fill that landed in the race carries its
   real executed quantity. If the re-read cannot answer either, the chunk
   contributes nothing. One bad chunk never throws: chunks already resolved are
   still an answer.

Nothing observed at all → decline, and the caller loops as today.

### §3.2 `POST /orders/openBatch` → `BaseReturn<BatchOpenResult[]>`

Request `{symbol, orders}` — LIMIT only, 2..15, one symbol, every item carrying
a `newClientOrderId`. Anything else is declined, and **a decline sends nothing**.

```ts
type BatchOpenResult = {
  newClientOrderId: string
  order?: CommonOrder   // placed
  reason?: string       // THIS order was definitively refused, venue's own text
}
```

- One `AddOrderBatch`, built field for field the way the single `openOrder` spot
  path builds one — including `cl_ord_id`, which replaces `userref` rather than
  accompanying it (they are mutually exclusive).
- A bulk cancel that cancelled NOTHING — every order had already filled, or only
  one was still resting — answers `notok` with `Batch cancel confirmed no orders`,
  never the base class's "not supported". A caller is entitled to remember "not
  supported" for the life of its process; this is a statement about those
  orders, not about the venue, and it happens routinely.
- **No retry of the send** (§2.2), and no routing of its failure through
  `handleKrakenErrors`, which re-invokes the method it wraps. A whole-batch
  failure is `notok` with Kraken's own wording passed through UNCHANGED,
  because that text is what the caller classifies on: a timeout is ambiguous, a
  validation rejection is definitive. A failure Kraken did NOT word — a dropped
  socket, a bare `Request failed with status code 502` — and Kraken's
  `EGeneral:Internal error` are prefixed `Server error, batch outcome unknown:`.
  Those shapes are worded by the HTTP stack, the caller's classifier cannot be
  relied on to know them all, and reading one as a refusal re-sends up to
  fifteen orders that may already be live.
- On success: items with an `error` carry it through as that order's `reason`.
  Items with a txid are re-read with ONE `QueryOrders` after a short pause,
  retried a few times for whatever is still missing — the same lag the single
  path already handles.
- A txid still missing after the retries is reported as the order that was SENT,
  plus the txid: status NEW, nothing executed, the sent price/quantity/side.
  This is not an invented order — Kraken issued that txid for that request, so
  the order is live, and reporting it absent would make the caller place it
  again. The reconcile pass corrects a stale field; it cannot undo a duplicate.

### §3.3 The limiter

`addOrderBatchCall(pair, type, engineCost, accountKey)` keeps `addOrderCall`'s
atomicity exactly — one mutex key per account, probe both budgets, commit both
or neither, no `await` in between (spec 012) — and differs only where Kraken
differs:

- REST is charged **once** per batch, whatever it carries.
- The matching-engine cost is supplied by the caller: orders in the batch for an
  add, the summed age-scaled cancel costs for a cancel.
- An `add` is admitted on the ordinary predicted-counter check (15 orders at +1
  against a threshold of 125 always fits eventually). A `cancel` is admitted
  whenever the counter is currently BELOW the threshold and is then charged in
  full — the counter may overshoot, which correctly delays the following calls
  on that pair, exactly as Kraken's own counter does (§2.3).

## §4 The wire format

The connector signs and sends Kraken spot requests through its own
`kraken-custom/SpotClient`, whose `serializeParams` flattens arrays into
repeated `key=value` pairs — a form encoding that cannot express an array of
orders at all. That serializer is **not** what carries these calls: on the spot
client a POST is signed over `nonce + JSON.stringify(body)` and SENT as that
same JSON object with `Content-Type: application/json`, so the nested `orders`
array goes out as JSON and the signature (HMAC-SHA512 over
`URI path + SHA256(nonce + body)`, Kraken's documented scheme) covers every
field of every order. `batch-body.spec.ts` pins both halves by recomputing the
signature from the bytes the client actually sent.

## §5 Out of scope

- **Every other venue, and Kraken Futures.** They decline, and their orders stay
  on the per-order path. Kraken Futures has a `batchOrder` envelope, but it is a
  different contract (send + cancel + edit together, its own per-element status
  shape) and its cancel path already reports a real outcome.
- **Client-order-id addressing.** `CancelOrderBatch` also accepts `cl_ord_ids`,
  but a Gainium client order id resolves ambiguously on this venue (see
  `getOrder`), and a bulk call is the worst place to resolve an ambiguity.
  Only txids are batched; anything else is absent from the answer.
- **The single-order paths.** `cancelOrder`'s pre-flight read and `openOrder`'s
  re-read are unchanged, and remain what runs for everything not batched.
- **MARKET orders**, which fill immediately and whose caller needs a price the
  batch reply does not carry.
