# 017 — Bitget candles: 3m, 2h and 8h are served at a different bar width,
# silently, on every Bitget line

Bug #913. Found while investigating #890. A Bitget bot whose indicator is
configured at `8h` has its indicator computed on **6-hour** bars; `2h` computes
on 1-hour bars and `3m` on 1-minute bars. Nothing fails, so nothing is
reported: the caller receives `status: OK` and a candle array, just not at the
width it asked for.

## 1. Definition

### 1.1 — expected

`BitgetExchange.spot_getCandles(...)` and `BitgetExchange.futures_getCandles(...)`
return candles whose bar width is the `interval` the caller asked for, for
every value of `ExchangeIntervals`, on all three Bitget product lines the
connector serves (classic v2 spot, classic v2 USDT/USDC futures, unified v3
inverse futures).

### 1.2 — actual

| interval | v2 futures | v2 spot | v3 inverse |
|---|---|---|---|
| `3m` | 1-minute bars | 1-minute bars | correct |
| `2h` | 1-hour bars | 1-hour bars | correct |
| `8h` | 6-hour bars | 6-hour bars | 6-hour bars |

Each returns `status: OK`. The bars carry the venue's own timestamps, so they
are not even aligned to the requested width — an "8h" series opens at
02:00/08:00/14:00/20:00 UTC.

### 1.3 — expected

A caller asking for a width the venue has no granularity for is served it by
merging the finest granularity that divides it, as the Reality-token path in
`spot_getCandles` already does.

### 1.4 — actual

Only the Reality-token path does that. Every other symbol on the classic line
falls through to `convertInterval`, which substitutes a *different* width and
returns it unlabelled.

### 1.5 — expected

The page budget in `futures_getCandles` advances by the width of the bars the
venue is actually sending.

### 1.6 — actual

It steps `from`/`to` by `timeIntervalMap[interval]` — the *requested* width —
while the venue serves the substituted one. At `8h` a 200-row page covers
200 × 6h = 1200h but the cursor advances 200 × 8h = 1600h, so a long window
comes back with a 400-hour hole every page.

## 2. Evidence

### 2.1 — the venue's own accepted set (measured 2026-09-22, public, no auth)

Bitget answers an unsupported granularity with `400171` and *names* the set it
accepts:

```
GET /api/v2/mix/market/history-candles?symbol=BTCUSDT&productType=USDT-FUTURES&granularity=8H
  -> 400171 "... should be [1m,3m,5m,15m,30m,1H,4H,6H,12H,1D,1W,1M,6Hutc,12Hutc,1Dutc,3Dutc,1Wutc,1Mutc]"
GET /api/v2/spot/market/candles?symbol=BTCUSDT&granularity=8h
  -> 400171 "... should be [1min,3min,5min,15min,30min,1h,4h,6h,12h,1day,1week,1M,6Hutc,...]"
GET /api/v3/market/candles?category=COIN-FUTURES&symbol=BTCUSD_CM&interval=8H
  -> 40020  "Parameter 8H error"
```

So `8h` exists on no Bitget line. But `3m` and `2H` do:

```
v2 futures  granularity=3m   -> 00000, bar spacing 3m    (USDT-FUTURES and USDC-FUTURES, 60d back)
v2 futures  granularity=2H   -> 00000, bar spacing 2h    (both product types, 60d back)
v2 spot     granularity=3min -> 00000, bar spacing 3m    (recent and history endpoints)
v2 spot     granularity=2h   -> 400171 (no 2h on spot)
v3 inverse  interval=3m / 2H -> 00000, correct spacing
```

`3min` is accepted by the live spot endpoint and named in its own error text,
but is **absent from the `bitget-api` SDK's `SpotKlineInterval` union**, which
still carries the v1 documentation's set.

### 2.2 — the real code path, driven against the live venue

`tmp-repro/bitget913.ts` constructs the real `BitgetExchange` (no keys — candles
are public), stubs only the rate limiter, and asks each reader for 20 bars:

```
FUTURES(usdm) 8h: asked width 8h  | 27 bars | distinct deltas(h)=6     | aligned to 8h? false
FUTURES(usdm) 2h: asked width 2h  | 40 bars | distinct deltas(h)=1     | aligned to 2h? false
FUTURES(usdm) 3m: asked width 3m  | 60 bars | distinct deltas(m)=1     | aligned to 3m? false
FUTURES(usdm) 4h: asked width 4h  | 20 bars | distinct deltas(h)=4     | aligned to 4h? true
SPOT          8h: asked width 8h  | 27 bars | distinct deltas(h)=6     | aligned to 8h? false
SPOT          2h: asked width 2h  | 40 bars | distinct deltas(h)=1     | aligned to 2h? false
SPOT          3m: asked width 3m  | 60 bars | distinct deltas(m)=1     | aligned to 3m? false
COINM         8h: asked width 8h  | 27 bars | distinct deltas(h)=6     | aligned to 8h? false
COINM         2h/3m/4h: correct
```

### 2.3 — the substitutions in code

`convertInterval` (`index.ts:1578`) maps `8h`→`6Hutc`, `2h`→`1H`/`1h`,
`3m`→`1m`/`1min`; `coinmGranularity` (`index.ts:1721`) maps `8h`→`6Hutc`.
Both are consumed as the `granularity` of the candle request and neither result
is ever reconciled with the width asked for.

`spot_getCandles` aggregates back to the requested width **only** when
`isRealitySymbol(symbol)` is true (`index.ts:3117`); `BTCUSDT` is not a Reality
token, so it takes the `convertInterval` branch below it.

### 2.4 — no downstream guard catches it

main-app's `filterIndicatorIntervalsByExchange` has no Bitget branch, so an
indicator at any interval passes its check. Nothing else compares a returned
bar's width to the requested one, in this connector or in its callers — the
substitution has no observable trace anywhere.

## 3. Assumption

The root cause is that `convertInterval`/`coinmGranularity` treat "the closest
granularity Bitget has" as an acceptable answer to "the granularity the caller
asked for". Two of the three substitutions are not even necessary — the venue
has a native `3m` on every line and a native `2H` on both futures lines — and
the one that is necessary (`8h`, which no line has) needs the same
merge-the-finer-bars treatment the Reality path already performs.

Correcting `convertInterval` to the native granularities, and routing the
remainder (`8h` everywhere, `2h` on spot) through the existing
`aggregateCandles` by recursing at the base interval, fixes the width, the
alignment and §1.6's page budget at once — the recursion prices its own pages
at the width actually being served.

## 4. Non-goals

- The downstream guard in main-app. Fixing the connector makes these intervals
  genuinely servable on Bitget, so a guard that refused them would be wrong.
  (main-app's `krakenSupported` list, written 2026-03-02, already refuses the
  `3m`/`2h`/`8h` that spec 005 taught the Kraken connector to serve on
  2026-09-08 — the same mistake, one exchange earlier.)
- Bitget's quarterly inverse *delivery* contracts, which stay on the classic
  v2 COIN-FUTURES endpoint the venue has withdrawn (§2.1).
- Weekly/daily alignment, which `1Wutc`/`1Dutc` already handle natively.
