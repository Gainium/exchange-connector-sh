# 018 — A spec's virtual clock leaks into every spec file that loads before it

Bug spec. The subject is the **test suite's own correctness**, not any
runtime behaviour: nothing a user can observe changes. What changes is
whether "the suite is green" means anything for the 23 spec files that
were being exercised against a clock four months in the future.

---

## §1 Definition

### §1.1 Expected

`Date.now()` inside a spec reads the real wall clock, unless the spec
currently running deliberately installed a virtual one for itself.

A spec that wants a virtual clock — and `limit.ts`'s decay genuinely
needs one, so the Kraken limiter specs can exercise minutes of token
decay without sleeping — owns that clock for the duration of **its own
suite only**. Installing it and handing it back are symmetric: the
install happens in a hook of the outermost `describe` that needs it,
and the restore happens in the matching `after()` of that same
`describe`.

### §1.2 Actual

`core/src/exchange/exchanges/kraken/order-call-atomicity.spec.ts`
installs its virtual clock at **module load time** (lines 31-33) and
restores it inside a `before()` of the file's **last** `describe`
(line 269):

```ts
let VNOW = 1_800_000_000_000          // 2027-01-15
const realDateNow = Date.now
;(Date as any).now = () => VNOW       // ← at module load
```

Mocha loads every spec file before running any test. From that load
onwards — i.e. for the whole run up to that nested `before()` — the
global `Date.now` is the virtual one, pinned at `1_800_000_000_000`
(2027-01-15), roughly four months ahead of today.

Every spec file that sorts at or before
`kraken/order-call-atomicity.spec.ts` therefore runs on the future
clock. That is not a small tail: it is **23 of the 41 spec files**,
including all of `binance-custom/`, `binance/`, `bitget/`, `bybit/`,
`coinbase/`, `hyperliquid/` and the first eight `kraken/` files.

### §1.3 Why it matters even though no user sees it

Any spec whose subject reads `Date.now()` — candle lookback floors,
rate limiters, order-age pricing, cache TTLs, expiry checks — is
silently exercised four months out, and *which* specs those are is
decided by filename sort order. A fix "verified" under that clock was
not verified against today. It has already cost one investigation
(#913), where a correct new spec failed under `npm test` while passing
in isolation — the shape that gets a real fix mistrusted or a wrong one
accepted.

## §2 Evidence

Observed, not inferred. A mocha root-hook plugin (kept outside the
repo) records the date `Date.now()` reads as during each test and
attributes it to the spec file that was running:

```
$ npx mocha -r ts-node/register --require /tmp/clock-probe.js \
    --extension ts 'src/**/*.spec.ts'
782 passing (41s)

===== CLOCK PROBE (Date.now() as seen by each spec file) =====
real today = 2026-09-22
SKEWED  src/binance-custom/losslessOrderId.e2e.spec.ts            -> 2027-01-15
SKEWED  src/exchange/exchanges/bitget/candle-intervals.spec.ts    -> 2027-01-15
…
SKEWED  src/exchange/exchanges/kraken/batch-limit.spec.ts         -> 2027-01-15
SKEWED  src/exchange/exchanges/kraken/order-call-atomicity.spec.ts-> 2026-09-22, 2027-01-15
   ok   src/exchange/exchanges/kraken/outage-backoff.spec.ts      -> 2026-09-22
   …
===== 23 file(s) running on a skewed clock =====
```

The boundary falls exactly at `order-call-atomicity.spec.ts` — the
file's own last `describe` is where the clock is handed back, so it is
the only file that sees both dates. That is the signature of a
module-load install with a late restore, and it identifies the culprit
without ambiguity.

The original report additionally names the setter stack:

```
!!! Date.now REPLACED at
    at Object.<anonymous> (…/kraken/order-call-atomicity.spec.ts:33:19)
```

### §2.1 A second victim: the sibling limiter spec's restore is a no-op

`kraken/batch-limit.spec.ts` does scope its clock correctly — top-level
`before()`/`after()`, anchored on `Date.now()` (lines 92-111). But
because it sorts *before* `order-call-atomicity.spec.ts` and the latter
patched at load, the `previousDateNow` it captures is **already the
virtual function**. Its careful restore therefore hands back the fake,
and the probe above reports it SKEWED. A correct spec is made incorrect
by the other file's leak.

---

## §3 Assumption (hypothesis, not fact)

The only cause is **when** the clock is installed and removed, not
*that* it is installed. Moving the install into a top-level `before()`
of the file's outermost `describe`, and the restore into the matching
`after()`, confines the virtual clock to that file's own suite and
leaves every other file on the real clock.

Confirmation: after the change the probe must report **0 skewed
files**, with `order-call-atomicity.spec.ts` itself reading the
virtual date and every other file reading today's.

---

## §4 Constraints the fix must respect

### §4.1 The atomicity spec keeps its virtual clock and keeps passing

Spec 012 (shipped with `eadf1c7`) deliberately avoids wall-clock
sleeping: `limit.ts` reads `Date.now()` for decay and the spec
advances `VNOW` instead of sleeping. Every one of its assertions must
still hold. This change alters *when* the clock is installed and
removed, nothing else.

### §4.2 No production behaviour changes

`limit.ts` and `index.ts` are not touched. The Kraken rate-limit and
order-call behaviour that shipped with `eadf1c7` is untouched.

### §4.3 The anchor must stay ahead of what earlier specs left behind

`limit.ts` is a process-wide singleton shared by
`batch-limit.spec.ts`, `order-call-atomicity.spec.ts` and
`rate-limit.spec.ts`, and its decay only ever runs **forward**:

```ts
const elapsedSeconds = (now - s.lastRestTime) / 1000
if (elapsedSeconds > 0) { …decay…; s.lastRestTime = now }
```

A backwards clock jump does not corrupt a counter — it **freezes** it,
because neither the decay nor the timestamp update runs. So a spec
that starts its virtual clock *behind* where an earlier spec left the
limiter's timestamps would find buckets that never refill.

`batch-limit.spec.ts` runs first (it sorts earlier) and, measured in
isolation, leaves the shared limiter's timestamps about **58.5 minutes**
ahead of real `Date.now()`. The atomicity spec's anchor must clear that
with a wide margin. Its own header already treats "advance an hour" as
the unit that drains every bucket, so the margin is expressed in the
same terms.

This is what makes the absolute `1_800_000_000_000` un-keepable, quite
apart from the leak: a fixed 2027 constant is only "ahead" by accident
of today's date, and a spec pinned to an absolute instant silently
becomes a spec pinned to the past.

### §4.4 Nothing downstream reads the limiter's counters

`rate-limit.spec.ts` is the only spec sorting after the atomicity file
that imports `limit.ts`, and it only stubs `noteRateLimited` — it never
reads a counter and never depends on decay. Handing the real clock
back mid-run is therefore safe for it. Draining the counters on the way
out (as `batch-limit.spec.ts` already does) keeps that true for any
spec added later.
