# 019 — Bitget futures candles come back empty at `1d` and `1w` over any
# window wider than the venue's ~90-day window-span cap

Bug #914. Found while fixing #913 (Bitget candle granularity) and confirmed
independent of it. Any Bitget **futures** read at daily or weekly bars over
more than ~90 days returns nothing at all: chart history, server-side and
client-side backtests, market-archive backfill, and a daily/weekly indicator's
warm-up. It fails silently as far as the user is concerned — the caller gets
`NOTOK` with a bare message, and a backtest reads an empty series as the end of
history (the shape of bug #245).

## 1. Definition

### 1.1 — expected

`BitgetExchange.futures_getCandles(symbol, interval, from, to)` returns the
candles of `interval` covering `[from, to]`, for every interval, over a window
of any width — the full history restored by bug #225.

### 1.2 — actual

At `1d` and `1w` over a window wider than ~90 days it returns
`status: NOTOK`, `reason: "parameter verification failed starttime || endtime"`
and no candles at all. Measured through the real code path against the live
venue, 2026-09-23, BTCUSDT / USDT-FUTURES, window = 730 days:

```
1d  status=NOTOK bars=0
1w  status=NOTOK bars=0
4h  status=OK    bars=4360
8h  status=OK    bars=2190
```

### 1.3 — expected

A page asked of `/api/v2/mix/market/history-candles` satisfies **both** of the
venue's limits: at most 200 rows **and** at most the window-span cap in §2.1.

### 1.4 — actual

A page is sized by row count alone — `to = from + 200 × interval`. That is
inside the span cap for every interval up to `4h` (200 × 4h = 33 days) and
outside it at `1d` (200 days) and `1w` (1400 days), so at those two intervals
*every* page is refused and the whole call fails.

### 1.5 — expected

`1h`, `4h` and `8h` are unaffected by the change: same pages, same series.

### 1.6 — actual (pre-fix, and the behaviour to preserve)

The loop runs `ceil(candlesSize / 200)` pages, each 200 rows wide, and the last
one is allowed to run past the requested `to`. That overhang is load-bearing:
the venue only serves bars that **close** inside `[startTime, endTime]`, so
without it the bar the requested end falls inside — the in-progress candle of a
live read — is dropped.

## 2. Evidence

### 2.1 — the venue's window-span cap (measured 2026-09-23, public, no auth)

`/api/v2/mix/market/history-candles` refuses a window wider than ~90 days with
`40017 "Parameter verification failed startTime || endTime"`, whatever the
granularity, and whether the window ends now or entirely in the past:

```
granularity=1H     span=90d -> 00000 (200 rows)   span=91d -> 40017
granularity=4H     span=90d -> 00000 (200 rows)   span=91d -> 40017
granularity=1Dutc  span=90d -> 00000 (90 rows)    span=91d -> 40017
granularity=1Wutc  span=90d -> 00000 (13 rows)    span=91d -> 40017
1Dutc, window ending 400d ago:  90d -> 00000 (90)  91d -> 40017
```

Bisected, the boundary sits at ~90.27 days and is identical at `1H`, `4H`,
`1Dutc` and `1Wutc`. It is a span limit, not a retention floor: a 90-day window
400 days in the past is served in full. An `endTime` up to 89 days in the
future is accepted, so an overhanging final page is fine.

The rows are half-open and close-inclusive: asking `[t, t + 200 × 4h)` returns
200 rows, the first at exactly `t` and the last at `t + 199 × 4h`.

### 2.2 — the in-code comment asserting the opposite

`src/exchange/exchanges/bitget/index.ts:1667-1672` said the ~90-day window
"belongs to the other endpoint, `/mix/market/candles`, which we do not call
here… there is no date floor to apply". The first half is true (there is no
retention floor) and was the point of #225; the conclusion drawn from it — that
this endpoint imposes no window constraint at all — is false, per §2.1.

### 2.3 — the origin

`git blame` puts the comment and the page-count bound on `124f6580`
(2026-07-31), the fix for **bug #225** — "futures_getCandles clamped the
request start to 89 days ago". Before it, `from` was clamped to 89 days ago, so
the window was never wider than 89 days and the cap was never reached: at `1d`
`candlesSize` came to 89, under the 200-row page, so `to` was left alone. The
#225 fix correctly removed that clamp to restore full history, and doing so
exposed the span cap at the two intervals whose 200-row page is wider than it.
A regression of #225, and the fix must satisfy both: page around the cap
**without** reinstating any floor on `from`.

## 3. Assumption

The root cause is that the page budget is expressed in bars only. Bounding a
page by `min(200 bars, span cap)` — and driving the loop off the window's own
advance rather than off a bar count, since span-limited pages carry fewer bars
than the bar-count arithmetic assumes — makes `1d` and `1w` serve the whole
window, with no floor on `from` and no change to `4h` and below.
