# 020 — A Bitget candle merge that yields ONE bucket keeps the truncated
# leading bar and serves it as a whole candle

Bug #917. Found verifying #913 (spec 017) in production, and **caused by**
that fix rather than by rolling it back: #913 made `aggregateCandles` the
path every Bitget `8h` read (and every spot `2h` read) now goes through, so a
defect that used to be reachable only by Reality tokens became load-bearing
for the whole venue. Native intervals are unaffected.

A bar built from only the second half of its bucket is stamped at the
bucket's START and returned as if it were complete. Its `open`, `high` and
`low` are wrong; `close` happens to be right. Nothing downstream can tell —
there is no error, no flag, and the shape is indistinguishable from a good
bar. When such a bar reaches `market-archive` it is written to ClickHouse and
never revisited, because gap detection only looks for rows that are *absent*
(`market-archive src/backfill/backfiller.ts`, `store/candleFilter.ts`).

## 1. Definition

### 1.1 — expected

`aggregateCandles(candles, stepMs)` returns only buckets it has the WHOLE of
at the front. A range that starts part-way into its first bucket yields a
first bar without its open/high/low, which is wrong data rather than late
data, so that bucket is dropped — exactly as the sibling helper written for
bug #709 does (`core/src/exchange/exchanges/kraken/candles.ts:221`, `if
(out.length && candles[0].time !== out[0].time) out.shift()`), and exactly as
the commit that introduced this function said it did ("a partial leading
bucket is dropped", `2a96a74`). A TRAILING partial bucket is still kept: that
is the live in-progress bar every connector already returns as its last
candle.

Dropping the only bucket leaves an empty result. That is the correct answer —
"I have no whole bar for you in this window" — and callers must read it as a
gap still to fill, never as a window that has been covered.

### 1.2 — actual

The guard is `result.length > 1 && …`, so it cannot fire when the merge
produced exactly one bucket. A window that starts mid-bucket AND spans only
one bucket returns the truncated bar, presented as whole.

Measured through the real code path (`core/src/exchange/exchanges/bitget/uta.ts`),
no network:

```
window starts mid-bucket, ONE 4h bar  -> [{"time":1790064000000,"open":"200","high":"210","low":"190","close":"205","volume":"1"}]
window covers whole bucket, TWO bars  -> [{"time":1790064000000,"open":"100","high":"210","low":"90","close":"205","volume":"2"}]
multi-bucket, leading partial         -> leading bucket correctly dropped
```

Both are stamped `2026-09-22T08:00:00Z`. The first opens at 200 — the price
four hours into the bar — while the bucket really opens at 100.

## 2. Evidence

### 2.1 — the live venue, through the real connector

`BitgetExchange.futures_getCandles('BTCUSDT', 8h, from, to)` against the live
Bitget API, 2026-09-22, around the `2026-09-22T08:00Z` bucket:

```
[07:59:59.999, 16:00:00.001]  (whole bucket)  -> 08:00  o=85327.9  h=86688  l=85300  c=86361   correct
[12:00:00.000, 16:00:00.000]  (starts mid-bucket, one bucket)
                                              -> 08:00  o=85956.5  h=86688  l=85411  c=86361   WRONG
```

The venue's own `4h` bars for that bucket are `08:00 o=85327.9 l=85300` and
`12:00 o=85956.5 l=85411`. The wrong bar's open and low are the **12:00 4h
bar's** open and low — only the second half of the bucket went into it.

### 2.2 — production, serving exactly that bar

`GET https://api.gainium.io/candles?exchange=bitgetUsdm&type=8h&symbol=BTCUSDT`
returns, for the same bucket, `o=85956.5 h=86688 l=85411 c=86361` — identical
to the truncated bar in §2.1, six hours after the bucket closed and still
uncorrected. The bar is also internally impossible: every other pair of
consecutive 8h bars in the response satisfies `open[n] === close[n-1]`, and
this one does not (`close` of the 00:00 bar is 85327.9, the 08:00 bar opens
at 85956.5).

The same request over a window the archive holds no row for falls through to
the exchange and comes back correct (`o=85327.9`), which places the wrong
value in the stored row rather than in the live read.

### 2.3 — the caller that hands it a mid-bucket window, in production

`market-archive src/backfill/backfiller.ts` drives a gap with
`cursor = gap.from` and asks for `[cursor - 1, gap.to + 1]`, advancing
`cursor` by one bar each round. On the **last** round of every gap
`cursor === gap.to`, so the window is 2 ms wide and sits exactly on the gap's
final bucket boundary. Bitget's `history-candles` answers a window by the bars
that CLOSED inside it, so a 2 ms window at `16:00` returns the `12:00` 4h bar —
the second half of the `08:00` bucket, and nothing else.

Measured through the real code path against the live venue, the same window
before and after the change:

```
[2026-09-22T15:59:59.999Z, 2026-09-22T16:00:00.001Z]
  result.length > 1  ->  08:00  o=85956.5 h=86688 l=85411 c=86361   (the archived bar)
  result.length      ->  (empty)
```

That bar then clears both of the backfiller's filters — `isInRequestedGap`
(08:00 is inside the gap) and `filterClosedCandles` (the 08:00 bucket closed at
16:00) — so it is written, and `ReplacingMergeTree` **overwrites the correct
row the earlier round of the same gap had just written**. This is why the
corruption is always the newest bar, always one per gap fill, and lands on the
same bucket for every symbol swept together.

### 2.4 — scope

Only the widths Bitget has no granularity for and that are therefore merged:
`8h` on every product line, and `2h` on spot (`bitgetBaseInterval`). Native
intervals never call `aggregateCandles`. `bitgetUsdm 4h`, `1h` and `binance
8h` cross-check against their venues with no mismatch.

## 3. Assumption

The root cause is the `> 1` in the leading-partial guard, and nothing else:
the bucketing, the stamping and the OHLCV merge are all correct, and the
multi-bucket case already drops the truncated bar. Replacing `result.length >
1` with `result.length` makes the single-bucket case behave like every other
case and like the Kraken sibling.

Deliberately NOT changed here: the backfiller's 2 ms final-iteration window
(§2.3). Asking a venue for a 2 ms slice and getting the previous bar back is
its own defect, in `market-archive`'s window arithmetic and in another repo —
but it is not what makes the answer wrong. The connector must not answer ANY
window with a bar that lies about what it contains, and once it stops doing
so, that window simply yields nothing and the correct row already written for
that bucket stands.

## 4. Out of scope

- The #913 behaviour this sits on: an `8h` request is still read at `4h` and
  merged into real 8-hour bars, never substituted with a `6h` one. Untouched.
- Native intervals. Untouched.
- The wrong rows already in ClickHouse. Gap detection skips a row that is
  present, so they will not self-correct; they need a one-off re-backfill,
  which is an operator action against production and not part of this change.
