# 021 — Bitget candle pages lose the first bar of every page but the first,
# because the cursor advances past the end of the page it just read

Bug #918. Found while fixing #914 (Bitget futures window-span cap) and
confirmed independent of it — spec 019's plan records it as deliberately left
undone there. Every Bitget candle read whose range spans more than one page
comes back with holes in it: chart history, server-side and client-side
backtests, market-archive backfill, and any indicator's warm-up. It is silent —
`status: OK`, no error, a plausible-looking series — and at the widths that are
read at a narrower base and merged (futures `8h`; spot `2h`, `3m`, `1w`) there
is no hole to see at all, only a bar whose OHLC and volume are wrong.

## 1. Definition

### 1.1 — expected

`futures_getCandles(symbol, interval, from, to)` and
`spot_getCandles(symbol, interval, from, to)` return **every** bar of `interval`
that opens in `[from, to)`, contiguously, however many venue pages the window
takes.

### 1.2 — actual

One bar is dropped at every page boundary (two across the spot historic→recent
switch). Measured through the real code path against the live venue,
2026-09-23, BTCUSDT, at `origin/main`:

```
FUTURES (USDT-FUTURES)
  4h over 730d : OK  4360 bars   4380 exist   gaps=[1x, 2x]   20 holes
  8h over 730d : OK  2190 bars   2190 exist   gaps=[1x]        0 holes  <- see §1.4
  1d over 730d : OK   723 bars    730 exist   gaps=[1x, 2x]    7 holes
  1w over 730d : OK   100 bars    104 exist   gaps=[1x, 2x]    5 holes
  1h over  30d : OK   718 bars    720 exist   gaps=[1x, 2x]    2 holes

SPOT
  1h over  60d : OK  1438 bars   1440 exist   gaps=[1x, 2x, 3x]   3 holes
  4h over 730d : OK  4364 bars   4380 exist   gaps=[1x, 2x, 3x]  17 holes
  2h over 200d : OK  2400 bars   2400 exist   gaps=[1x, 2x]       1 hole   <- see §1.4
  1d over 730d : OK   727 bars    730 exist   gaps=[1x, 2x, 3x]   4 holes
```

The missing opens sit exactly one page apart. Futures `4h`: the first five are
`2024-10-26T04:00`, `2024-11-28T16:00`, `2025-01-01T04:00`, `2025-02-03T16:00`,
`2025-03-09T04:00` — 33.33 days apart, which is `200 × 4h`, the page width.
Futures `1d`/`1w`: 90 days apart, which is the §019 span cap.

### 1.3 — expected

The relative damage must not scale with how many boundaries a range crosses.

### 1.4 — actual, and why it is worse than a hole

A merged width is read at its base interval and aggregated, so a bar missing
from the base does not leave a gap in the merged series — it silently changes
that merged bar's open/high/low/close and volume instead. Futures `8h` above
reports `0 holes` over a window whose `4h` base is missing 20 bars: 20 of those
2190 `8h` bars are simply wrong. Same for spot `2h` and `3m`, and for `1w`,
which is read at `1d`.

### 1.5 — expected

A fix changes which windows are asked for, and nothing else: the futures
overhang past the requested end (spec 019 §1.6) still carries the in-progress
candle, the `8h`→`4h` merge of #913 still merges, and the §019 span cap is still
respected at every granularity.

## 2. Evidence

### 2.1 — the three endpoints' window semantics (measured live 2026-09-23, public, no auth)

They do not agree with each other, and none of them agrees with the cursor:

| endpoint | window | first open served | last open served |
|---|---|---|---|
| `/api/v2/mix/market/history-candles` | `[start, end)` | `start` | `end − width` |
| `/api/v2/spot/market/history-candles` | `(…, end)`, `end`-only | (200 bars back) | `end − width` |
| `/api/v2/spot/market/candles` | `(start, end]` | `start + width` | `end` |

```
mix/history-candles  BTCUSDT 4H  start=1787227200000 end=1790107200000 (200 bars)
  -> rows 200  first 1787227200000 (== start)  last 1790092800000 (== end − 4h)

spot/candles         BTCUSDT 4h  window of 10 bars, limit 1000
  -> rows 10   first == start + 4h   last == end
spot/candles         BTCUSDT 4h  window of 100 bars, limit 1000
  -> rows 100  first == start + 4h   last == end

spot/history-candles BTCUSDT 4h  endTime=end, limit 200
  -> rows 200  last == end − 4h
```

The spot pair being opposite at `endTime` is what makes the spot loss two bars
rather than one at the single historic→recent switch inside a long range — the
`3x` gaps in §1.2.

### 2.2 — the cursor

`src/exchange/exchanges/bitget/index.ts`, `futures_getCandles` at `:1753`:

```ts
from = +to + timeIntervalMap[interval]
…
to = +from + pageSpan
```

The page just read served opens up to `to − width` (§2.1 row 1), so the bar
opening at `to` is the *first* bar of the next page — but the next page is asked
to start at `to + width`, so no page ever asks for it.

`spot_getCandles` at `:3401`, `:3410` and `:3414` does the same thing three
times: `cursor = chunkEnd + step` / `cursor = retryEnd + step`, where a historic
page served opens up to `chunkEnd − step` and a recent page served opens up to
`chunkEnd`.

### 2.3 — the origin

`git blame` puts the futures line on `d8d5e23` (2026-09-23, the #914 fix), but
that commit only moved it; `git log -S "from = +to + timeIntervalMap[interval]"`
puts it on **`b414b01`, 2025-12-12, "v1.1.18: Fixed Bitget futures candles
error"** — the commit that introduced the multi-page loop in the first place.
Before it there was a single request and no boundary to lose a bar at. The spot
sites are `80e5c77`, 2026-04-07, "v1.3.3: Changed Improve bitget get spot
candles request", which introduced spot's chunked pager on the same arithmetic.
**Latent**, nine and five months old respectively, in both cases present from
the moment paging was added.

#914 did not cause it, but it does make it materially worse at the two
intervals it repaired: pages there are span-limited to 90 days, so a 730-day
`1d` range now crosses 8 boundaries where it used to cross none (it returned
nothing at all).

## 3. Assumption

The root cause is that the cursor is advanced by one bar past the end of the
window just read, on the assumption that the venue's window is closed at
`endTime`. It is not: the futures endpoint and the spot historic endpoint both
stop one bar short of it, and the spot recent endpoint starts one bar *after*
`startTime`. Starting the next page at the previous page's end — `from = +to` on
futures, `cursor = chunkEnd − step` on spot — makes the pages tile with no hole,
at the cost on spot of at most two bars of overlap, which that method's existing
dedup already absorbs.

### 3.1 — a neighbouring defect this does NOT fix

Against the live venue, the final page — the deliberately overhanging one whose
`endTime` is in the future (spec 019 §1.6) — is answered by back-filling 200
rows from the last *closed* bar, reaching back well before its own `startTime`
and re-serving bars earlier pages already returned:

```
req[1789696800000..1790416800000] -> 200 rows, first 1789398000000  <<< before startTime
```

`futures_getCandles` has no dedup, so those duplicates reach any caller of an
un-merged interval. It is **pre-existing and independent of the cursor** —
measured at `origin/main`, 730d of `4h` returned 4400 rows for 4360 distinct
bars. Fixing the holes changes the count (4400 rows for 4380 distinct bars) but
neither causes nor removes it, and at `1w` the extra page it now needs raises it
from 4 duplicates to 12. It is filed separately rather than folded in here: its
fix is a dedup on the accumulation, which changes the returned payload for every
Bitget futures candle read and is a wider change than this one claims. The
merged widths are unaffected either way — `aggregateCandles` deduplicates its
input.

### 3.2 — termination

Spot additionally needs a termination guard it did not need before: `chunkEnd`
is clamped to `to`, so a cursor that no longer jumps past it would re-ask the
final window until the safety cap. Stopping once a page has reached `to` ends
the loop exactly where the old arithmetic did, with no extra request.
