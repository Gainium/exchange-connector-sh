# 022 — Bitget futures candles repeat the bars the overhanging final page re-serves

Bug #920. Sibling of spec 019 (page span cap, #914), spec 020 (merge of a
truncated leading bucket, #913) and spec 021 (cursor skipped a bar per page,
#918). Independent of all three: it reproduces with or without them, and the
only thing they change is *how many* bars come back twice.

## 1. Definition

`futures_getCandles` is the platform's reader for every Bitget USDT-M /
USDC-M futures candle series — charts, indicators, backtests and the
market-archive backfill all sit behind it.

### 1.1 Expected

The series it returns describes a time axis: **each bar opening time appears
at most once, and the bars are in strictly ascending time order.** This is
already the contract everywhere else in the same file and its neighbours —
`spot_getCandles` ends on a dedup + ascending sort (§4.1), and
`aggregateCandles` deduplicates its input before merging (§4.2).

### 1.2 Actual

The series contains repeated opening times and is not monotonic. Measured
through the real code path against the live venue, `BTCUSDT` /
`USDT-FUTURES`, 2026-09-22 23:42 UTC, at `origin/main` (i.e. with #913/#914/
#918 already in):

```
1h  over  30d: raw= 800 unique= 720 duplicates= 80 non-ascending-steps=1
4h  over 730d: raw=4400 unique=4380 duplicates= 20 non-ascending-steps=1
1d  over 730d: raw= 810 unique= 730 duplicates= 80 non-ascending-steps=1
1w  over 730d: raw= 117 unique= 105 duplicates= 12 non-ascending-steps=2
```

It is silent: `status: OK`, plausible values, roughly ascending order.

### 1.3 Which widths are affected

Every width the classic line serves directly: `1m` `3m` `5m` `15m` `30m`
`1h` `2h` `4h` `1d` `1w`. The two merged widths (`8h` on both product lines,
`2h` on spot) are immune only by accident — `aggregateCandles` deduplicates
its own input (§4.2) — and they are still built from a base series that is
wrong.

### 1.4 What must NOT change

The final page deliberately runs past the requested `to` so the bar the end
falls inside can survive (spec 019 §1.6). That overhang stays. The last bar
of the series must be the same bar before and after this fix; only repeated
opening times are removed.

## 2. Evidence

### 2.1 The venue serves a page END-ANCHORED, not start-anchored

`/api/v2/mix/market/history-candles` returns the **last**
`min(limit, span / width)` bars of the requested window, where the window's
effective end is the last *closed* bar. Probed directly, `BTCUSDT` /
`USDT-FUTURES` / `1H`, 2026-09-22 23:42:26 UTC (last closed bar 22:00):

| requested window | span | limit | rows | first row | last row |
|---|---|---|---|---|---|
| 21:42 → next-day 23:42 (future) | 26h | 200 | 26 | **09-21 21:00** | 09-22 22:00 |
| 21:42 → 00:42 (future) | 3h | 200 | 3 | **09-22 20:00** | 09-22 22:00 |
| 09-02 03:42 → 09-23 23:42 (future) | 524h | 200 | 200 | 09-14 15:00 | 09-22 22:00 |
| 09-02 03:42 → 09-23 23:42 (future) | 524h | 50 | 50 | 09-20 21:00 | 09-22 22:00 |
| 21:42 → 22:42 (past) | 1h | 200 | 1 | 09-22 21:00 | 09-22 21:00 |

Row 1 is the shape that matters: the first bar served opens **24 hours
before the window's own `startTime`**. While the window ends in the past,
end-anchored and start-anchored coincide and nothing is noticed; the moment
`endTime` is in the future the window slides backwards under the caller.

### 2.2 The real code path, live venue, instrumented per page

`futures_getCandles('BTCUSDT', 1h, now - 30d, now)`:

```
req[2026-08-23 23:42 .. 2026-09-01 07:42] -> 200 rows first 2026-08-23 23:00 last 2026-09-01 06:00
req[2026-09-01 07:42 .. 2026-09-09 15:42] -> 200 rows first 2026-09-01 07:00 last 2026-09-09 14:00
req[2026-09-09 15:42 .. 2026-09-17 23:42] -> 200 rows first 2026-09-09 15:00 last 2026-09-17 22:00
req[2026-09-17 23:42 .. 2026-09-26 07:42] -> 200 rows first 2026-09-14 15:00 last 2026-09-22 22:00
                                                         ^^^^^^^^^^^^^^^^^^
```

The three pages the cursor lays out inside the window are disjoint and tile
exactly, as spec 021 §3 requires. The **fourth** page is the overhanging one
of §1.4: its `endTime` is four days in the future, so the venue anchors it on
the last closed bar and walks back 200 rows — starting 83 bars before its own
`startTime`, all 83 of which page three already returned. 800 rows come back,
720 distinct.

### 2.3 The pager cannot avoid it

The overhang is required (§1.4) and its size is not a free parameter: it is
`pageSpan`, which is pinned by the venue's 200-row limit and its 90-day span
cap (spec 019 §1.3). How far back the venue then slides is decided by the
venue from the *span* of that page, not by anything the caller controls. So
the repetition cannot be prevented at request time — only the accumulated
result can be made to satisfy §1.1.

## 3. Assumption (hypothesis)

`futures_getCandles` accumulates every page into `allCandles` and returns it
verbatim — `return this.returnGood(timeProfile)(allCandles)`. There is no
dedup and no sort, unlike the two neighbours in §4. Because the final page is
end-anchored (§2.1) it re-serves bars earlier pages already pushed, and those
copies survive to the caller.

The comment on the cursor asserts the opposite, and is false as written: it
says the half-open window "is also why this cannot double-count, which
matters because the pages below are returned as accumulated, with no dedup."
Half-open is why the *cursor* introduces no overlap — which is true and is
what spec 021 §3 tests. It says nothing about the venue's own end-anchoring,
which is where the overlap actually comes from.

## 4. The contract this restores

### 4.1 `spot_getCandles` already enforces it

It ends on `// Dedup + sort ascending by time (chunks may overlap on
boundaries).` — a `seen` Set keyed on `c.time`, keeping the first occurrence,
then `.sort((a, b) => a.time - b.time)`. Added 2026-04-07 (`80e5c77`) for
spot's own overlapping chunks and never mirrored to futures.

### 4.2 `aggregateCandles` already assumes it

`bitget/uta.ts` deduplicates its input before bucketing, which is the only
reason the merged widths of §1.3 do not show the defect.

## 5. Fix

Give `futures_getCandles` the same tail as §4.1, and correct the false clause
of §3 in the cursor comment. Keep-first, not keep-last: every page but the
last has a window entirely in the past, so it only ever serves closed bars,
and the final page's copies of those same bars are identical. Nothing in the
pager changes, so §1.4 holds by construction — dedup cannot raise or lower
the maximum timestamp in the array.

## 6. Acceptance

1. §1.1 — for `1m`/`1h`/`4h`/`1d`/`1w` over a multi-page window,
   `data.length === new Set(data.map(c => c.time)).size`.
2. §1.1 — `time` is strictly ascending across the whole series.
3. §1.4 — the last bar of the series is byte-identical to the last bar the
   unfixed reader returned, and still opens at or after `to - width`.
4. §1.3 — the merged `8h` width still merges a complete base series.
5. Spec 019 §1.3 and spec 021 §1.1/§1.2 stay green: no page wider than the
   venue's span cap, and no hole at a page boundary.
