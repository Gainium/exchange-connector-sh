# 023 — Bitget spot candle ranges collapse to a single venue page,
# because the pager's cursor is the un-coerced `from` query string

Bug #921. Found while verifying #918 in production, and confirmed independent
of it: the numbers in §1.2 are byte-identical on the pre-#918 and post-#918
code. Every Bitget **spot** candle read whose window needs more than one venue
page comes back as one page's worth of bars — the most recent ~200 (historic
endpoint) or ~1000 (recent endpoint) — however long a range was asked for. It
is silent: `status: OK`, a plausible series, no error, just a chart or a
backtest that begins weeks after the range it was given.

## 1. Definition

### 1.1 — expected

`spot_getCandles(symbol, interval, from, to)` returns every bar of `interval`
that opens in `[from, to)`, whatever the runtime type of `from`/`to`, and pages
the venue as many times as that window takes. The connector's own HTTP surface
is the contract here: `GET /candles?from=…&to=…` is how every caller reaches it.

### 1.2 — actual

The loop makes exactly **one** venue call and returns what that page holds.
Measured through the real code path against the live venue, 2026-09-23,
BTCUSDT spot, at `origin/main` — the same window passed as numbers and as the
strings the HTTP layer really delivers:

```
                       from/to as NUMBER                from/to as STRING
2h  200d  expect 2400  2400 in-window, 20 calls   |     100 in-window,  1 call
2h   60d  expect  720   720 in-window,  3 calls   |     100 in-window,  1 call
3m   10d  expect 4800  4799 in-window,  5 calls   |     999 in-window,  1 call
1h  200d  expect 4800  4800 in-window, 20 calls   |     200 in-window,  1 call
1d  700d  expect  700   700 in-window,  5 calls   |     200 in-window,  1 call
1w  700d  expect  100    99 in-window,  1 call    |      99 in-window,  1 call
```

`1w` is the one width that escapes: 200 bars is 1400 days, so the single page
the collapse leaves already covers any range a caller asks for. Nothing about
`1w` is healthy — it simply never needed a second page.

Through the connector's own HTTP endpoint (a freshly built `origin/master`
instance, real venue, `GET /candles?exchange=bitget&symbol=BTCUSDT&…`), which
is the string column above and is what production runs:

```
2h  200d: bars= 100  expected=2400   oldest 2026-09-14  <- 8 days of a 200-day request
2h   60d: bars= 100  expected= 720
2h   20d: bars= 240  expected= 240   <- inside the recent lookback: one 1000-bar page covers it
3m   10d: bars=1000  expected=4800
1h  200d: bars= 200  expected=4800
1d  700d: bars= 200  expected= 700
```

### 1.3 — expected

Which widths are damaged in production must follow from the connector's
behaviour, not from what happens to sit in front of it.

### 1.4 — actual

Through `api.gainium.io/candles` (public, read-only, same day) only the widths
**market-archive does not serve** show the truncation; the archive answers the
native ones from ClickHouse and main-app never reaches the fallback:

```
2h  200d: bars= 544  expected=2400     <- archive has no 2h; connector fallback
2h   60d: bars= 645  expected= 720
3m   10d: bars=1000  expected=4800     <- archive has no 3m; connector fallback
1h  200d: bars=4800  expected=4800     <- served by the archive
4h  200d: bars=1200  expected=1200     <- served by the archive
1d  700d: bars= 700  expected= 700     <- served by the archive
```

So the user-visible surface is `2h` and `3m` charts/backtests, and every other
spot width the archive has not backfilled for a symbol. The defect underneath
is not interval-specific.

### 1.5 — expected

A fix changes only which windows are asked for. The half-open cursor of #918
still tiles pages with no hole, the dedup of #920 still absorbs the overlap it
costs, the `2h`→`1h` merge of #913 still merges, and `futures_getCandles` — which
already coerces with unary `+` at every use and is measurably unaffected — is
not touched.

## 2. Evidence

### 2.1 — the values are strings by the time they reach the pager

`core/src/exchange/exchange.controller.ts:109`:

```ts
@Get('/candles')
async getCandles(
  …
  @Query('from') from: number = null,
  @Query('to') to: number = null,
```

`@Query` performs no conversion without a transforming pipe, and neither
`src/main.ts` nor `core/src/main.ts` installs one (`useGlobalPipes` appears
nowhere in either repo). The `: number` annotation is erased at compile time.
`exchange.service.ts:126` passes both straight through to the exchange class.

Upstream is not the problem and cannot fix it: main-app's
`core/src/exchange/additionalAPIs.ts:63` already coerces (`+startAt`, `+endAt`)
before `Exchange.getCandles` serialises them into an axios query string — where
they become strings again, over the wire, for the connector to parse.

### 2.2 — what the string does to the loop

`core/src/exchange/exchanges/bitget/index.ts`, `spot_getCandles`:

```ts
let cursor = from                                    // :3334  string
const chunkEnd = Math.min(cursor + size * step, to)  // :3375
```

`cursor + size * step` is string **concatenation**, not addition: a 13-digit
epoch and a 9-digit page span become one ~22-digit numeric string, always
greater than `to`, so `Math.min` returns `to`. Every chunk therefore ends at
`to`, the first call is `getSpotHistoricCandles({ endTime: to, limit: 200 })`
(or the recent endpoint's 1000), and `advanceCursor(to)` — whose first line is
`if (pageEnd >= to) return false` — ends the loop after it. One page, always.

Two further sites in the same method are concatenations for the same reason and
are repaired by the same coercion: `coversStart`'s `+data[0][0] <= cursor + step`
(:3427), and `advanceCursor`'s `cursor = pageEnd - step` is safe only because
`-` coerces.

`futures_getCandles` writes `+to - +from > pageSpan`, `to = +from + pageSpan`,
`from = +to` — every arithmetic use coerced — which is why the futures column of
a paired measurement is identical for both input types.

### 2.3 — the origin

`git blame` puts both lines' current text on later commits that only moved or
resized them (`42ed1a4`, 2026-07-12, "page recent spot candles at 1000"), but
`git show 80e5c77:…/bitget/index.ts` has them in their original form:

```
2034:    let cursor = from
2039:    const chunkEnd = Math.min(cursor + maxSize * step, to)
```

**`80e5c77`, 2026-04-07, "v1.3.3: Changed Improve bitget get spot candles
request"** — the commit that introduced spot's chunked pager. **Latent**, five
and a half months old, present from the moment spot paging existed; before it
there was a single request and no cursor to concatenate. The controller's
un-piped `@Query` binding is older still (`8fe6e62`, 2025-06-25). #918 and #920
neither caused it nor changed it.

## 3. Assumption

The root cause is that `spot_getCandles` never coerces `from`/`to`, so the one
place that *adds* to them — the cursor — concatenates instead. Coercing both
once at the top of the method, as `futures_getCandles` already does at every
use, restores paging for every width and touches nothing else: every other use
of `from`/`to` in the method is either already coercing (`-`, `Math.min`,
`Date.now() -`) or a template literal, which renders a number and a numeric
string identically.

### 3.1 — what this does NOT fix

`1w` over 700d returns 200 bars where 100 were asked for, reaching back to
2022 — the single `endTime`-only historic page is 200 bars wide regardless of
`from`. That overhang before the requested start is pre-existing, identical for
both input types (§1.2), and not what this spec is about; the caller windows
its own series. It is left as it is rather than folded in.

Neither does it fix the leading edge. A range whose FIRST chunk is served by
`/spot/market/candles` never gets the bar opening exactly at `from`, because
that endpoint's window is `(startTime, endTime]` (§2.1 of spec 021) and the
chunk asks for `startTime: cursor`. Measured live, 2026-09-23, on the numeric
path — so it is present today wherever this defect is not:

```
3m over  10d  from=2026-09-13T00:00  first bar=2026-09-13T00:03  1 bar missing, at `from`
1h over  20d  from=2026-09-03T00:00  first bar=2026-09-03T01:00  1 bar missing, at `from`
```

One bar, identical for both input types, and a different fix (the first recent
chunk must start one bar early, as the cursor already does at every later
boundary). Filed on its own evidence rather than folded in.

Nothing here changes the archive's coverage: `2h` and `3m` remain fallback
reads. They will simply be complete.
