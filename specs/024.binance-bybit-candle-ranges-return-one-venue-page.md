# 024 — A binance or bybit candle range returns one venue page,
# because neither adapter has a pager at all

Bug #923. Found while fixing #921 (Bitget spot paging collapsed to one
request) and confirmed independent of it: neither adapter does arithmetic on
`from`/`to` today, so #921's string-concatenation cause cannot apply here.
Bitget is the only adapter with a paging loop. Binance and bybit issue exactly
one venue call for any range and return whatever that page holds — the most
recent 1000 bars (binance) or 200 (bybit). It is silent: `status: OK`, no
error, a plausible series that simply begins later than the range it was given.

## 1. Definition

### 1.1 — expected

`getCandles(symbol, interval, from, to)` returns every bar of `interval` that
opens in `[from, to)`, paging the venue as many times as that window takes.
The connector's own HTTP surface is the contract: `GET /candles?from=…&to=…`
is how every caller reaches it.

### 1.2 — actual

Measured 2026-09-23 through the REAL adapter code against the live venues — a
throwaway `ts-node` harness constructing `BinanceExchange` / `BybitExchange`
directly (no Nest boot, public endpoints, no auth), counting `getKlines` /
`getKline` calls and passing the window as the query strings the HTTP layer
really delivers — at `origin/main`:

```
binance spot   1h 200d  bars= 1000  expected=4800  oldest=2026-03-07  calls=1  asc=true
binance usdm   1h 200d  bars= 1000  expected=4800  oldest=2026-03-07  calls=1  asc=true
bybit  spot    1h 200d  bars=  199  expected=4800  oldest=2026-09-14  calls=1  asc=false
bybit  linear  1h 200d  bars=  199  expected=4800  oldest=2026-09-14  calls=1  asc=false
binance spot   1d 700d  bars=  700  expected= 700  oldest=2024-10-23  calls=1
bybit  spot    1d 700d  bars=  199  expected= 700  oldest=2026-03-08  calls=1
```

`calls=1` is the signature. Binance anchors at `startTime` and serves the
OLDEST page of the window; bybit anchors at `end` and serves the NEWEST, which
is why a 200-day bybit request begins 8 days ago. `binance 1d 700d` is the case
that escapes — 700 bars fit in one 1000-bar page, so nothing is missing; the
same read on bybit loses 500 of 700.

And through the connector's own HTTP endpoint — a freshly built instance, real
venues, `GET /candles?exchange=<ex>&symbol=BTCUSDT&interval=1h&from=<now-200d>&to=<now>`:

```
binance      1h 200d: bars=1000  expected=4800  oldest=2026-03-07  asc=true
binanceUsdm  1h 200d: bars=1000  expected=4800  oldest=2026-03-07  asc=true
bybit        1h 200d: bars= 200  expected=4800  oldest=2026-09-14  asc=false
bitget       1h 200d: bars=4801  expected=4800  oldest=2026-03-07  asc=true   <- the pager #921 fixed
```

Bitget in the same run is the control: it is the only adapter that pages, and
it is the shape the other two should have.

### 1.3 — expected

Which reads are damaged in production must follow from the connector's
behaviour, not from what happens to sit in front of it.

### 1.4 — actual

`api.gainium.io/candles` goes through main-app, which tries **market-archive**
first and reaches the connector only on an archive miss. For BTCUSDT the
archive answers every common width, so nothing shows. It shows on series the
archive has not finished backfilling (public read, same day, 200d of `1h`,
4800 expected):

```
                 binance              bybit
ZKUSDT           4800                 4226   from 2026-03-07
ARKMUSDT         4800                 1878   from 2026-06-10
PENDLEUSDT       4800                 1314   from 2026-06-16
bybit BTCUSDT 2h 200d                 2019 / 2400
bybit BTCUSDT 3m 200d                14463 / 96000
```

The asymmetry is the defect's shape: the archive's backfiller walks a gap by
re-asking the connector and advancing past the last returned bar, so a bybit
gap fills 200 bars per balancer round-trip against binance's 1000, and deep
history on bybit is still arriving months later. Users see a chart or backtest
that starts in June for a range asked from March.

### 1.5 — expected

A fix changes only which windows are asked for. Every caller that passes a
count keeps its current request shape and call volume; the merged result has
no hole at a page boundary and no duplicate bar.

## 2. Evidence

### 2.1 — there is no loop to get wrong

`core/src/exchange/exchanges/bybit/index.ts:1678` `getCandles` — one call, and
the limit it asks for is a fifth of what the venue will serve:

```ts
return this.client.getKline({
  category: this.getCategory() as GetKlineParamsV5['category'],
  symbol,
  interval: this.convertInterval(interval),
  start: from,
  end: to,
  limit: countData || 200,
})
```

`core/src/exchange/exchanges/binance/index.ts:2201` `spot_getCandles` — the
same shape at binance's cap; `futures_getCandles` (:2263) is the same again:

```ts
if (countData) { options.limit = countData } else if (!countData) { options.limit = 1000 }
…
return this.client.getKlines(options)
```

`bybit.futures_getCandles` (:415) delegates straight to `getCandles`, so linear
and inverse are the same single call.

This is NOT #921's cause reappearing: neither method ADDS to `from`/`to`
anywhere, so the un-coerced query strings the controller delivers
(spec 023 §2.1 — `@Query` with no transforming pipe, still true) pass through
into the request untouched and the venue parses them. §1.2's numbers were taken
with string inputs for exactly that reason.

### 2.2 — the real window semantics of each endpoint, measured

Not assumed. Live, 2026-09-23, BTCUSDT `1h`, a window exactly 5 bars wide
(`start = S`, `end = S + 5h`):

```
binance /api/v3/klines     n=6   00:00 01:00 02:00 03:00 04:00 05:00     ascending
bybit   /v5/market/kline   n=6   05:00 04:00 03:00 02:00 01:00 00:00     descending
```

Six bars for a five-bar span: **both ends are INCLUSIVE** on both venues —
`[start, end]`, not `[start, end)`. A chunk must therefore span
`(pageSize - 1)` bars, or the limit binds and one end of the window is dropped.

Which end is dropped differs, and that is the whole reason the two symptoms
differ. Same 10h window, `limit=5`:

```
binance  00:00 01:00 02:00 03:00 04:00     anchored at startTime, oldest first
bybit    10:00 09:00 08:00 07:00 06:00     anchored at end,       newest first
```

Page caps, measured by over-asking (neither venue errors — both silently clamp):

```
binance spot   /api/v3/klines    limit=1000 -> 1000   limit=1200 -> 1000   limit=1500 -> 1000
binance usdm   /fapi/v1/klines   limit=1500 -> 1500
binance coinm  /dapi/v1/klines   limit=1500 -> 1500
bybit   spot   /v5/market/kline  limit=1000 -> 1000   limit=1500 -> 1000
bybit   linear /v5/market/kline  limit=1000 -> 1000
```

So: binance spot 1000, binance futures 1500, bybit 1000 on every category.
Bybit's current `limit: countData || 200` leaves 80% of its own page unused.

### 2.3 — the origin

`git blame` at HEAD puts every line of both call sites on **`8fe6e62`,
2025-06-25** — the repository's root commit. Both adapters have issued exactly
one call for a range since the code first existed; `git log -S` finds no commit
that ever removed a loop. **Latent**, ~15 months old, not a regression. The
un-piped `@Query` binding is from the same commit.

## 3. Assumption

The root cause is the absence of a pager. Walking `[from, to]` forward in
chunks of the endpoint's real page size — a chunk spanning `pageSize - 1` bars
so the limit never binds (§2.2), the half-open cursor of #918
(`cursor = pageEnd - step`) so no bar falls between pages whichever way the
venue reads its bounds, dedup + sort on accumulation as #920 requires, and a
`totalChunks + 5` safety cap — returns the whole window, and nothing else in
either method has to change.

Both methods must coerce `from`/`to` first. They are strings in production
(spec 023 §2.1) and the pager is the first code in either adapter to ADD to
them; without the coercion `cursor + span` concatenates and the loop collapses
to one call exactly as #921's did. That is a precondition of this fix, not a
second fix.

### 3.1 — scope: what keeps its current behaviour

`countData` keeps meaning "one page of N". Paging engages only for a read that
passes BOTH `from` and `to` and NO count, so every caller that passes a count
issues exactly the request it issues today:

- main-app's indicator warm-up (`core/src/indicators/service.ts:915`) and its
  backtest candle loader (`core/src/backtest/data/candles.ts:408`) both page
  themselves and pass `requestStep` as the count — 1000 for binance spot, 999
  for bybit, 1500 for binance futures.
- the dashboard's chart, market-stats, deal price history and manual-backtest
  reads all pass `limit` (`main-dash-redesign/core/src/utils/tradingView/historyApi.ts:114`).
- the agent `get_candles` tool passes `limit` (`main-app/src/agents/agentTools/marketDataTools.ts:436`).

**market-archive's backfiller does NOT pass a count**, contrary to the brief:
`market-archive/src/backfill/client.ts:311` sends `{exchange, symbol, interval,
from, to}` and nothing else, and its own comment says "the caller is expected to
loop until the window is filled". It therefore DOES start paging, which is the
intended effect — it is the consumer §1.4 shows starved. Its loop still
terminates: it advances past the last bar returned, so a longer response ends
the gap sooner rather than looping more. What changes is that one balancer
round-trip now holds the connector for several sequential venue calls instead
of one; at the 0.2–0.5 s per call measured in §1.2 a 200-day 1h gap is ~5 calls
(~1.5 s), but a 1m gap of the same width would be ~290 (~90 s) against the
balancer's 5-minute per-IP cap. That ceiling is the same one Bitget has run
under since #921 shipped; it is recorded here rather than pre-emptively capped,
because a cap is a new silent truncation and the operator has been asked.

### 3.2 — what this does NOT fix

Bybit's single-call path still returns bars NEWEST-first, and binance's
OLDEST-first. Only the new paging branch sorts ascending — it has to, since it
concatenates pages. Normalising the count path's order is a behaviour change
for every count-passing caller and is out of scope here.

`futures_getCandles`'s COIN-M branch (`binance/index.ts:2300`) chunks by 200
DAYS rather than by bar count and calls `this.client` (the SPOT `MainClient`)
instead of the `client` it just resolved, so a coin-M range wider than 200 days
comes back `status: OK` with ZERO bars. Measured through the running connector,
`binanceCoinm` `BTCUSD_PERP` `1d` with `count=400`:

```
150d -> 150 bars    199d -> 199 bars    201d -> 0 bars    300d -> 0 bars
```

A range read with no count no longer reaches that branch once this fix lands
(the pager runs first), but a count-passing caller still does. Separate
reproduction, separate fix, filed on its own.
