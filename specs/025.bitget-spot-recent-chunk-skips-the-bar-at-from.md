# 025 — A Bitget spot range whose first chunk is served by the recent
# endpoint never returns the bar opening at `from`

Bug #924. Carved out of spec 023 §3.1, which named it while fixing a different
defect in the same method and deliberately left it: #921 is a coercion at the
top of `spot_getCandles`, this is a change to which window the first venue call
asks for. Different evidence, different risk.

Silent: `status: OK`, no hole in the middle of the series, no error — just a
series that begins one bar late. It is the bar an indicator warm-up and a
backtest start on.

## 1. Definition

### 1.1 — expected

`spot_getCandles(symbol, interval, from, to)` returns every bar of `interval`
that opens in `[from, to)`, including the one opening exactly at `from`,
whichever of the two spot endpoints serves the first chunk.

### 1.2 — actual

When the first chunk is inside the recent lookback, the bar at `from` is
missing and the series begins at `from + step`. Measured through the real code
path against the live venue, BTCUSDT spot, 2026-09-23, at `core/main`
(`c16c6eb`, i.e. post-#918/#920/#921 — so this survives all three), with
NUMERIC `from`/`to` so #921 is not in play:

```
                        firstBar - from   in-window / expected   first chunk
3m  over  10d                  +1 bar         4799 / 4800        recent
1h  over  20d                  +1 bar          479 /  480        recent
1h  over  90d                   0 bars        2160 / 2160        historic
1d  over 400d                   0 bars          400 /  400       historic
```

The missing bar is always exactly the one at `from`, and only ever on a range
short enough that its FIRST chunk is inside the recent lookback.

### 1.3 — expected

A history-starting range is unchanged, and no range gains a bar that opens
BEFORE `from` — today neither shape returns one (`preFromBars = 0` in all four
rows above). The fix must keep that true: the historic endpoint already reaches
back exactly to `from` on its own (§2.2), so it needs no correction and must
not be given one.

### 1.4 — expected

The fix changes only which window the FIRST chunk asks for. #918's half-open
cursor (`cursor = pageEnd - step`) still tiles every LATER boundary with no
hole and must not be back-stepped a second time; #920's dedup still absorbs the
overlap that costs; #921's coercion at the top of the method still stands;
`futures_getCandles` and every non-Bitget adapter are untouched.

## 2. Evidence

### 2.1 — the recent endpoint's window is open at the start

`GET /api/v2/spot/market/candles`, live, 2026-09-23, BTCUSDT 3min, a 50-bar
window on exact bar boundaries:

```
requested startTime 1789259760000  2026-09-13T00:36:00Z
requested endTime   1789268760000  2026-09-13T03:06:00Z
first bar returned  1789259940000  2026-09-13T00:39:00Z   = startTime + 1 bar
last  bar returned  1789268760000  2026-09-13T03:06:00Z   = endTime
rows 50 for a 50-step window (51 if both ends were inclusive)
```

`(startTime, endTime]` — exclusive at the start, inclusive at the end. Same
shape spec 021 §2.1 measured, and the same one `candle-page-boundary.spec.ts`'s
`spotStub` already models.

### 2.2 — the historic endpoint's is not, and already covers `from`

`GET /api/v2/spot/market/history-candles`, same day, `endTime = from + 200*step`,
`limit = 200`:

```
first bar returned  = from            (offset 0 steps)
last  bar returned  = endTime - 1 bar
```

`endTime`-only, 200 bars walking back, exclusive of `endTime`. With
`chunkEnd = cursor + 200*step` the page reaches back to exactly `cursor`, which
is why a history-starting range loses nothing today and why §1.3 holds.

### 2.3 — the first chunk asks `startTime: from`, and nothing precedes it

`core/src/exchange/exchanges/bitget/index.ts`, `spot_getCandles`:

```ts
let cursor = from                              // :3350
…
? await this.client.getSpotCandles({
    startTime: cursor,                         // :3406
    endTime: chunkEnd,
```

Instrumenting the live probe above shows the first call really is
`ep=recent startTime=1789259760000` — byte-equal to `from`. Combined with
§2.1 the bar at `from` is never requested by anyone.

#918's cursor (`cursor = pageEnd - step`, :3381) already compensates for this
at every LATER boundary — that is exactly what the back-step is for. The FIRST
chunk is the one boundary it cannot reach, because there is no preceding page
whose end it steps back from.

### 2.4 — why #918's own test does not see it

`candle-page-boundary.spec.ts`'s `read()` helper measures holes only BETWEEN
`inWindow[0]` and the last bar:

```ts
for (let t = inWindow[0]; t < inWindow[inWindow.length - 1]; t += width)
```

A series that simply starts one bar late has `inWindow[0] = from + step` and no
interior gap, so it reports zero missing. The leading edge is outside what any
existing assertion looks at.

### 2.5 — the origin

`git blame core/src/exchange/exchanges/bitget/index.ts` puts both `let cursor =
from` (:3350) and `startTime: cursor` (:3406) on **`80e5c77`, 2026-04-07,
"v1.3.3: Changed Improve bitget get spot candles request"** — the commit that
introduced spot's chunked pager. `git show 80e5c77^:…/bitget/index.ts` contains
neither line: before it there was a single request and no cursor at all.

**Latent**, five and a half months old, present from the moment spot paging
existed. Not a regression: `bf9b6de` (#918), `2542e78`/`ba4269b` (#920),
`f458e12` (#921) and `c16c6eb` (#923) all postdate it and §1.2 was measured on
top of all of them.

## 3. Assumption

The root cause is that the first recent chunk asks the venue for
`startTime = from` while the venue serves `(startTime, endTime]`, so the bar at
`from` is never inside any requested window. Seeding the pager one bar early —
`cursor = from - step` — makes the first recent call ask `startTime = from - step`,
whose first served bar is `from`.

The seed is applied **only when the first chunk will use the recent endpoint**.
Applying it unconditionally would also shift the historic path, whose page is
anchored on `endTime` and already reaches back to exactly `cursor` (§2.2): it
would return a bar opening before `from` and move every subsequent chunk
boundary, breaking §1.3.

Seeding is preferred over `startTime: cursor - step` at the call site, which
would back-step a second time at every later boundary where #918's
`cursor = pageEnd - step` already applies (§1.4).

Cost: the recent path's first page carries one extra bar. It is in-window
(`from` itself), so nothing is added before `from`; the method's existing dedup
and sort absorb any overlap, and `chunkEnd` is still clamped to `to`.
