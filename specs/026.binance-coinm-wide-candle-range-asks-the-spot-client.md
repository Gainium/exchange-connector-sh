# 026 — A binance COIN-M candle range wider than 200 days comes back empty,
# because the chunk loop asks the SPOT client for a COIN-M symbol

Bug #925. Found while fixing #923 (binance/bybit candle ranges returned one
venue page, spec 024) and independent of it: #923's pager engages only for a
read that passes NO count, and this branch is reachable only WITH one. The
COIN-M-only wide-range loop in `futures_getCandles` sends its chunks to
`this.client` — the SPOT `MainClient` on `api.binance.com` — which does not
list `BTCUSD_PERP` and answers `-1121 Invalid symbol` to every chunk. The
`.catch` on that call discards the failure, the accumulator stays empty, and
the method returns `status: OK` with `[]`.

## 1. Definition

### 1.1 — expected

`getCandles(symbol, interval, from, to, count)` on `binanceCoinm` returns the
bars of `interval` that open in the requested window, whatever its width, and
reports a failure as a failure. The connector's own HTTP surface is the
contract: `GET /candles?exchange=binanceCoinm&…` is how every caller reaches it.

### 1.2 — actual

Measured 2026-09-23 through the connector's own HTTP endpoint on this host,
`GET /candles?exchange=binanceCoinm&symbol=BTCUSD_PERP&interval=1d&count=400&from=<now-Nd>&to=<now>`:

```
150d -> status=OK bars=150
199d -> status=OK bars=199
201d -> status=OK bars=0     <- silent
300d -> status=OK bars=0     <- silent
```

A clean threshold at exactly 200 days, with no `reason`. `binanceUsdm` over the
same 300d window returns 300 bars — it never enters this branch.

### 1.3 — expected

Which host a COIN-M read reaches must follow from the market, not from which
line of the method issued the call.

### 1.4 — actual

`tcpdump` SNI capture on this host, isolating the 300-day request (the only
outbound TLS handshake in the window):

```
300d coinm read -> 1 x api.binance.com      <- SPOT
199d coinm read -> 1 x dapi.binance.com     <- COIN-M
```

And the two hosts, asked directly for the same symbol:

```
GET api.binance.com/api/v3/klines?symbol=BTCUSD_PERP   -> {"code":-1121,"msg":"Invalid symbol."}
GET dapi.binance.com/dapi/v1/klines?symbol=BTCUSD_PERP -> [[1790035200000,"86561.3",…]]
```

### 1.5 — expected

A chunk asks for a window the endpoint can actually serve in one call.

### 1.6 — actual

The branch chunks by a flat **200 days** and sends `limit: countData`, so a
chunk can hold far more bars than the row it asks for. Live against the COIN-M
host, a 200-day `1h` chunk asked with `limit=400` — exactly the request the
loop builds:

```
rows=400   2025-11-27 02:00 .. 2025-12-13 17:00   expected=4800
```

16 days served for a 200-day chunk. The remaining 4400 bars are a hole that
nothing downstream can see, because the loop then advances past the whole chunk.

### 1.7 — scope: what must keep its current behaviour

`binanceUsdm` and spot candle reads, and COIN-M windows of 200 days or less.
All three take different paths and all three are correct today (verified:
usdm 300d -> 300 bars, coinm 199d -> 199 bars). A fix touches only the COIN-M
>200-day branch.

## 2. Evidence

### 2.1 — the call site

`core/src/exchange/exchanges/binance/index.ts` `futures_getCandles`:

```ts
const client = this.usdm ? this.usdmClient : this.coinmClient      // resolved…
…
if (this.coinm) {
  if (options.endTime - options.startTime > 200 * 24 * 60 * 60 * 1000) {
    for (let start = options.startTime; start < options.endTime; start += 200 * DAY) {
      …
      await this.client                                            // …and not used
        .getKlines({ ...options, startTime: start, endTime: end })
        .then((res) => { candles.push(...) })
        .catch(this.handleBinanceErrors(…))                        // discarded
      …
    }
    return this.returnGood<CandleResponse[]>(timeProfile)(candles)  // OK with []
  }

```

`this.client` is `new MainClient({ baseUrl: getBinanceBase(domain) })` (:224) —
the SPOT client, on every instance including a COIN-M one.

The `.catch` is why it is silent: `handleBinanceErrors` returns a `BaseReturn`,
and a `BaseReturn` resolved into a `.catch` inside a `for` body is a value
nobody reads. The loop continues, and the `returnGood` after it reports the
empty accumulator as success.

### 2.2 — who reaches this branch

Only a caller that passes a count, because #923's pager (spec 024) sits above
it and takes every count-less range read. Both real count-passing callers send
a window exactly `requestStep` bars wide and `requestStep` as the count, 1500
for `binanceCoinm`:

- main-app's backtest candle loader, `core/src/backtest/data/candles.ts:408`
- the dashboard's chart / market-stats / manual-backtest loader,
  `main-dash-redesign/core/src/utils/candles/index.ts:602`

1500 bars exceed 200 days at `4h` and wider (`4h` 250d, `8h` 500d, `1d` 1500d,
`1w` 10500d). So on `binanceCoinm` a chart or backtest at `4h`, `8h`, `1d` or
`1w` asks for a window this branch answers with nothing — for `1d` that is any
range at all, since one 1500-bar request already spans 1500 days.

market-archive's backfiller passes no count (spec 024 §3.1) and is unaffected.

### 2.3 — the origin

**Regression**, `6baebfb1158d254c333c3b6644a019ead3421456`, 2026-01-27,
"wip: binance ws api, ed25519 keys" — the migration off `binance-api-node` onto
the typed `MainClient` / `USDMClient` / `CoinMClient` trio.

`git blame` puts `await this.client` on the root commit `8fe6e62`
(2025-06-25), but at that commit there was only ONE client and the call read
`this.client.deliveryCandles(...)` — `deliveryCandles` was the COIN-M method,
so the receiver was right. `6baebfb` introduced
`const client = this.usdm ? this.usdmClient : this.coinmClient`, rewrote the
method's single-call path to `client.getKlines(options)`, and rewrote this
loop's call from `.deliveryCandles(` to `.getKlines(` — on the unchanged
`this.client` receiver, which had by then become the SPOT client. The market
used to be selected by the METHOD NAME and is now selected by the CLIENT; this
one call site was converted for the first half of that and not the second.

`git log -S "const client = this.usdm ? this.usdmClient : this.coinmClient"`
returns `6baebfb` and `a942019` only; no later commit touched the loop's
receiver.

## 3. Assumption

The root cause is the receiver, and the 200-day chunking and the swallowed
`.catch` are why it stayed invisible. All three are removed by routing this
window through `pageCandleRange` — the helper #923 already added for exactly
this shape — instead of the hand-rolled loop:

- it calls the `client` resolved for the market, so COIN-M reads reach `dapi`;
- it chunks by BAR COUNT at the endpoint's measured 1500-row cap (spec 024
  §2.2, re-verified: `limit=1500` -> 1500 rows, `limit=1501` -> `-1130`), so a
  chunk can never ask for more than one page holds;
- a throw propagates out of `fetchPage`, so a total failure reaches
  `handleBinanceErrors` and returns `notok` with the venue's own reason
  instead of `OK` with `[]`.

### 3.1 — what stays the same

The **200-day trigger is unchanged**: a COIN-M window of 200 days or less still
takes the single call below it, and `binanceUsdm` and spot never satisfy
`this.coinm` so their condition is byte-for-byte what it is today (§1.7).

`countData` still means "one page of N" for every other read (spec 024 §3.1).
It never meant that in this branch — the loop has always walked the whole
window and only used the count as a per-chunk row limit — so honouring the
window here restores the branch's own intent rather than widening #923's.

Call volume does not grow. The window the real callers send is 1500 bars wide;
today's 200-day chunking issues 8 calls for it at `1d`, the pager issues 2.

The in-queue timeout bail-out this branch has (`Response timeout` when
`checkLimits` blocked longer than `this.timeout`) is preserved, gated to this
branch so the `binanceUsdm` and spot paging paths #923 added keep the behaviour
they shipped with.
