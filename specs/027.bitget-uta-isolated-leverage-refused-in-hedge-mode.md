# 027 — On a Bitget unified account in hedge mode, an isolated bot opens at the
# venue's default leverage, because the isolated leverage request is refused
# and the refusal is only logged

## 1. Definition

### 1.1 — expected

A futures bot with isolated margin at leverage N, on a Bitget unified (v3)
account, opens its position at N isolated. If the venue will not accept N, the
bot is told — it does not trade at some other leverage.

### 1.2 — actual

On a unified account in hedge (two-way) mode the position opens at the venue's
default isolated leverage (20x) while the bot is set to 2x, and nothing
reaches the bot. The connector's log carries, once per side, per bot start:

```
WARN Bitget UTA isolated long leverage for BTCUSD not set: DOUBLE_SIDE_HOLD afterShortLeverage and afterLongLeverage none validation error
WARN Bitget UTA isolated short leverage for BTCUSD not set: DOUBLE_SIDE_HOLD afterShortLeverage and afterLongLeverage none validation error
```

## 2. Required behaviour

- §2.1 Hedge mode: isolated leverage is set in ONE `set-leverage` request with
  `marginMode: isolated`, `longLeverage` and `shortLeverage` (Bitget v3 docs:
  "only applicable with isolated margin and two-way position mode"), no
  `posSide`.
- §2.2 One-way mode: one request per side with `leverage` + `posSide`
  (unchanged from before — no one-way refusal has been observed).
- §2.3 `futures_changeMarginType(symbol, ISOLATED, N)` on a unified account
  sets the isolated leverage and returns `notok` with the venue's reason when
  it is refused.
- §2.4 `futures_changeMarginType(symbol, CROSSED, N)` sends no isolated
  request.
- §2.5 `futures_changeLeverage(symbol, N)` sets cross leverage (its answer)
  and isolated leverage in the §2.1/§2.2 shape on a best-effort basis: the
  caller does not say which margin mode the bot trades, so an isolated refusal
  here is logged, not returned.

## 3. Evidence

- Every `Bitget UTA isolated … not set` line in the connector logs of the
  whole fleet since the unified line shipped carries the same
  `DOUBLE_SIDE_HOLD` reason — none from a one-way account.
- `uta_changeLeverage` sent `{ marginMode: 'isolated', posSide, leverage }`
  once per side and caught the failure into a `Logger.warn`, returning the
  cross result as success.
- `uta_changeMarginType` was a no-op returning success, so the margin step —
  the only call that carries the bot's margin mode — could not catch it either.
- Orders on the unified line carry `marginMode: isolated` per order
  (`uta_openOrder`), so the position opens isolated, at whatever isolated
  leverage the venue holds for the symbol: its default.

## 4. Assumption (hypothesis)

The hedge-mode refusal is caused by sending a single `posSide` instead of both
`longLeverage` and `shortLeverage`; the venue's error names exactly those two
fields as missing. Not verifiable against the live venue from here — the spec
stubs the venue with the rule its error message states.
