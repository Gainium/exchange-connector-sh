# 028 — A Bitget unified account in multi-assets mode margins inverse
# contracts from its whole wallet, but the platform still demands the
# contract's own coin

Follows [014](014.bitget-inverse-perpetuals-moved-to-the-unified-api.md).

## 1. Definition

### 1.1 — expected

On a Bitget Unified Trading Account whose `assetMode` is `multi_assets`, an
inverse (COIN-M) order is fundable from any coin in the wallet: a USDT-only
account can open DOGEUSD at cross margin. The platform lets the order reach
the venue, and the venue — the authority — accepts or refuses it.

### 1.2 — actual

The platform applies the classic rule "an inverse contract is margined in the
coin it is written on" before the order leaves:

- the trading terminal requires free base coin
  (`useVerifyTerminalBalance`: `coinm ? freeBase >= base : …`) and refuses
  with "Not enough assets to place order";
- the DCA and Combo engines compare the order against the base-coin balance
  (`checkBalance`), and their pooled-collateral escape hatch
  (`pooledMarginOrKeep`) skips COIN-M outright;
- the grid engine's swap check reads the base-coin balance too.

Reproduced 2026-09-24 on a unified sub-account holding 100 USDT and no DOGE:
a $10 DOGEUSD terminal order is refused.

## 2. Required behaviour

- §2.1 `getMarginAvailableUsd` on a Bitget futures connection answers
  `effEquity − imr` from `GET /api/v3/account/assets`, floored at 0, when
  `GET /api/v3/account/settings` reports a unified account with
  `assetMode: multi_assets`.
- §2.2 It answers `null` — "not pooled, keep the per-coin rule" — for any
  other `assetMode` (absent included), an `accountLevel` of `isolated`, a
  classic account, and an assets answer carrying no `effEquity`.
- §2.3 A non-pooled unified account costs one settings read, no assets read.
- §2.4 A classic account and a spot connection answer `null` (spot without
  asking the venue).
- §2.5 main-app: once the per-coin check of a COIN-M DCA/Combo deal or grid
  swap has failed, the pool (USD) is converted to the base coin at the deal
  price and may widen — never shrink — what is available. An isolated bot and
  a missing price keep the per-coin rule.
- §2.6 main-app exposes the figure to the dashboard as the GraphQL query
  `getPooledMarginAvailable(input: { uuid })` → `data: Float` (`null` when not
  pooled, for paper, and for spot).
- §2.7 Dashboard: when the terminal's base-coin check for a COIN-M, non-import,
  non-isolated order comes up short, it asks that query and passes when the
  pool covers the order's USD notional / leverage. While the answer is
  pending it does not block; a failed or `null` answer blocks as today.

## 3. Decisions

- **Per connection, not per pair.** `assetMode` and `accountLevel` are
  account-wide; `effEquity`/`imr` are account-wide. A per-pair answer would
  repeat the same figure. The existing `/marginAvailableUsd` channel (Kraken
  Futures flex) already has exactly this shape, so it is reused: no new
  endpoint, no `BaseReturn` change, and paper-trading needs no mirror (main-app
  never asks it — `Exchange.getMarginAvailableUsd` on a paper connection
  already degrades to "no opinion").
- **Single-asset mode keeps the base-coin rule.** Only `multi_assets` is
  treated as pooled; anything else, documented or not, answers `null`.
- **Classic accounts and every other exchange are unchanged.** Kraken's
  inverse connection already answers `null` (`!usdm`); every other venue
  inherits the abstract `null`. The COIN-M branch in main-app therefore only
  ever widens on a connection that reports a pool.
- **Out of scope:** the not-enough-balance latch
  (`spendableForNotEnoughBalance`). It only trips after the venue refuses an
  order for funds, which a pooled account will not do for these orders.

## 4. Assumptions (hypotheses)

- `effEquity − imr` is the USD the account can still commit. Both are
  documented as account-level figures (effective equity; initial margin
  requirement) but their exact netting — open-order margin in `imr` — has not
  been checked against a live account from here. If the figure is too wide the
  venue refuses the order, which is where it ends today; if too narrow, the
  terminal and engine refuse as they do today. Neither direction is worse than
  the current behaviour.
- An isolated bot on a `multi_assets` account is still margined per coin. Not
  verified; treated as not pooled so that uncertainty keeps today's behaviour.
