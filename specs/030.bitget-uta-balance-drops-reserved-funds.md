# 030 — A Bitget unified account's balance drops to its unreserved part
# while orders rest

Follows [014](014.bitget-inverse-perpetuals-moved-to-the-unified-api.md).
The same conversion lives in websocket-connector-sh
(`prepareBitgetUtaOutboundAccountInfo`); both must change together.

## 1. Definition

### 1.1 — expected

For a Bitget Unified Trading Account, a coin's `free + locked` is the coin's
full holding: what Bitget itself shows as the coin's value, including funds
reserved by resting orders and margin committed to open positions. Placing or
cancelling an order moves value between `free` and `locked` but does not
change the total.

### 1.2 — actual

`free + locked` equals the venue's per-coin `balance` field, and the venue
takes reserved funds OUT of that field. Every order placed shrinks the
reported total by the margin it reserves; every cancel restores it.

## 2. Evidence

Traced from the v3 private stream's published balances for a unified COIN-M
account (figures below are illustrative, in the same proportions). Under the
current code `free + locked` is the venue's `balance`:

| event                                   | free + locked |
|-----------------------------------------|---------------|
| no deal                                 | 1.000         |
| one limit order resting                 | 0.904         |
| that order cancelled                    | 1.000         |
| entry filled, position open             | 0.904         |
| six DCA orders placed, one by one       | 0.645 → 0.461 → 0.329 → 0.235 → 0.167 → 0.119 |
| ladder cancelled and re-placed          | climbs back to 0.904, then falls to 0.119 again |

The venue's own "Est. value" for the account stays at the full amount the
whole time; the platform stores the last row with 0 locked.

With the one resting order, `balance` plus `balance − available` came to
exactly the pre-order total: reserved funds leave `balance`, so `balance`
cannot anchor the total.

## 3. Observed (2026-09-27, raw v3 `account` snapshot)

The §3 hypothesis of the first fix — that per-coin `equity` is the full
total — was wrong. Snapshot for the same account with the ladder resting:

    totalEquity 634.73  unrealisedPnL 0
    BTC balance 0.00088924  equity 0.00088924  locked 0.00587569
        available -0.00498646  usdValue 75.3740391

`equity` equals `balance` and shrinks with it. `totalEquity` (USD) is the
venue's total: 634.73 at the coin's own price (usdValue / balance) is
0.0074884 BTC, the venue's "Est. value" 0.007488. The per-coin `locked`
alone (0.00588) does not close the gap either; position margin appears in
no per-coin field.

## 4. Required behaviour

- §4.1 Held funds are `totalEquity − unrealisedPnL − Σ usdValue` over every
  coin in the payload (`accountEquity` / `unrealisedPnl` over REST). Open P&L
  stays out, as on the classic futures path.
- §4.2 When held funds exceed one cent and exactly one reported coin has a
  price, they are added to that coin's total at its own price:
  `total = balance + held × balance / usdValue`,
  `free = clamp(available, 0, total)`, `locked = total − free`.
- §4.3 With several priced coins, or no account total, the coin figures stand
  (`balance`, or `available + locked`): there is no honest split.
- §4.4 The classic v2 paths are not touched.
- §4.5 REST (`convertUtaAssets`) and the stream
  (`prepareBitgetUtaOutboundAccountInfo`) produce the same partition for the
  same payload.
