# 031 — OKX X-Perp orders sent under the bare instFamily

Follows the X-Perp cache-miss refresh (1.20.23) and the funding-history fix
(1.19.15), which closed the same symptom on funding, leverage and candles.

## 1. Definition

### 1.1 — expected

Every OKX request for an X-Perp pair (`<BASE>-USD_UM_XPERP`) carries the live
instId with its expiry tag (`<BASE>-USD_UM_XPERP-<YYMMDD>`). This holds for
order placement, cancel and order lookup, for OKX Europe and non-Europe
instances, and whether or not a public instruments call happens to fail.

### 1.2 — actual

Live bot orders on X-Perp pairs are intermittently rejected with OKX 51001
("Instrument ID, Instrument ID code, or Spread ID doesn't exist"). The same
bots, on the same pairs, fill most of their orders.

## 2. Evidence

- Bot logs: every rejection is `Method limitOrders() Step Send new order
  request`, i.e. `openOrder`. They cluster: several bots rejected within the
  same second.
- OKX `/public/instruments?instType=FUTURES` on www, my and eea hosts lists
  the affected pairs as `ruleType=xperp, state=live`, instId with expiry tag.
  Nothing was delisted.
- The affected accounts are OKX Europe (`okxSource=my`), so `isEuPerp` is true
  and `ensureXperpMap()` does try to load the map.
- `ExchangeService.getExchange` builds a new exchange instance per request,
  so the instance-level `xperpMap` is empty on every order: each order,
  cancel and lookup downloads the whole FUTURES list (~280 KB).
- `ensureXperpMap` swallows a failed fetch (`.catch(() => [])`) and
  `updateSymbol` then falls through to `xperpMap.get(s) ?? s`, the bare
  instFamily.
- Without a symbol hint, a non-Europe instance never loads the map at all.

## 3. Assumption (hypothesis)

The rejected orders are the ones whose per-request instruments fetch failed
(most likely 50011 rate limit under a burst of orders), so the bare instFamily
was sent. The connector never logged the instId it sent, so this cannot be
read back from production directly. §4's logging closes that gap.

## 4. Required behaviour

- 4.1 The instFamily → instId map is process-wide, so a failed fetch after a
  successful one still resolves.
- 4.2 Concurrent loads share one in-flight request.
- 4.3 openOrder / cancelOrder / cancelOrderByOrderIdAndSymbol / getOrder pass
  the pair, so a fresh map that lacks the pair is refetched, and a non-Europe
  instance resolves X-Perp pairs.
- 4.4 A miss refresh is rate-limited per pair, not globally.
- 4.5 On OKX 51001, log the instId that was sent. For an X-Perp pair, mark
  the map stale so the next call refetches.
- 4.6 Non-X-Perp pairs are unchanged and never fetch X-Perp instruments.
