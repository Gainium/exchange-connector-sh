# 033 — Kraken Futures calls were rate-limited with the Kraken spot model

## §1 Definition

### §1.1 Expected

- **§1.1.1** Every private Kraken Futures (`krakenUsdm`) call is charged against
  one cost budget of **500 per 10 seconds** per account key, Kraken Futures'
  published derivatives limit
  (https://docs.kraken.com/api/docs/guides/futures-rate-limits). A call is
  admitted when the cost spent in the trailing 10 s plus its own stays within
  500; otherwise it waits until enough of the window expires. A refused call
  spends nothing.
- **§1.1.2** Each call costs what Kraken publishes for its endpoint:
  sendorder / cancelorder / editorder 10, orders/status 1, openorders 2,
  accounts 2, openpositions 2, fills 2 (25 with `lastFillTime`), GET
  leveragepreferences 2, PUT leveragepreferences 10.
- **§1.1.3** Public futures endpoints (tickers, instruments, candles, public
  trade history, funding-rate history) are free, as Kraken documents, and never
  wait.
- **§1.1.4** A futures method missing from the cost table is charged 10, not 0:
  a private call nobody listed must not be free.
- **§1.1.5** A real `apiLimitExceeded` from Kraken Futures fills the account's
  window, so the following calls wait a whole window instead of re-hitting a
  budget Kraken says is spent. It no longer downgrades the account's *spot*
  tier.
- **§1.1.6** Futures calls charge neither the spot REST counter nor the spot
  per-pair matching-engine counter.
- **§1.1.7** Kraken spot is unchanged: same counter, decay, tiers,
  matching-engine costs and batch paths.
- **§1.1.8** The hottest futures window is published as an extra
  `krakenFutures` usage entry (ratio in [0,1]). The balancer routes Kraken on
  `rest` only and ignores types it does not filter for, so this is visibility,
  not a routing input.

### §1.2 Actual (before)

`checkLimits` had no futures branch. Futures order-status reads went through
the spot REST bucket (20 tokens refilling at 0.5/s per account), and futures
place/cancel additionally through the spot matching-engine counter (cancel
charged 8 against a threshold of 125 refilling at 2.34/s per pair). Once an
account burst past 20 calls — a price move filling many DCA levels, each
followed by an order-status read and a take-profit cancel + re-place — its
calls were released one every ~2 s, about 25× below what Kraken Futures
allows for order-status reads. The throttle was local: Kraken's own budget
was nowhere near spent.

`futures_getAvgFillPrice` called `fills` without charging any budget.

### §1.3 Assumption

The 500/10 s derivatives budget applies per API key, matching the spot
per-key accounting and the balancer's account-sticky routing for Kraken
private routes. Kraken's page does not state the scope; if it were per
account across several keys, one account with several keys could overshoot,
and Kraken's `apiLimitExceeded` handling (§1.1.5) covers that case.

### §1.4 Out of scope

- The `/history` pool (100 tokens, +100 per 10 min), used by the futures
  order-events fallback in `getOrder`, stays uncharged. Charging it would add
  local waits without evidence Kraken requires them. Revisit if `apiLimitExceeded` appears on history calls.
- A futures `batchorder` path (cost 9 + n). With the correct budget, a
  per-order cancel + place storm fits easily (25 cancel+place pairs = 500), so
  batching is not needed to remove the queueing.
