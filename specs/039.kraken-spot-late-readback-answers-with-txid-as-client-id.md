# 039 — A Kraken spot order read back late is answered under its txid

## 1. Definition

### 1.1 — expected

`KrakenExchange.openOrder` (spot) answers a placement with the order it
placed. When the caller sent a `newClientOrderId`, the answer's
`clientOrderId` is that id and its `orderId` is the txid Kraken issued —
whichever read produced the answer.

### 1.2 — actual

After `AddOrder` returns a txid, `openOrder` reads the order back with
QueryOrders, three tries 500 ms apart, passing the caller's client id. When
all three miss (QueryOrders lags a just-placed order), the last-resort read
is `getOrder({ newClientOrderId: txid })`. That routes through the txid path,
which labels the order with the id it was asked for — the txid. The answer
then reports `clientOrderId === orderId === txid`, and a consumer matching
the answer to its request by client id sees an order it never sent.

### 1.3 — unchanged

- The last-resort read still goes by txid (exact QueryOrders lookup, never
  the userref scan for a txid).
- A failed last-resort read is returned as it is.
- No txid returned: the read goes by client id, as before.
- No client id sent: the answer keeps the txid as its client id.
- Which orders are placed, and how often anything is asked.

## 2. Evidence

- A Kraken spot placement was accepted at 14:16:32 (the connector's
  broker-tag log line names the txid), and the bot saved the answer about
  3 s later. Three read-back misses plus the fallback account for those 3 s;
  a first-try hit answers in under 1 s.
- The bot's event for that placement names the txid where it prints the
  answer's client order id. The primary read-back passes the caller's id, so
  only the last-resort read can produce a txid there.
- The same shape recurs across Kraken spot placements over the past month.

## 3. Assumption

The only code path that labels a fresh placement with its txid is the
last-resort `getOrder` call in `openOrder`. Supported by reading every
`convertSpotQueryOrder` caller reachable from `openOrder`.
