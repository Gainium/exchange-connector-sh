# 041 — a Hyperliquid cancel whose size shrank without a trade is read back as executed

Bug spec (SKILL.md Part 0). Scope: `src/exchange/exchanges/hyperliquid/index.ts`
(`getOrder`, `convertOrder`) and `src/exchange/exchanges/hyperliquid/orderFills.ts`
(`collectOrderFills`). Companion of websocket-connector-sh spec 020, which fixed
the same reading on the user-stream path.

## §1 Definition

### §1.1 Expected

`getOrder` for a Hyperliquid order that ended without filling (`canceled`,
`reduceOnlyCanceled`, `marginCanceled`, … — any status other than `open` and
`filled`) reports an executed size, quote and fee equal to the order's real
fills on the venue: zero when it has none.

### §1.2 Actual

`convertOrder` sets `executedQty = origSz − sz`. Hyperliquid can lower `sz` on a
resting order without a trade (a reduce-only order shrunk to the position it
can still reduce), so a `reduceOnlyCanceled` order with `sz 0.041` of
`origSz 0.044` and no fill is read back as `CANCELED`, 0.003 executed, no fee.
`getOrder` already fetches the order's fills from `userFillsByTime` for the
price, but only uses them for price and fee, never for the size.

## §2 Evidence

- Production, after the stream-side fix (spec 020) was deployed: new
  Hyperliquid order rows with status CANCELED, `executedQty = origSz − sz`, no
  fills, no fee — reduce-only grid orders on perps.
- The bot log for a sampled order shows the stream CANCELED was never processed
  by the bot; the row was written by the bot's cancel path ("Order not found" →
  "Real order … status: CANCELED" → "Save order … with status CANCELED"), i.e.
  from this `getOrder`, not from the stream.
- The stream frame for that order: `reduceOnlyCanceled`, `sz 0.041`,
  `origSz 0.044`, no `userFills` for the cloid.
- Origin: latent — `executedQty: origSz − sz` dates from the Hyperliquid
  integration (1ab4275, 2025-09-24).

## §3 Assumption (root cause, hypothesis)

`origSz − sz` is not evidence of a fill; the fill history is. When the history
window was read to its end (`collectOrderFills` stopped on a short page) and the
order's fills sum to less than `origSz − sz`, the fills are what executed.

## §4 Requirements

- **§4.1** Non-filled terminal status, history read to the end, no fill for the
  oid → executedQty 0, quote 0, no fee.
- **§4.2** Same, history holds fills summing to less than `origSz − sz` →
  executedQty, quote and fee from those fills.
- **§4.3** Fills cover `origSz − sz` (a real partial fill before the cancel) →
  unchanged (price and fee from fills, size `origSz − sz`).
- **§4.4** History not read to the end (page cap, unadvanceable page) or the
  lookup threw → unchanged `origSz − sz`: an unread history is no evidence.
- **§4.5** `filled` and `open` orders → unchanged.
- **§4.6** §4.1/§4.2 apply only if the account's retained history reaches back
  to the order's placement. `userFillsByTime` serves only an account's most
  recent fills (~10,000; a busy account measured on 2026-10-31 kept ~25h), so
  before lowering the size one more request (`startTime: 0`, oldest retained
  fills first) checks it: a short page or an oldest fill strictly before
  `order.timestamp` → covered. Not covered, or that request failed →
  unchanged `origSz − sz` (price from the fills found), warned.

## §5 Known limit

The retention limit this section used to accept is handled by §4.6. If the
fills lookup itself throws, `origSz − sz` is still returned (§4.4) — getOrder
has to return an order, and an error would change its contract with main-app.
