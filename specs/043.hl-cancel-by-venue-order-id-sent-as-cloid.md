# 043 — cancelling a Hyperliquid order by its exchange order id fails with "422 Failed to deserialize"

Bug spec (SKILL.md Part 0). Scope: `src/exchange/exchanges/hyperliquid/index.ts`
(`cancelOrderByOrderIdAndSymbol`, and the `oid` sent by `getOrder`).

## §1 Definition

### §1.1 Expected

`cancelOrderByOrderIdAndSymbol({symbol, orderId})` (DELETE `/orders/byid`)
cancels the order whose EXCHANGE order id is `orderId`, the same id this
connector reports as `CommonOrder.orderId` (Hyperliquid's `oid`). It returns the
cancelled order read back from the venue, like `cancelOrder` does.

### §1.2 Actual

The method forwarded `orderId` to `cancelOrder` as `newClientOrderId`, which
sends it as the `cloid` of a `cancelByCloid` action. A cloid must be `0x` + 32
hex characters, so for a numeric oid Hyperliquid rejects the request body:
`422 Unprocessable Entity - Failed to deserialize the JSON body into the target type`.

## §2 Evidence

- Production: `closeOrderOnExchange({symbol:"TAO-USDC", orderId:"590895215023"})`
  on a Hyperliquid perp account returned exactly that 422.
- Live venue probe with a throwaway wallet: `cancelByCloid` with cloid
  `590895215023` → 422 deserialize; with a well-formed cloid, and `cancel` with
  `{a, o: 590895215023}` → both past deserialization ("User or API Wallet does
  not exist"). Info `orderStatus` with `oid` as a numeric STRING → 422; as a
  number → `unknownOid` (accepted).
- The real class at HEAD, `cancelOrderByOrderIdAndSymbol` against the live API →
  the same 422; with the change → past deserialization.
- Callers: main-app `cancelOrderOnExchange` (GraphQL `closeOrderOnExchange`,
  `importExchangeOrder`) is the only consumer; V2 sends `order.orderId` (the oid).
  Bots cancel through `cancelOrder` (cloid), not this method.
- Origin: latent — the method dates from the Hyperliquid integration (e5af83b,
  2025-09-17).

## §3 Assumption (root cause, hypothesis)

The by-order-id entry point reuses the cloid cancel, so the exchange id is sent
in a field that only accepts a client id. Cancelling with Hyperliquid's `cancel`
action (`o` = oid as a number) and reading back by the numeric oid fixes it.

## §4 Requirements

- §4.1 Numeric `orderId` → `cancel({cancels:[{a: asset, o: Number(orderId)}]})`,
  no `cancelByCloid`; read-back `orderStatus` receives the oid as a number.
- §4.2 Cloid-shaped `orderId` (`0x` + 32 hex) → `cancelByCloid`, as before, so a
  caller that already sends the client id keeps working.
- §4.3 `cancelOrder` (the bots' cancel) is unchanged.
- §4.4 Any other `orderId` → NOTOK, nothing sent to the venue.
- §4.5 `getOrder` with a cloid → `orderStatus` receives it unchanged.

## §5 Known limit

Not verified against a funded account (cancelling a real user's resting order
is a write to their account); the venue-level probe proves only that the
request now deserializes and reaches authorization.
