# 044 — A Kraken key that cannot read or cancel orders passes verification

Bug spec. Owner: `src/exchange/helpers/verify.ts` (`verifyKraken`) and
`src/exchange/exchanges/kraken/index.ts` (`verifyOrderPermissions`).

## 1. Definition

Expected: verifying a Kraken spot key that lacks "Orders and trades — Query open
orders & trades" or "— Cancel & close orders" fails with a message naming the
missing permission.

Actual: verification probes only Balance (funds query) and the WebSocket token,
so such a key passes. Its bots cannot read their own orders
(`EGeneral:Permission denied` on open orders) and, when closed, cannot cancel
them (`EGeneral:Permission denied` on cancel): the orders keep resting on the
exchange, holding the account's funds.

## 2. Evidence

Production grid bot on a Kraken spot key: `getActiveOrders()` refused with
`EGeneral:Permission denied` from the first minutes; the user's close refused
the same way on cancel; 35 orders kept resting. The key had passed
verification when it was added.

## 3. Assumption

Verification has no probe for the order-query or cancel permission.

## 4. Behaviour

4.1 After Balance and the WebSocket probe pass, `verifyOrderPermissions()` asks
for open orders, then sends a cancel addressed to a fresh random `cl_ord_id`
(a UUID no order carries; never a txid or userref, which could match a real
order). A permitted key gets the list / `EOrder:Unknown order`.

4.2 Only a definite `EGeneral:Permission denied` fails verification, naming the
permission. Rate limits, 5xx and any other answer pass, as for the WebSocket
probe. Kraken Futures keys are not probed.

4.3 Open question: Kraken does not document whether it checks the cancel
permission before it looks the order up. If it looks the order up first, a key
without the permission gets `EOrder:Unknown order` and still passes. That is a
missed refusal, never a false one.

Test: `src/exchange/exchanges/kraken/order-permissions.spec.ts`.
