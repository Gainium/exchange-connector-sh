# 045 — A Kraken batch order lookup the venue rejects becomes a bare 500

Bug spec. Owner: `src/exchange/exchanges/kraken/index.ts` (`getOrdersBatch`).

## 1. Definition

Expected: `POST /orders/batch` for Kraken spot, when the venue rejects the
QueryOrders call (e.g. `EGeneral:Permission denied` for a key without order-query
permission, a nonce or rate-limit error, a transport failure), answers a NOTOK
`BaseReturn` whose `reason` is the venue's message. The log carries that
message only.

Actual: the SDK throws on a venue error array even with HTTP 200. `getOrdersBatch`
awaited it with no catch, so the throw escaped the controller and Nest's
exception handler answered `500 Internal server error`, logging the whole thrown
object (credential fields redacted by `RedactingExceptionFilter`, but a
multi-line dump per call).

## 2. Evidence

Connector error log: `[ExceptionsHandler] Object(6) { code:
200, message: 'OK', body: { error: ['EGeneral:Permission denied'] } …`, one per
batch lookup, each followed by the per-order `getOrder` fallback logging
`Kraken API error: EGeneral:Permission denied`. Credential fields in those dumps
read `[REDACTED]`. Reproduced in `spot-orders-batch-error.spec.ts` with a stubbed
SDK that throws: `getOrdersBatch` rejected.

## 3. Assumption

`querySpotOrdersChunk` wraps the same SDK call in try/catch; `getOrdersBatch`
(added in 432415f, 1.20.13) does not.

## 4. Behaviour

- §4.1 A throw on the first chunk → NOTOK with the venue's reason, never worded
  "not supported" (main-app latches batching off on that wording).
- §4.2 Logged as `krakenErrorMessage(error)` only; `noteKrakenRateLimit` is fed.
- §4.3 A throw on a later chunk keeps the rows already resolved (OK, partial).
- Unchanged: a non-throwing error answer still declines via `super`; no change
  to how orders are placed or cancelled.
