# 046 — Kraken Futures `getOrder` reports the request time as the order's update time

Bug spec. Owner: `src/exchange/exchanges/kraken/index.ts` (futures `getOrder`, `futures_convertOrder`).

## 1. Definition

Expected: `GET /order` for a Kraken Futures order answers `updateTime` = the time
Kraken last changed the order (its fill, cancel or edit) and `transactTime` = when
it was placed, as every other venue does. `Date.now()` only when Kraken gives no time.

Actual: neither `getOrder` path passed a time to `futures_convertOrder`, whose
fallback is `Date.now()`. Every answer said "this order last changed the instant
you asked". A consumer comparing that time with another event (main-app's venue
order probe: did this fill land after its deal closed?) read every old fill as new.

## 2. Evidence

The venue order probe's rows for Kraken Futures fills carry a `venueUpdateTime`
1 ms before their own `checkedAt`, on every such row; no row of any other venue
does. One was a grid exit the user stream reported FILLED about 2 s BEFORE its
deal closed, recorded as filled more than an hour after the close.

## 3. Assumption

The two paths drop times Kraken does return: `getOrderStatus` →
`order.lastUpdateTimestamp` / `order.timestamp` (ISO strings); `getOrderEvents` →
the element's `timestamp` (epoch ms) for the latest state `krakenLatestHistoryState`
picks. Passing them through fixes the time and nothing else.

### §2.1 History path: `updateTime` = the latest event's timestamp.
### §2.2 Open-orders path: `updateTime` = `lastUpdateTimestamp`, `transactTime` = `timestamp`.
### §2.3 No time from Kraken: `Date.now()`, as before.
### §2.4 `krakenFuturesTimeMs` parses epoch ms (number or digit string) and ISO; anything else is undefined.

Test: `src/exchange/exchanges/kraken/futures-order-venue-time.spec.ts`.

## 4. Out of scope

Kraken spot `getOrder` has the same `Date.now()` fallback (`convertOrder` is called
without `closetm`/`opentm`); tracked separately.
