# 048 — Bitget classic fee sweep cannot finish inside the caller's deadline

Bug spec. Owner: `src/exchange/exchanges/bitget/index.ts`
(`spot_getAllUserFees`, `futures_getAllUserFees`).

## 1. Definition

Expected: `getAllUserFees` for a classic Bitget key answers with this account's
own maker/taker rate for every listed pair, quickly enough that the caller
(exchange-balancer gives `/fees/all` 5 minutes) receives it.

Actual: one signed `GET /api/v2/common/trade-rate` per listed pair, 8 at a
time. Bitget documents that endpoint at **10 requests/s per UID**, and the spot
listing is ~3,660 pairs, so the sweep needs at least ~366 s even at the
venue's ceiling — it can never finish inside 300 s. Sent 8-wide it also runs
into `too many requests`, and each refused pair is answered with the pair's
*publicly listed* rate.

## 2. Evidence

- Public listing on 2026-11-21: 3,666 spot symbols, 892 USDT-M + 50 USDC-M.
- Prod connector log (62.84.191.108, 2026-11-21 09:44–09:51): `Error getting
  spot fees for PAXGUSDT … too many requests` and 220 more lines of the same
  shape; `Bitget request must sleep … Method: getTradeRate` lines in earlier
  archives.
- Cron: `Catch code … Internal Server Error, endpoint: fees/all, exchange:
  bitget` every run since 2026-11-20 (the balancer's deadline expiring).
- Bitget classic docs list `GET /api/v2/common/all-trade-rate`
  ("Get Business Line All Symbol Trade Rate"): signed, `businessType` only,
  same 10/s/UID limit, `data: [{symbol, makerFeeRate, takerFeeRate}]`. Unsigned
  it answers `40006 Invalid ACCESS_KEY` exactly like `trade-rate` does.

## 3. Assumption (hypothesis)

The per-pair fan-out is the cause; one `all-trade-rate` call per business
line returns the same per-account rates the per-pair endpoint does. Because
that equivalence could not be checked against a live account from here, the
fix proves it on every sweep (§3.4) instead of trusting it.

### §3.1 Spot: one `all-trade-rate` call (`businessType: spot`) prices every listed pair; at most one `trade-rate` call.
### §3.2 Futures: the same with `businessType: mix`.
### §3.3 A listed pair the batch leaves out keeps the listed rate, marked `source: 'ladder'` so main-app never lets it overwrite a stored rate.
  *(Amended by spec 049: a gap of up to 100 pairs is first asked per-symbol; only pairs that still fail, or a larger gap, keep the ladder rate.)*
### §3.4 Probe: one pair is also asked per-symbol; if the two disagree the batch is not trusted and the sweep falls back to the per-pair fan-out (previous behaviour).
### §3.5 A unified-account refusal from the batch routes to v3; a key refusal is the call's result. No fan-out either way.
### §3.6 Any other batch failure (unknown endpoint, malformed body) falls back to the per-pair fan-out.

Test: `src/exchange/exchanges/bitget/all-trade-rate.spec.ts`.

## 4. Out of scope

- The fan-out's own per-pair fallback stays unmarked (existing tests pin its
  shape); it now runs only when the batch is unusable.
- `uta_getAllUserFees`' missing-pair fallback (already one call per category).
