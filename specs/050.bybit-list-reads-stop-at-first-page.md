# 050 — Bybit open-order and position list reads stop at the first page

Bug spec (existing behaviour is wrong).

## §1 Definition

`getAllOpenOrders()` and `futures_getPositions()` owe their caller the
**complete** list (or a NOTOK), in the same `BaseReturn<T>` shape as today.
Callers decide from these lists whether an order is still resting or a
position still open, so a missing row reads as "gone".

### §1.1 Expected

- Every page Bybit holds is read, sequentially, following the response's
  `nextPageCursor` (sent back as `cursor`) until it is empty. Each request asks
  for the largest page the endpoint allows (`/v5/order/realtime`: 50;
  `/v5/position/list`: 200).
- This holds for both branches of each method: the linear no-symbol branch
  that loops settle coins, and the single-request branch (spot, inverse, or a
  given symbol).
- A page that answers a non-`OK` `retMsg`, or rejects, fails the WHOLE read
  through the existing `handleBybitErrors` path (retry the whole read for a
  retryable error, otherwise NOTOK). A partial list is never returned as OK.
- A cursor that repeats, or a read that has not ended after a bounded number
  of pages, fails the read as NOTOK instead of looping.
- The count overload (`returnOrders` falsy) answers the number of open orders
  on every page.
- The returned shape is unchanged: `BaseReturn<CommonOrder[]>`,
  `BaseReturn<number>`, `BaseReturn<PositionInfo[]>`.

### §1.2 Actual

- `getActiveOrders` is called once per settle coin (and once in the single
  branch) with no `limit` and no `cursor`. Bybit's documented default page is
  20 (`limit` "[1, 50]. Default: 20"), so orders 21+ per request are dropped
  and the call answers OK.
- `getPositionInfo` sends `limit: 200` but never follows `nextPageCursor`, so
  positions past 200 per request are dropped the same way.
- The linear settle-coin loop of `getAllOpenOrders` has no `.catch`: a rejected
  page rejects the method. Its count overload answers 0 for any account,
  because rows are only collected when `returnOrders` is set.

## §2 Evidence

- Bybit v5 docs, Get Open & Closed Orders: `limit` "Limit for data size per
  page. [1, 50]. Default: 20"; `cursor` "Use the nextPageCursor token from the
  response to retrieve the next page". Get Position Info: `limit` "[1, 200].
  Default: 20", same cursor contract.
- Live read through the dashboard GraphQL `getAllOpenOrders` (which calls this
  method with no symbol): three linear accounts of one user each returned
  exactly 20 open orders over 10 symbols, while our NEW order rows on two of
  those accounts number 22, the two extras being on an 11th symbol that is
  absent from the venue list.
- `src/exchange/exchanges/bybit/index.ts` `getAllOpenOrders`: neither
  `getActiveOrders` call carries `limit` or `cursor`; `futures_getPositions`:
  neither `getPositionInfo` call carries `cursor`.

## §3 Assumption (hypothesis)

The missing orders are on page two: the connector reads one default page per
request. The test in §4 fails on the current code because only the first
page's rows come back while the stub holds a second page behind
`nextPageCursor`.

## §4 Tests

`src/exchange/exchanges/bybit/list-paging.spec.ts`:

- §1.1 two pages (20 + 6) on the linear loop → 26 orders, count 26, each
  request asks `limit: 50`, the second carries the first page's cursor.
- §1.1 the same on the single-request branch (spot).
- §1.1 page two answers non-OK → NOTOK, no data; page two rejects → NOTOK,
  the method does not reject.
- §1.1 a cursor that repeats → NOTOK.
- §1.1 positions: two pages on the linear loop → every position returned.
