# 053 — A Kraken Futures order aged out of the events page is read from the account fills

Bug spec (Definition / Evidence / Assumption). Test:
`src/exchange/exchanges/kraken/futures-order-aged-out-fills.spec.ts`.

## §1 Definition

`getOrder` on Kraken Futures asks the live status view (`getOrderStatus`) first. That view only knows
orders that are open, or that ended in the last few seconds. Anything else falls back to the order-events
page (`getOrderEvents`).

**Expected.** An order that executed on the venue is reported as executed, whatever page it has aged out of.

**Actual.** The events page is only Kraken's most recent slice of history. Once an order leaves it, the
fallback answers `Order not found in history` without looking anywhere else. main-app reads that as a
definitive "no such order" and, after its retry ladder, writes the order off as CANCELED with nothing
executed. A sell that filled while the user stream was down therefore leaves its units in the deal and its
proceeds unbooked.

## §2 Evidence (prod, read-only)

2026-10-30, Kraken Futures combo grid sells. From ~02:26Z Kraken Futures answered `503`; the user stream
delivered no fill. The sells filled on the venue during the day (the account fills carry our client order
id and the full size). From 05:03Z the connector answered `Order not found in history` for them, and at the
deal close main-app logged `Order not found after 5 lookup(s), order … status set to CANCELED`. The account
fills fallback added for history snapshots that say less than the fills only runs when an event IS found.

## §3 Assumption (root cause) and requirements

- §3.1 The no-event branch returns not-found without asking the account fills. When the live view answered
  that it does not hold the id and the fills hold executions against our client order id, report the order
  `FILLED` with the summed size and the size-weighted price. Kraken gives no order size on this path, so
  `origQty` is what executed; main-app compares it with its own size (main-app-sh spec 270).
- §3.2 Unchanged: no fills for the id (a cancel or reject with nothing executed), or a refused/failed fills
  read, is still the definitive not-found. A cancel or reject still on the events page is answered from it
  exactly as before.
- §3.3 When the live view did NOT answer (the call returned no `success`), the fills are not consulted: the
  order may still be resting, part-filled, and its fills would not be its whole execution.
- `BaseReturn<T>` is unchanged. `getAccountFills`' failure reason now carries Kraken's own error word
  (`authenticationError` for a key without the query-trades permission), so a caller can tell a permanent
  refusal from a blip.

## Invariants

The wrong state lives in main-app's books: `main-app/deals`
`deals.kraken-futures-combo-closed-holding-written-off-exits` (observe).
