# 056 — Bybit USDT-M / COIN-M publish their futures account fills

Bug spec (Definition / Evidence / Assumption). Test:
`src/exchange/exchanges/bybit/account-fills.spec.ts`.

## §1 Definition

`GET /accountFills` (`getAccountFills`) is the read-only feed of executions on the account. main-app uses it
to price a futures position the bot did not close, such as a venue liquidation or a hand close on the
exchange. Kraken Futures (spec 053) and Bitget USDT-M (spec 054) answer it. Bybit answered the abstract
default, which is an empty page.

**Expected.** On Bybit linear (USDT-M) and inverse (COIN-M) the feed returns the account's own
position-moving executions, newest first, so a caller can price an outside close from the venue's record.

**Actual.** Bybit answers an empty page. main-app therefore closes a Bybit futures deal whose position was
closed on the venue as "profit unknown", and the real loss is never booked.

- §1.1 A futures account reads `/v5/execution/list` (`category` linear/inverse, `limit` 100, no symbol).
- §1.2 Each row maps to an `AccountFill`:
  - `fillId` is `execId`; `orderId` passes through.
  - `clientOrderId` is `orderLinkId`. Every bot order carries one; a hand or venue order carries none.
  - `symbol` is uppercased; `side` is `Sell` → SELL, else BUY.
  - `price` is `execPrice`, `quantity` is `execQty`, `timestamp` is `execTime`.
- §1.3 Forced closes are typed in the vocabulary the other fill venues use: `BustTrade` → `liquidation`,
  `AdlTrade` → `unwindCounterparty`. Any other type passes through as sent (`Trade`).
- §1.4 Only `Trade`, `BustTrade` and `AdlTrade` rows are kept. `Funding` rows carry a quantity and the mark
  price but trade nothing; `Settle`, `Delivery`, `MovePosition` and the rest are not fills.
- §1.5 `fee` is `execFee`, only on linear (the quote coin) and only when it is ≥ 0. Inverse charges the
  base coin and a negative fee is a maker rebate; both are left out.
- §1.6 `sinceMs` pages backwards: `endTime = sinceMs − 1`. Bybit then answers `[endTime − 7 d, endTime]`;
  with no `sinceMs` it answers the last 7 days.
- §1.7 The venue's `nextPageCursor` is followed until 100 kept rows are in hand, at most 5 venue pages,
  stopping on a repeated cursor. Each venue page goes through `checkLimits`. A run of funding rows
  therefore cannot end the history early.
- §1.8 A non-OK venue answer fails the read (`NOTOK` via `handleBybitErrors`), never an empty OK page.
- §1.9 Spot answers an empty page and sends no request.

## §2 Evidence

A Bybit linear TRXUSDT long position was zero on the venue from about 15:36 UTC. The bot closed the deal
about 18 h later, and its log says "position closed outside the bot and the venue fills do not account for
it — closing the deal, profit unknown". The deal is flagged `closedExternally` + `profitUnknown`, with a
profit far from the real loss. `BybitExchange` has no `getAccountFills` override (grep), so main-app's
`venueCloseEvidenceFor` got the abstract default `[]` and returned no evidence.

## §3 Assumption

The empty page is the abstract default, not a venue limitation. Bybit publishes the account's executions on
`/v5/execution/list` (`RestClientV5.getExecutionList`): newest first, ≤ 100 per page, cursor-paged, with
`orderLinkId`, `execType` and `execFee` on each row. Tests §1.1 and §1.4–§1.9 fail against the unmodified
adapter because it never calls the venue.

## §4 Contract

Additive. There is no new route and no change to `BaseReturn` or `AccountFill`; the `fillType` doc now
notes the shared forced-close vocabulary. Kraken and Bitget answers are unchanged. main-app's
`isForcedCloseFillType` already recognises `liquidation` and `unwindCounterparty`, so no consumer change is
needed.
