# 057 — Binance USDⓈ-M / COIN-M publish their futures account fills

Bug spec (Definition / Evidence / Assumption). Test:
`src/exchange/exchanges/binance/account-fills.spec.ts`.

## §1 Definition

`GET /accountFills` (`getAccountFills`) is the read-only feed of executions on the account. main-app uses it
to price a futures position the bot did not close: a hand close in the Binance app or a venue liquidation.
Kraken Futures (053), Bitget USDT-M (054) and Bybit (056) answer it. Binance answered the abstract default,
which is an empty page.

**Expected.** On Binance USDⓈ-M and COIN-M, the feed returns the account's own trades on the symbol asked
for, newest first, with the bot's own trades told apart from everything else. A caller can then price an
outside close from the venue's own record.

**Actual.** Binance answers an empty page. main-app closes a Binance futures deal whose position was closed
on the venue as "profit unknown", with profit 0, and the real result is never booked.

- §1.1 The route takes an optional `symbol`. Binance's trade feed is per-symbol: with no symbol, and on spot,
  it answers an empty OK page and sends no request. Other venues ignore `symbol`.
- §1.2 With a symbol, futures reads `userTrades` (`/fapi/v1` USDⓈ-M, `/dapi/v1` COIN-M) with `limit` 1000.
  Each page goes through `checkLimits('getAccountFills', 'request', w)`, with w = 5 on USDⓈ-M and 20 on
  COIN-M, the venue's own weights.
- §1.3 `sinceMs` reads the 7 days strictly before it: `endTime = sinceMs − 1`, `startTime = endTime − 7 d +
  1`. With no `sinceMs` the venue answers its default, the last 7 days.
- §1.4 A full page is followed forward from just after its newest trade (at most 5 pages), so the newest
  trades are always read whichever end of the window the venue pages from.
- §1.5 Trades carry no client order id. Each distinct order, newest first and at most 20 of them, is looked
  up once (`getOrder` by `orderId`, weight 1) and attributed by the client id on it:
  - `web_` / `ios_` / `android_` / `electron_` (venue-assigned to a hand order) → `clientOrderId` empty,
    `source` = the channel upper-cased;
  - `autoclose-…` → `fillType` `liquidation`; `adl_autoclose…` → `unwindCounterparty`;
    `…settlement_autoclose…` / `…delivery_autoclose…` → `settlement`; all of these have `source` `SYS`
    and an empty `clientOrderId`;
  - any other id was supplied by an API client (a bot's own orders among them) → kept, `source` `API`.
- §1.6 Each trade maps to `AccountFill`:
  - `fillId` is `id`, and `orderId` passes through;
  - `symbol` is upper-cased; `side` is `SELL` → SELL, otherwise BUY;
  - `price`, `quantity` = `qty` (contracts on COIN-M), `timestamp` = `time`;
  - `realizedPnl` passes through.

  `fee` is `|commission|`, set only on USDⓈ-M and only when `commissionAsset` is the symbol's quote coin.
  A BNB-paid fee and COIN-M's base-coin fee are left out.
- §1.7 The answer is cut at the newest trade whose order cannot be attributed (the venue no longer has it,
  `-2013`, or it is past the lookup cap). What is returned is always an unbroken newest-first run, never one
  with a gap a newest-first walk could step over.
- §1.8 Any other venue error fails the read (`NOTOK` via `handleBinanceErrors`). It is never an empty OK
  page.

## §2 Evidence

Binance USDⓈ-M deals whose position was closed outside the bot were closed by the bot with profit 0, no
`closeTrigger`, and the "profit unknown" outside-close path. `BinanceExchange` has no `getAccountFills`
override (grep), so main-app's `venueCloseEvidenceFor` got the abstract default `[]` and found no evidence.

## §3 Assumption

The empty page is the abstract default, not a venue limitation. Binance publishes the account's trades on
`userTrades`. That feed is symbol-required on USDⓈ-M and limited to a ≤ 7-day window, and each row carries
`orderId`, `side`, `price`, `qty`, `commission`, `commissionAsset`, `realizedPnl` and `time` but no client
order id. Binance stamps a venue-assigned client id on every order that was not given one (the hand-trade
channel prefixes, `autoclose-` / `adl_autoclose` for its own closes). main-app gives every bot order an id
starting with its broker code. Tests §1.2–§1.5, §1.7 (endpoint) and §1.8 fail against the unmodified
adapter, because it never calls the venue.

## §4 Contract

Additive. `GET /accountFills` gains an optional `symbol` query param. `AccountFill` gains an optional
`realizedPnl`. `getAccountFills(sinceMs?, symbol?, timeProfile)` is the new signature on every venue.
Kraken, Bitget and Bybit ignore `symbol`, and their retries replay the same arguments, so their answers do
not change. A caller that sends no symbol gets exactly what it got before. paper-trading has no
`/accountFills` route.
